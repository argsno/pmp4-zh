4.1 现代 GPU 的体系结构

图 4.1 展示了典型支持 CUDA 的 GPU 体系结构的高层视图（从 CUDA C 程序员的角度看）。GPU 由一组高度线程化的流式多处理器（SM）构成。每个 SM 包含多个称为流处理器或 CUDA 核心的处理单元（为简洁起见，下文简称核心），在图 4.1 中以 SM 内部的小方块表示，这些处理单元共享控制逻辑和内存资源。例如，Ampere A100 GPU 拥有 108 个 SM，每个 SM 有 64 个核心，整个 GPU 共有 6912 个核心。

SM 还带有不同的片上内存结构，在图 4.1 中统称为“Memory”（内存）。这些片上内存结构将是第 5 章“内存体系结构与数据局部性”的主题。GPU 还带有数 GB 的片外设备内存，在图 4.1 中称为“Global Memory”（全局内存）。早期的 GPU 使用图形双倍数据速率同步 DRAM，而较新的 GPU（从 NVIDIA 的 Pascal 架构开始）可能使用 HBM（高带宽内存）或 HBM2，它们由与 GPU 紧密集成在同一封装中的 DRAM（动态随机存取存储器）模块组成。为简洁起见，在本书其余部分我们将所有这些类型的内存统称为 DRAM。我们将在第 6 章“性能考量”中讨论访问 GPU DRAM 所涉及的最重要概念。

4.2 线程块调度

当核函数被调用时，CUDA 运行时系统启动一个执行核函数代码的线程网格。这些线程按线程块逐个分配到 SM 上。也就是说，一个线程块中的所有线程被同时分配到同一个 SM。

图 4.2 说明了线程块到 SM 的分配方式。多个线程块很可能会同时分配到同一个 SM。例如在图 4.2 中，每个 SM 分配了三个线程块。然而，线程块需要预留硬件资源才能执行，因此同时分配给给定 SM 的线程块数量是有限的。线程块数量的上限取决于多种因素，这些因素将在第 4.6 节中讨论。

由于 SM 数量有限，且每个 SM 能够同时分配的线程块数量也有限，因此在 CUDA 设备中能够同时执行的线程块总数存在上限。大多数网格包含的线程块远多于这一数目。为了确保网格中的所有线程块都能得到执行，运行时系统维护一个待执行线程块的列表，并在先前分配的线程块执行完毕后，向 SM 分配新的线程块。

以线程块为单位把线程分配到 SM，保证了同一线程块内的线程被同时调度到同一个 SM 上。这一保证使得同一线程块内的线程能够以跨线程块的线程之间所不可能的方式进行交互。1 这包括屏障同步，相关内容将在第 4.3 节讨论；也包括访问位于 SM 上的低延迟共享内存，相关内容将在第 5 章“内存体系结构与数据局部性”中讨论。

4.3 同步与透明可扩展性

CUDA 允许同一线程块内的线程使用屏障同步函数__syncthreads()来协调各自的活动。注意，“__”由两个“_”字符组成。当一个线程调用__syncthreads()时，它将被阻塞在该调用所在的程序位置，直到同一线程块中的每个线程都到达该位置。这保证了线程块中所有线程都完成执行的某个阶段后，才允许其中任何一个线程进入下一阶段。

屏障同步是一种简单而常用的协调并行活动的方法。在现实生活中，我们经常用屏障同步来协调多人的并行活动。例如，假设四个朋友开一辆车去购物中心。他们可以各自去不同的商店购买自己的衣服。这是一种并行活动，比他们一直作为一个群体按顺序逛所有感兴趣的商店要高效得多。然而，在他们离开购物中心之前需要一次屏障同步。他们必须等到四个朋友全部回到车上才能离开。比其他人先完成的人必须等待那些完成较晚的人。如果没有屏障同步，当车离开时，可能有一个或多个人被留在购物中心，这会严重损害他们的友谊！

图 4.3 说明了屏障同步的执行过程。线程块中共有 N 个线程，时间从左向右推进。有些线程很早就到达屏障同步语句，有些则晚得多。先到达屏障的线程将等待晚到的线程。当最后一个线程到达屏障时，所有线程都可以继续执行。有了屏障同步，“任何人都不会被落下”。

在 CUDA 中，如果存在__syncthreads()语句，则它必须被线程块中的所有线程执行。当__syncthreads()语句放在 if 语句中时，要么线程块中的所有线程都执行包含该__syncthreads()的分支，要么所有线程都不执行。对于 if-then-else 语句，如果每个分支都有一个__syncthreads()语句，则要么线程块中的所有线程都执行 then 分支，要么所有线程都执行 else 分支。这两处__syncthreads()是两个不同的屏障同步点。例如，在图 4.4 中，从第 04 行开始的 if 语句里使用了两处__syncthreads()。所有 threadIdx.x 值为偶数的线程执行 then 分支，其余线程执行 else 分支。第 06 行和第 10 行的__syncthreads()调用定义了两个不同的屏障。由于不能保证线程块中的所有线程都会执行其中任意一个屏障，该代码违反了使用__syncthreads()的规则，将导致未定义的执行行为。一般来说，不正确使用屏障同步可能导致结果错误，或导致线程彼此永远等待，这种情况称为死锁。避免此类不当使用屏障同步的责任在程序员身上。

屏障同步对线程块内的线程施加了执行约束。这些线程应在时间上彼此接近地执行，以避免过长的等待时间。更重要的是，系统需要确保参与屏障同步的所有线程都能获得所需的资源，从而最终到达屏障。否则，一个永远到不了屏障同步点的线程可能导致死锁。CUDA 运行时系统通过把一个线程块中所有线程作为一个整体来分配执行资源，从而满足这一约束，正如我们在第 4.2 节中看到的。线程块中的所有线程不仅必须被分配到同一个 SM，而且必须被同时分配到该 SM。也就是说，只有当运行时系统为线程块中所有线程完成执行所需的全部资源都准备就绪后，线程块才能开始执行。这保证了线程块中所有线程在时间上的接近性，并防止屏障同步期间出现过长甚至无限期的等待。

这引出了 CUDA 屏障同步设计中的一个重要权衡。通过不允许不同线程块中的线程彼此进行屏障同步，CUDA 运行时系统可以按任意相对顺序执行线程块，因为任何一个线程块都不需要等待其他线程块。这种灵活性使得实现具有可扩展性，如图 4.5 所示。图中时间自上而下推进。在只有少量执行资源的低成本系统中，可以同时执行的线程块数量较少，如图 4.5 左侧所示的一次执行两个线程块；在拥有更多执行资源的高端实现中，可以同时执行许多线程块，如图 4.5 右侧所示的一次执行四个线程块。如今高端 GPU 可以同时执行数百个线程块。

能够以多种不同的速度执行同一应用程序代码，使得可以根据不同市场细分对成本、功耗和性能的要求，制造出多种不同的实现。例如，移动处理器可以缓慢地执行应用程序，但功耗极低；台式机处理器则可以以更高的速度执行同一应用程序，同时消耗更多功耗。两者执行的是同一应用程序，代码无需任何改动。在不同的、执行资源数量各异的硬件上执行同一应用程序代码的能力称为透明可扩展性，它减轻了应用程序开发者的负担，并提高了应用程序的可用性。

4.4 线程束与 SIMD 硬件

我们已经看到，线程块之间可以按任意顺序执行，这使程序在不同设备上具有透明可扩展性。不过，关于每个线程块内线程的执行时序，我们此前并未多谈。从概念上讲，应该假定线程块内的线程可以按任意顺序相互执行。对于分阶段的算法，只要我们希望确保所有线程都完成了前一个执行阶段后，才让其中任何一个线程开始下一阶段，就应该使用屏障同步。执行核函数的正确性不应依赖于“某些线程在未使用屏障同步的情况下会彼此同步执行”这样的假设。

CUDA GPU 中的线程调度是一个硬件实现概念，因此必须在具体硬件实现的背景下讨论。迄今为止的大多数实现中，线程块一旦被分配到 SM，就会被进一步划分为由 32 个线程组成的单元，称为线程束（warp）。线程束的大小由具体实现决定，在未来的 GPU 代次中可能发生变化。了解线程束有助于理解和优化 CUDA 应用在特定代次 CUDA 设备上的性能。

线程束是 SM 中线程调度的单位。图 4.6 展示了某种实现中线程块划分成线程束的情况。在这个例子中有三个线程块——Block 1、Block 2 和 Block 3——它们都被分配到一个 SM。为了调度的目的，这三个线程块中的每一个又被进一步划分成线程束。每个线程束由 32 个 threadIdx 值连续的线程组成：线程 0 至 31 构成第一个线程束，线程 32 至 63 构成第二个线程束，依此类推。对于给定的线程块大小和分配给每个 SM 的线程块数量，我们可以计算出驻留在 SM 中的线程束数量。在这个例子中，如果每个线程块有 256 个线程，我们可以确定每个线程块有 256/32 即 8 个线程束。SM 中有三个线程块，因此 SM 中共有 8×3 = 24 个线程束。

线程块基于线程索引划分成线程束。如果线程块组织成一维数组，即只使用 threadIdx.x，则划分非常直接。线程束内的 threadIdx.x 值是连续递增的。对于大小为 32 的线程束，线程束 0 从线程 0 开始到线程 31 结束，线程束 1 从线程 32 开始到线程 63 结束，依此类推。一般地，线程束 n 从线程 32×n 开始，到线程 32×(n+1)−1 结束。对于大小不是 32 的倍数的线程块，最后一个线程束将用非活跃线程填充，以占满 32 个线程位置。例如，如果线程块有 48 个线程，它将被划分为两个线程束，第二个线程束将用 16 个非活跃线程填充。

对于由多维线程组成的线程块，在划分成线程束之前，这些维度会被投影成线性化的行主序布局。该线性布局的确定方式是：把 y 和 z 坐标较大的行放在坐标较小的行之后。也就是说，如果线程块由二维线程组成，那么就要把所有 threadIdx.y 为 1 的线程放在 threadIdx.y 为 0 的线程之后，threadIdx.y 为 2 的线程放在 threadIdx.y 为 1 的线程之后，依此类推。threadIdx.y 值相同的线程按照 threadIdx.x 递增的顺序放置在连续的位置上。

图 4.7 展示了把二维线程块中的线程放入线性布局的示例。上半部分展示了线程块的二维视图。读者应当能看出它与二维数组行主序布局的相似性。每个线程表示为 Ty,x，其中 x 是 threadIdx.x，y 是 threadIdx.y。图 4.7 的下半部分展示了线程块的线性化视图。前四个线程是 threadIdx.y 值为 0 的线程，它们按 threadIdx.x 值递增的顺序排列。接下来四个线程是 threadIdx.y 值为 1 的线程，同样按 threadIdx.x 值递增的顺序排列。在这个例子中，全部 16 个线程组成半个线程束。该线程束将再填充 16 个线程，凑成一个 32 线程的线程束。设想一个 8×8 线程的二维线程块，这 64 个线程将组成两个线程束。第一个线程束从 T0,0 开始，到 T3,7 结束；第二个线程束从 T4,0 开始，到 T7,7 结束。读者不妨自己动手把这个图画出来，作为练习。

对于三维线程块，我们首先把 threadIdx.z 值为 0 的所有线程按线性顺序排列。这些线程被视为一个二维线程块，如图 4.7 所示。然后，把 threadIdx.z 值为 1 的所有线程按线性顺序排列，依此类推。例如，对于一个三维的 2×8×4 线程块（x 维有 4 个、y 维有 8 个、z 维有 2 个），这 64 个线程将被划分为两个线程束，第一个线程束包含从 T0,0,0 到 T0,7,3，第二个线程束包含从 T1,0,0 到 T1,7,3。

SM 的设计目标是按照单指令多数据（SIMD）模型执行线程束中的所有线程。也就是说，在任何时刻，处理器为线程束中的所有线程取出并执行一条指令（参见“线程束与 SIMD 硬件”补充栏）。图 4.8 展示了 SM 中的核心如何分组为处理块：每 8 个核心组成一个处理块，共享一个取指/分发单元。举一个真实的例子，Ampere A100 的 SM 有 64 个核心，被组织成 4 个处理块，每个处理块 16 个核心。同一线程束中的线程被分配到同一个处理块，该处理块为线程束取出指令，并同时为线程束中的所有线程执行该指令。这些线程把同一条指令应用于数据的不同部分。由于 SIMD 硬件实际上限制了线程束中的所有线程在任何时刻都执行同一条指令，因此线程束的执行行为常被称为“单指令多线程”。

SIMD 的优势在于，控制硬件的成本（例如取指/分发单元）可以在许多执行单元之间分摊。这种设计选择使得可以用较小比例的硬件来承担控制功能，而用较大比例的硬件来提高算术吞吐量。我们预计在可预见的将来，线程束划分仍将是一种流行的实现技术。不过，线程束的大小可能因实现而异。到目前为止，所有 CUDA 设备都使用了类似的线程束配置，即每个线程束由 32 个线程组成。

线程束与 SIMD 硬件

在他 1945 年的开创性报告中，约翰·冯·诺依曼描述了一种构建电子计算机的模型，该模型基于先驱 EDVAC 计算机的设计。这一模型如今通常被称为“冯·诺依曼模型”，它一直是几乎所有现代计算机的基础蓝图。

下面的图展示了冯·诺依曼模型。计算机具有 I/O（输入/输出），既可以向系统提供程序和数据，也可以从系统产生程序和数据的输出。要执行程序，计算机首先把程序和它的数据输入到内存（Memory）。

程序由一组指令组成。控制单元维护着一个程序计数器（PC），其中保存着下一条待执行指令的内存地址。在每个“指令周期”中，控制单元使用 PC 把一条指令取入指令寄存器（IR）。随后对指令的各个位进行检查，以确定计算机各个组件要采取的动作。这就是该模型也被称为“存储程序”模型的原因，这意味着用户可以通过把不同的程序存入计算机的内存来改变计算机的行为。

以线程束为单位执行线程的动机，可以用下面这个为反映 GPU 设计而改造的冯·诺依曼模型来说明。该处理器与图 4.8 中的处理块相对应，只有一个负责取指和分发指令的控制单元。相同的控制信号（即从控制单元指向图 4.8 中各处理单元的箭头）作用于多个处理单元，每个处理单元对应 SM 中的一个核心，并执行线程束中的一个线程。

由于所有处理单元都由控制单元指令寄存器（IR）中的同一条指令控制，它们之间的执行差异源于寄存器文件中数据操作数值的不同。这在处理器设计中被称为单指令多数据（SIMD）。例如，虽然所有处理单元（核心）都由同一条指令（如 add r1, r2, r3）控制，但在不同的处理单元中 r2 和 r3 的内容是不同的。

现代处理器中的控制单元相当复杂，包括用于取指令的精密逻辑和访问指令缓存的端口。让多个处理单元共享一个控制单元，可以显著降低硬件制造成本和功耗。

4.5 控制发散

当线程束内的所有线程在处理各自的数据时遵循同一条执行路径（更正式的说法是控制流）时，SIMD 执行效果良好。例如，对于 if-else 结构，当线程束中的所有线程要么都执行 if 路径、要么都执行 else 路径时，执行效果良好。然而，当线程束内的线程走不同的控制流路径时，SIMD 硬件将对这些路径进行多趟执行，每条路径一趟。例如，对于 if-else 结构，如果线程束中一些线程走 if 路径，而另一些线程走 else 路径，硬件将执行两趟：一趟执行走 if 路径的线程，另一趟执行走 else 路径的线程。在每一趟中，走另一条路径的线程不被允许生效。

当同一线程束中的线程走不同的执行路径时，我们说这些线程表现出控制发散，即它们的执行发生了发散。针对发散线程束执行的多趟方案，扩展了 SIMD 硬件实现 CUDA 线程完整语义的能力。硬件虽然为线程束中的所有线程执行同一条指令，但它有选择地让这些线程只在与其所走路径对应的那一趟中生效，从而使每个线程看起来都走了自己的控制流路径。这在利用 SIMD 硬件低成本优势的同时，保留了线程的独立性。不过，发散的成本在于：硬件需要执行额外的趟数，以便让线程束中的不同线程做出各自的决策，此外每一趟中非活跃线程还会消耗执行资源。

图 4.9 展示了线程束如何执行一个发散 if-else 语句的示例。在这个例子中，当由线程 0–31 组成的线程束到达 if-else 语句时，线程 0–23 走 then 路径，而线程 24–31 走 else 路径。在这种情况下，线程束将对代码执行一趟：线程 0–23 执行 A，线程 24–31 处于非活动状态。线程束还将对代码执行另一趟：线程 24–31 执行 B，线程 0–23 处于非活动状态。随后线程束中的线程重新汇聚，执行 C。在 Pascal 架构及更早的架构中，这些趟是顺序执行的，即一趟执行完毕后，再执行另一趟。从 Volta 架构开始，各趟可以并发执行，即一趟的执行可以与另一趟的执行交错进行。这一特性称为独立线程调度。感兴趣的读者可参阅关于 Volta V100 架构的白皮书（NVIDIA，2017）了解详情。

发散也可能出现在其他控制流结构中。图 4.10 展示了线程束如何执行一个发散 for 循环的示例。在这个例子中，每个线程执行的循环迭代次数不同，介于四次到八次之间。在前四次迭代中，所有线程都处于活动状态并执行 A。在其余的迭代中，一些线程执行 A，而另一些线程由于已完成各自的迭代而处于非活动状态。

通过检查控制结构的判断条件，可以确定它是否会导致线程发散。如果判断条件基于 threadIdx 值，则该控制语句可能导致线程发散。例如，语句 if(threadIdx.x > 2) {…}会使线程块第一个线程束中的线程走两条发散的执行路径。线程 0、1 和 2 走的路径与线程 3、4、5 等不同。类似地，如果循环的条件基于线程索引值，循环也可能导致线程发散。

使用带线程控制发散的控制结构的一个常见原因，是在把线程映射到数据时处理边界条件。这通常是因为线程总数需要是线程块大小的整数倍，而数据的大小可以是任意数。从第 2 章“异构数据并行计算”中的向量加法核函数开始，我们就在 addVecKernel 里使用了 if(i<n)语句。这是因为并非所有向量长度都能表示成线程块大小的整数倍。例如，假设向量长度为 1003，我们选取 64 作为线程块大小。那么需要启动 16 个线程块来处理全部 1003 个向量元素。然而，16 个线程块共有 1024 个线程。我们需要禁用线程块 15 中最后 21 个线程，让它们不执行原程序所不期望或不允许的工作。请记住，这 16 个线程块被划分为 32 个线程束。只有最后一个线程束（即最后一个线程块中的第二个线程束）会出现控制发散。

请注意，控制发散对性能的影响会随着所处理向量规模的增大而减小。对于长度为 100 的向量，四个线程束中会有一个出现控制发散，这可能对性能产生显著影响。对于长度为 1000 的向量，32 个线程束中只有一个会出现控制发散。也就是说，控制发散只会影响大约 3% 的执行时间。即使它使该线程束的执行时间翻倍，对总执行时间的净影响也只有大约 3%。显然，如果向量长度为 10,000 或更长，313 个线程束中只有一个会出现控制发散，控制发散的影响将远小于 1%！

对于二维数据，例如第 3 章“多维网格与数据”中的彩色到灰度转换示例，也会使用 if 语句来处理在数据边缘工作的线程的边界条件。在图 3.2 中，为了处理 62×76 的图像，我们使用了 20 = 4×5 个二维线程块，每个线程块由 16×16 个线程组成。每个线程块将被划分为 8 个线程束，每个线程束由线程块的两行组成。总共涉及 160 个线程束（每个线程块 8 个线程束）。要分析控制发散的影响，请参阅图 3.5。区域 1 中 12 个线程块里的线程束都不会出现控制发散。区域 1 有 12×8 = 96 个线程束。对于区域 2，全部 24 个线程束都会出现控制发散。对于区域 3，所有底部线程束都映射到完全位于图像之外的数据，因此它们都不会通过 if 条件。读者可以自行验证：如果图片在垂直方向上有奇数个像素，这些线程束就会出现控制发散。在区域 4，前 7 个线程束会出现控制发散，但最后一个线程束不会。总而言之，160 个线程束中有 31 个会出现控制发散。

同样地，控制发散对性能的影响会随着水平方向像素数量的增加而减小。例如，如果用 16×16 的线程块处理 200×150 的图片，线程块总数为 130 = 13×10，即 1040 个线程束。区域 1 至 4 中的线程束数量分别为 864（12×9×8）、72（9×8）、96（12×8）和 8（1×8）。其中只有 80 个线程束会出现控制发散。因此，控制发散对性能的影响将小于 8%。显然，如果处理一幅水平方向超过 1000 像素的真实图片，控制发散对性能的影响将小于 2%。

控制发散的一个重要含义是：不能假定线程束中的所有线程具有相同的执行时序。因此，如果必须等线程束中所有线程都完成执行的某个阶段后，才能让其中任何一个线程继续推进，就必须使用诸如__syncwarp()之类的屏障同步机制来保证正确性。

4.6 线程束调度与延迟容忍

当线程被分配到 SM 时，分配给一个 SM 的线程数量通常多于该 SM 的核心数。也就是说，每个 SM 只拥有足够的执行单元，在任何时刻只能执行分配给它的全部线程中的一部分。在早期的 GPU 设计中，每个 SM 在任一时刻只能为单个线程束执行一条指令。在较新的设计中，每个 SM 在任一时刻可以为少数几个线程束执行指令。无论哪种情况，硬件都只能为 SM 中全部线程束中的一部分执行指令。一个合理的问题是：既然 SM 在任何时刻只能执行其中一部分线程束，为什么还要分配这么多线程束给它？答案是：这正是 GPU 容忍诸如全局内存访问之类的长延迟操作的方式。

当某个线程束要执行的指令需要等待先前发起的某个长延迟操作的结果时，该线程束不会被选中执行。相反，会挑选另一个已不再等待先前指令结果的驻留线程束来执行。如果有多个线程束都准备好了，则使用一种优先级机制从中选一个执行。这种用其他线程的工作来填充部分线程操作延迟时间的机制，通常被称为“延迟容忍”或“延迟隐藏”（参见“延迟容忍”补充栏）。

延迟容忍

延迟容忍在许多日常情境中都是需要的。例如，在邮局里，每个想寄包裹的人都应该在去服务台之前填好所有表格和标签。然而，正如我们都经历过的，有些人会等着服务台工作人员告诉他们该填哪张表格、如何填写。

当服务台前排着长队时，最大限度地提高服务人员的工作效率就很重要。让一个人站在工作人员面前填表而其他所有人都等着，并不是一个好办法。这个人填表期间，工作人员应该去帮助排在后面的其他顾客。这些顾客“随时可以办理”，不应被那位需要更多时间填表的顾客挡住。

这就是为什么一位好的工作人员会礼貌地请第一位顾客站到一旁填表，同时继续为其他顾客服务。在大多数情况下，第一位顾客不需要排到队尾，只要他或她填完表、工作人员也服务完当前顾客，就会立即得到服务。

我们可以把这些邮局顾客想象成线程束，把工作人员想象成硬件执行单元。需要填表的顾客对应一个其后续执行依赖于某个长延迟操作的线程束。

请注意，线程束调度也用于容忍其他类型的操作延迟，例如流水线浮点算术和分支指令。只要有足够多的线程束在场，硬件在任意时刻都可能找到某个可执行的线程束，从而在部分线程束的指令等待这些长延迟操作结果的同时，充分利用执行硬件。对已准备好执行的线程束的挑选，不会在执行时间线上引入任何空闲或浪费的时间，这被称为零开销线程调度（参见“线程、上下文切换与零开销调度”补充栏）。借助线程束调度，线程束指令的长时间等待被其他线程束指令的执行“隐藏”了起来。这种容忍长操作延迟的能力，是 GPU 不像 CPU 那样把几乎同样多的芯片面积用于缓存和分支预测机制的主要原因。因此，GPU 可以把更多的芯片面积用于浮点执行和内存访问通道资源。

线程、上下文切换与零开销调度

基于冯·诺依曼模型，我们可以更深入地理解线程是如何实现的。在现代计算机中，一个线程就是一个程序以及该程序在冯·诺依曼处理器上执行的状态。回想一下，线程由程序的代码、代码中正在执行的指令，以及其变量和数据结构的值组成。

在基于冯·诺依曼模型的计算机中，程序代码存储在内存里。PC 跟踪程序中正在执行的指令的地址。IR 保存正在执行的指令。寄存器和内存保存变量和数据结构的值。

现代处理器被设计成支持上下文切换，即多个线程可以轮流取得进展，分时共享一个处理器。通过仔细地保存和恢复 PC 值以及寄存器和内存的内容，我们可以挂起一个线程的执行，并在稍后正确地恢复该线程的执行。然而，在这些处理器中进行上下文切换时，保存和恢复寄存器内容会带来显著的开销，表现为额外增加的执行时间。

零开销调度指的是 GPU 的这种能力：让需要等待长延迟指令结果的线程束进入休眠，并激活一个随时可以执行的线程束，而不会在处理单元中引入任何额外的空闲周期。传统 CPU 之所以会产生这类空闲周期，是因为把执行从一个线程切换到另一个线程，需要把执行状态（例如离开线程的寄存器内容）保存到内存，并从内存载入进入线程的执行状态。GPU 的 SM 通过把分配给它的所有线程束的执行状态保存在硬件寄存器中来实现零开销调度，因此在从一个线程束切换到另一个线程束时，无需保存和恢复状态。

要使延迟容忍行之有效，理想的做法是让分配给 SM 的线程数量远多于其执行资源所能同时支持的数量，从而在任意时刻都能最大限度地找到可执行的线程束。例如，Ampere A100 GPU 的 SM 有 64 个核心，但可以同时分配给它多达 2048 个线程。因此，分配给 SM 的线程数量可以是其核心在任意一个时钟周期内所能支持数量的 32 倍之多。这种线程对 SM 的过度订阅对延迟容忍至关重要。它增加了在当前执行的线程束遇到长延迟操作时找到另一个线程束来执行的机会。

4.7 资源划分与占用率

我们已经看到，为了容忍长延迟操作，给 SM 分配尽可能多的线程束是可取的。然而，把 SM 所支持的最大线程束数量分配给 SM 并不总是可行的。分配给 SM 的线程束数量与其支持的最大线程束数量之比称为占用率。要理解是什么因素可能阻止 SM 达到最大占用率，首先理解 SM 的资源是如何划分的很重要。

SM 中的执行资源包括寄存器、共享内存（在第 5 章“内存体系结构与数据局部性”中讨论）、线程块槽位和线程槽位。这些资源在线程之间动态划分，以支持线程的执行。例如，Ampere A100 GPU 每个 SM 最多支持 32 个线程块、每个 SM 最多 64 个线程束（2048 个线程）、每个线程块最多 1024 个线程。如果用大小为 1024 个线程的线程块（所允许的最大值）启动网格，则每个 SM 中的 2048 个线程槽位会被划分并分配给 2 个线程块。在这种情况下，每个 SM 最多可容纳 2 个线程块。类似地，如果用大小为 512、256、128 或 64 个线程的线程块启动网格，2048 个线程槽位将分别被划分并分配给 4、8、16 或 32 个线程块。

这种在线程块之间动态划分线程槽位的能力使 SM 具有很高的灵活性。它们既可以执行许多线程数很少的线程块，也可以执行少量线程数很多的线程块。这种动态划分可以与固定划分方法形成对比：在固定划分中，每个线程块无论实际需要多少资源，都获得固定的资源量。当线程块需要的线程数少于固定划分所支持的数量时，固定划分会导致线程槽位浪费；而当线程块需要的线程槽位多于固定划分提供的数量时，固定划分又无法支持。

资源的动态划分可能导致各种资源限制之间产生微妙的相互作用，从而造成资源利用不足。这种相互作用可能发生在线程块槽位与线程槽位之间。在 Ampere A100 的例子中，我们看到线程块大小可以从 1024 变化到 64，分别使每个 SM 有 2–32 个线程块。在所有上述情况下，分配给 SM 的线程总数都是 2048，这使占用率达到最大。然而，考虑每个线程块有 32 个线程的情况。此时 2048 个线程槽位需要被划分并分配给 64 个线程块。但是，Volta 的 SM 一次最多只能支持 32 个线程块槽位。这意味着只有 1024 个线程槽位会被利用，也就是 32 个线程块、每块 32 个线程。此时的占用率为 (1024 个已分配线程)/(2048 个最大线程) = 50%。因此，要充分利用线程槽位并达到最大占用率，每个线程块至少需要有 64 个线程。

另一种可能对占用率产生负面影响的情况是：每个线程块的最大线程数不能被线程块大小整除。在 Ampere A100 的例子中，我们看到每个 SM 最多可以支持 2048 个线程。然而，如果选择 768 作为线程块大小，SM 将只能容纳 2 个线程块（1536 个线程），留下 512 个线程槽位未利用。在这种情况下，既达不到每个 SM 的最大线程数，也达不到每个 SM 的最大线程块数。此时的占用率为 (1536 个已分配线程)/(2048 个最大线程) = 75%。

前面的讨论没有考虑其他资源约束的影响，例如寄存器和共享内存。我们将在第 5 章“内存体系结构与数据局部性”中看到，在 CUDA 核函数中声明的自动变量会被放入寄存器。有些核函数可能使用很多自动变量，有些则用得很少。因此可以预期，有些核函数每个线程需要很多寄存器，有些则只需要很少。通过在 SM 中把寄存器动态划分给线程，SM 可以在每个线程所需寄存器很少时容纳许多线程块，而在每个线程所需寄存器较多时容纳较少的线程块。

不过，确实需要留意寄存器资源限制对占用率的潜在影响。例如，Ampere A100 GPU 每个 SM 最多允许 65,536 个寄存器。要以满占用率运行，每个 SM 需要为 2048 个线程提供足够的寄存器，这意味着每个线程使用的寄存器数不应超过 (65,536 个寄存器)/(2048 个线程) = 每个线程 32 个寄存器。例如，如果某个核函数每个线程使用 64 个寄存器，那么 65,536 个寄存器最多可以支持 1024 个线程。在这种情况下，无论线程块大小如何设置，该核函数都无法以满占用率运行，占用率至多为 50%。在某些情况下，编译器可能会执行寄存器溢出，以减少每个线程的寄存器需求，从而提高占用率水平。然而，这通常以增加线程从内存访问被溢出的寄存器值的执行时间为代价，并可能导致整个网格的总执行时间增加。关于共享内存资源的类似分析将在第 5 章“内存体系结构与数据局部性”中进行。

假设程序员实现了一个每个线程使用 31 个寄存器的核函数，并配置为每个线程块 512 个线程。此时，SM 将有 (2048 个线程)/(512 个线程/线程块) = 4 个线程块同时运行。这些线程总共使用 (2048 个线程)×(31 个寄存器/线程) = 63,488 个寄存器，低于 65,536 个寄存器的限制。现在假设程序员在核函数中又声明了两个自动变量，使每个线程使用的寄存器数增加到 33。此时 2048 个线程所需的寄存器数为 67,584 个，超过了寄存器上限。CUDA 运行时系统可能会通过只给每个 SM 分配 3 个线程块而不是 4 个来处理这种情况，从而把所需寄存器数减少到 50,688 个。但这会把 SM 上运行的线程数从 2048 减少到 1536；也就是说，仅仅多用了两个自动变量，程序占有的占用率就从 100% 下降到了 75%。这种现象有时被称为“性能悬崖”：资源使用量的微小增加，会导致并行度和性能的显著下降（Ryoo 等，2008）。

读者应当清楚，所有动态划分资源的约束之间会以复杂的方式相互作用。要精确确定每个 SM 中运行的线程数是困难的。读者可参阅 CUDA 占用率计算器（CUDA Occupancy Calculator，Web），它是一个可下载的电子表格，在给定核函数资源使用情况的情况下，计算出特定设备实现上每个 SM 实际运行的线程数。

4.8 查询设备属性

我们关于 SM 资源划分的讨论引出了一个重要问题：我们如何获知特定设备可用的资源量？当 CUDA 应用在某个系统上执行时，它如何获知设备中 SM 的数量，以及每个 SM 可以分配多少个线程块和线程？其他种类的资源也存在同样的问题，其中一些我们还没有讨论过。一般来说，许多现代应用被设计成在各种各样的硬件系统上运行。应用常常需要查询底层硬件可用的资源和能力，以便利用能力更强的系统，同时弥补能力较弱的系统（参见“资源与能力查询”补充栏）。

资源与能力查询

在日常生活中，我们经常查询某个环境中的资源和能力。例如，预订酒店时，我们可以查看酒店房间附带哪些设施。如果房间配有吹风机，我们就不必自带。大多数美国酒店房间都配有吹风机，而世界其他地区的许多酒店则没有。

一些亚洲和欧洲的酒店提供牙膏，甚至牙刷，而大多数美国酒店则不提供。许多美国酒店同时提供洗发水和护发素，而其他大洲的酒店往往只提供洗发水。

如果房间配有微波炉和冰箱，我们就可以把晚餐的剩菜带回去，第二天再吃。如果酒店有游泳池，我们可以带上泳衣，在商务会议之后游个泳。如果酒店没有游泳池但有健身房，我们可以带上跑鞋和运动服。一些亚洲高端酒店甚至提供运动服装！

这些酒店设施是酒店属性（即资源和能力）的一部分。经验丰富的旅行者会查看酒店网站上的属性介绍，选择最符合自己需求的酒店，并更高效、更有效地打包行李。

每个 CUDA 设备 SM 中的资源量被指定为设备计算能力的一部分。一般来说，计算能力级别越高，每个 SM 中可用的资源就越多。GPU 的计算能力往往随代际更迭而不断提高。Ampere A100 GPU 的计算能力为 8.0。

内置类型 cudaDeviceProp 是一个 C 结构体类型，其字段表示 CUDA 设备的属性。该类型的所有字段请读者参阅 CUDA C 编程指南。我们将讨论其中几个与执行资源分配到线程特别相关的字段。我们假定属性通过 devProp 变量返回，其字段由 cudaGetDeviceProperties 函数设置。如果读者选择用不同的变量名，那么显然需要在下面的讨论中用相应的变量名替换。

顾名思义，字段 devProp.maxThreadsPerBlock 给出被查询设备中每个线程块允许的最大线程数。有些设备每个线程块最多允许 1024 个线程，有些设备允许的更少。未来的设备甚至可能允许每个线程块超过 1024 个线程。因此，就应用而言，查询可用设备并确定哪些设备允许每个线程块有足够数量的线程，是一个好主意。

设备中 SM 的数量由 devProp.multiProcessorCount 给出。如果应用需要大量 SM 才能达到令人满意的性能，那么它一定要检查候选设备的这一属性。此外，设备的时钟频率在 devProp.clockRate 中。时钟频率与 SM 数量的组合，可以很好地指示该设备的最大硬件执行吞吐量。

主机代码可以在字段 devProp.maxThreadsDim[0]（x 维）、devProp.maxThreadsDim[1]（y 维）和 devProp.maxThreadsDim[2]（z 维）中找到线程块每个维度允许的最大线程数。这类信息的一个用法是：让自动调优系统在为底层硬件评估最佳线程块维度时，设置线程块维度的取值范围。类似地，它还可以在 devProp.maxGridSize[0]（x 维）、devProp.maxGridSize[1]（y 维）和 devProp.maxGridSize[2]（z 维）中找到网格每个维度允许的最大线程块数。这类信息的一个典型用途是判断网格是否能有足够的线程来处理整个数据集，还是需要某种迭代方法。

字段 devProp.regsPerBlock 给出每个 SM 中可用的寄存器数量。这个字段有助于判断核函数在特定设备上是能够达到最大占用率，还是会受其寄存器使用量的限制。注意，这个字段的名字略有误导性。对于大多数计算能力级别，线程块可以使用的最大寄存器数确实与 SM 中可用的寄存器总数相同。然而，对于某些计算能力级别，线程块可以使用的最大寄存器数小于 SM 上可用的寄存器总数。

我们还讨论过，线程束的大小取决于硬件。线程束的大小可以从 devProp.warpSize 字段获得。

cudaDeviceProp 类型中还有很多其他字段。随着我们逐步介绍这些字段所设计用来反映的概念和特性，我们将在全书中讨论它们。

4.9 小结

GPU 由 SM 组织而成，SM 又由多个共享控制逻辑和内存资源的核心处理块组成。当网格启动时，其线程块以任意顺序被分配到 SM，从而使 CUDA 应用具有透明可扩展性。透明可扩展性伴随着一个限制：不同线程块中的线程之间不能互相同步。

线程以线程块为单位被分配到 SM 执行。线程块一旦被分配到 SM，就会进一步被划分成线程束。线程束中的线程按照 SIMD 模型执行。如果同一线程束中的线程走不同的执行路径而发生发散，处理块会分趟执行这些路径，每个线程只在与其所走路径相对应的那一趟中处于活动状态。

SM 被分配的线程数量可能远多于它能够同时执行的线程数。在任何时刻，SM 只执行其驻留线程束中一小部分线程束的指令。这使得其他线程束可以等待长延迟操作，而不会拖慢数量庞大的处理单元的总体执行吞吐量。分配给 SM 的线程数与其所能支持的最大线程数之比称为占用率。SM 的占用率越高，它就越能更好地隐藏长延迟操作。

每个 CUDA 设备对每个 SM 中可用资源量的限制可能各不相同。例如，每个 CUDA 设备对每个 SM 所能容纳的线程块数、线程数、寄存器数以及其他资源量都有限制。对于每个核函数，这些资源限制中的一个或多个可能成为占用率的限制因素。CUDA C 为程序员提供了在运行时查询 GPU 中可用资源的能力。
