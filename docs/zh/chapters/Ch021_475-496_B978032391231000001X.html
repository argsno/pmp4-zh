Chapter 21

CUDA 动态并行

特别贡献：Juan Gómez-Luna

摘要

本章介绍 CUDA 动态并行，它是 CUDA 编程模型的一个扩展，允许 CUDA 核函数通过调用其他核函数来创建更多的线程网格。动态并行使得能够动态发现新工作的算法无需加重主机的负担或诉诸复杂的软件技术，即可准备并启动网格。本章以一个受益于动态并行的简单模式开始，然后使用两个高级示例——贝塞尔曲线计算和四叉树构建——来说明程序员在真实应用中使用动态并行时可能遇到的一些重要细节与微妙之处。最后，本章讨论了动态并行实际使用中的重要考量，包括内存数据可见性、待启动池配置、流以及嵌套深度。

关键词

动态工作发现；不规则工作分布；时空工作变化；网格启动；流；同步；递归核函数调用

CUDA 动态并行是 CUDA 编程模型的一个扩展，它允许核函数调用其他核函数，从而使在设备上执行的线程能够启动新的线程网格。在早期的 CUDA 版本中，网格只能从主机代码中启动。涉及递归、不规则循环结构、时空变化或其他不适合扁平且单层并行结构的算法，需要通过主机进行多次核函数调用来实现，这会增加主机的负担、主机与设备之间的通信量以及总执行时间。在某些情况下，程序员不得不借助循环串行化和其他笨拙的技术来满足这些算法需求，代价是软件可维护性下降。动态并行的支持使得能够动态发现新工作的算法可以准备并启动新网格，而无需加重主机的负担或影响软件可维护性。本章描述了使 CUDA 具备动态并行能力的扩展特性，包括对 CUDA 编程接口的修改与新增，以及利用这一新增能力的指南和最佳实践。

21.1 背景

许多真实世界的应用采用这样的算法：其工作在空间上存在差异，或者随时间动态变化的工作量。例如，图 21.1 展示了一个湍流模拟示例，其中所需的建模细节级别在空间和时间上都各不相同。随着燃烧流从左向右移动，活动范围和强度不断增加。建模模型右侧所需的细节级别远高于模型左侧。一方面，对模型左侧使用固定的细网格会带来无谓的过多工作量；另一方面，对模型右侧使用固定的粗网格又会牺牲过多的精度。理想情况下，应该对模型需要更多细节的部分使用细网格，对不需要那么多细节的部分使用粗网格。

到目前为止，我们一直假设所有核函数都是从主机代码调用的。线程网格所完成的工作量在调用核函数时就已经预先确定。由于核函数代码采用单程序、多数据的编程风格，要让不同的线程块使用不同的网格间距即使不是极其困难，也是非常繁琐的。因此，这种限制偏向于使用固定且均匀（规则）的网格系统。为了达到期望的精度，这种固定网格方法——如图 21.1 右上方所示——通常需要满足模型中最苛刻的部分，并在不需要那么多细节的部分维护多余的数据、执行多余的工作。

一种更可取的方法如图 21.1 右下方的动态网格所示。当模拟算法检测到模型某些区域中的模拟量快速变化时，它会在这些区域细化网格，以达到期望的精度水平。对于没有表现出这种剧烈活动的区域，则不需要进行这种细化。因此，算法可以动态地将更多的计算资源引导到模型那些能从额外工作中获益的区域。

图 21.2 从概念上比较了对于图 21.1 中的模拟模型，没有动态并行的系统与具有动态并行的系统在行为上的差异。没有动态并行时，主机线程必须启动所有网格。如果发现了新工作，例如在某个网格执行过程中需要细化模型的某个区域，则该网格必须终止、向主机汇报，并由主机启动新的网格。这如图 21.2A 所示：主机启动一个网格，在该网格终止后接收其信息，并为已完成网格发现的任何新工作启动后续网格。图中把后续网格描绘为一个接一个地启动；不过也可以应用更精细的优化，例如在不同的流中启动相互独立的网格，或将它们合并起来以便并行运行。

图 21.2B 表明，有了动态并行，发现新工作的线程可以直接启动网格来完成这些工作。在我们的示例中，当某个线程发现模型中的某个区域需要细化时，它可以启动一个新网格来对细化后的区域执行计算，而无需承担终止网格、向主机汇报并让主机启动新网格的开销。

21.2 动态并行概述

从程序员的角度来看，动态并行意味着他们可以在核函数内部编写一条调用另一个核函数的语句。在图 21.3 中，主函数（主机代码）启动了三个核函数：A、B 和 C。这些都是主机代码中的核函数调用，正如我们在本书中一直假设的那样。图 21.3 中的新内容是，其中一个核函数 B 调用了三个核函数 X、Y 和 Z。在不支持动态并行的早期 CUDA 系统中，这是非法的。

从核函数内部调用核函数的语法，与从主机代码调用核函数的语法相同：

  • • Dg 的类型为 dim3，指定网格的维度和大小。
  • • Db 的类型为 dim3，指定每个线程块的维度和大小。
  • • Ns 的类型为 size_t，指定本次调用中每个线程块动态分配的共享内存字节数，这部分内存是在静态分配的共享内存之外的。Ns 是可选参数，默认值为 0。
  • • S 的类型为 cudaStream_t，指定与此调用关联的流。该流必须是在发起调用的同一个线程块中分配的。S 是可选参数，默认值为 0。流已在第 20 章（编程异构计算集群）中讨论过。

为了演示如何使用动态并行，我们提供了不使用和使用动态并行的核函数简单示例。这些示例基于一个假设的并行算法，它并不计算有用的结果，但提供了一种在许多应用中反复出现的、概念上简单的计算模式。它有助于说明两种方法之间的差异，以及在算法中每个线程完成的工作量可以动态变化时，如何使用动态并行提取更多的并行性，同时减少控制流发散。

图 21.4 展示了一个不使用动态并行编写的简单示例核函数。在这个示例中，核函数的每个线程执行一些计算（第 05 行），然后遍历它负责的数据元素列表（第 07 行），并为每个数据元素执行另一次计算（第 08 行）。

这种计算模式在许多应用中频繁出现。例如，在图搜索中，每个线程可以访问一个顶点，然后遍历相邻顶点列表。读者会发现，这种核函数结构与图 15.14 中面向顶点的 BFS 核函数相似。再举一个例子，在稀疏矩阵计算中，每个线程可以先确定一行非零元素的起始位置，然后遍历这些非零值。在诸如本章开头示例那样的模拟中，每个线程可以先处理一个粗网格单元，然后在需要细化网格时遍历更细的网格单元。

以图 21.4 所示风格编写应用存在两个主要问题。首先，如果循环中的工作（第 07–09 行）可以并行执行并获得收益，那么我们就错失了从应用中提取更多并行性的机会。其次，如果同一线程束内各线程的循环迭代次数差异很大，那么由此产生的控制发散会降低程序的性能。

图 21.5 展示了同一程序使用动态并行的版本。在这个版本中，原来的核函数被分成两个：父核函数和子核函数。父核函数的开头与原核函数相同，由被称为父网格的线程网格执行。父核函数不再循环，而是调用子核函数来继续工作（第 07–08 行）。子核函数由被称为子网格的线程网格执行，这些网格完成原先在循环体内完成的工作（第 18 行，图 21.5；原循环体为第 07–09 行，图 21.4）。

以这种方式编写程序可以解决前面提到的原代码的两个问题。首先，循环迭代现在由子核函数的线程并行执行，而不是由原核函数的线程串行执行。因此，我们从程序中提取了更多的并行性。其次，每个线程现在只执行一次循环迭代，这带来了更好的负载均衡，并消除了控制发散。虽然程序员也可以通过不同的方式重写核函数来实现这两个目标，例如使用面向边的广度优先实现，但对某些应用来说，这种变换可能笨拙、复杂且容易出错。动态并行提供了一种表达此类计算模式的简便方式。

21.3 示例：贝塞尔曲线

我们现在展示一个更有趣、更有用的示例：样条曲线的自适应细分。这个示例说明的是子网格启动数量随工作负载而变化的情况。示例的内容是计算贝塞尔曲线（Bezier Curves）。贝塞尔曲线在计算机图形学中经常用于绘制平滑、直观的曲线，这些曲线由一组控制点定义，控制点通常由用户指定。

从数学上讲，贝塞尔曲线由一组控制点 P0 至 Pn 定义，其中 n 称为控制点的阶（n=1 对应线性，2 对应二次，3 对应三次，以此类推）。曲线的第一个和最后一个控制点始终是曲线的端点，但中间的控制点（如果有）通常不在曲线上。

线性贝塞尔曲线

给定两个控制点 P0 和 P1，线性贝塞尔曲线就是连接这两个点的直线。曲线上点的坐标由以下线性插值公式给出：

Bt=P0+tP1−P0=1−tP0+tP1,t∈[0,1]

二次贝塞尔曲线

二次贝塞尔曲线由三个控制点 P0、P1 和 P2 定义。二次曲线上的点定义为从 P0 到 P1 以及从 P1 到 P2 的线性贝塞尔曲线上对应点的线性插值。曲线上点坐标的计算用以下公式表示：

Bt=1−t1−tP0+tP1+t[1−tP0+tP2],t∈[0,1],

它可以化简为以下公式：

Bt=(1−t)2P0+21−ttP1+t2P2,t∈0,1.

贝塞尔曲线计算（不使用动态并行）

图 21.6 展示了计算贝塞尔曲线上点坐标的 CUDA C 程序的一部分。从第 13 行开始的 computeBezierLines 核函数设计为使用一个线程块来计算一组三个控制点（按二次贝塞尔公式）的曲线点。每个线程块首先计算由这三个控制点确定的曲线的曲率度量。直观地说，曲率越大，绘制这三个控制点的平滑二次贝塞尔曲线所需的点就越多。这决定了每个线程块要完成的工作量。这反映在第 20 行和第 21 行：当前线程块要计算的点总数与曲率值成正比。

在第 24 行的 for 循环中，所有线程在每次迭代中计算一组连续的贝塞尔曲线点。循环体内的具体计算基于我们前面给出的公式。关键在于，一个线程块中的线程执行的迭代次数可能与另一个线程块中的线程执行的迭代次数大不相同。根据调度策略的不同，这种每个线程块工作量上的差异可能导致流式多处理器（SM）利用率下降，从而降低性能。

贝塞尔曲线计算（使用动态并行）

图 21.7 展示了使用动态并行的贝塞尔曲线计算代码。它把图 21.6 中的 computeBezierLines 核函数拆分成两个核函数。第一部分 computeBezierLines_parent 确定每个控制点需要完成的工作量，第二部分 computeBezierLines_child 执行计算。

在新的组织方式下，computeBezierLines_parent 核函数为每组控制点完成的工作量比原来的 computeBezierLines 核函数小得多。因此，在 computeBezierLines_parent 中，我们用单个线程来完成这项工作，而不是像 computeBezierLines 那样使用一个线程块。在第 58 行，我们只需要为每组控制点启动一个线程。这体现在核函数启动配置中：用 BLOCK_DIM 除 N_LINES 得到线程块的数量。

computeBezierLines_parent 核函数与 computeBezierLines 核函数之间有两个关键差异。首先，用于访问控制点的索引是基于线程生成的（图 21.7 中的第 08 行），而不是基于线程块生成的（图 21.6 中的第 14 行）。这是因为如本章前面所述，每个控制点的工作由单个线程而不是线程块完成。其次，用于存储计算出的贝塞尔曲线点的内存在图 21.7 的第 15 行被动态确定并分配。这样，代码就可以为每组控制点分配恰好足够的内存，并将其放入 bLines 变量。请注意，在图 21.6 中，每个 BezierLine 元素都按最大可能的点数声明（第 09 行）。而在图 21.7 中，声明只有一个指向动态分配存储空间的指针。允许核函数调用 cudaMalloc() 函数，可以在控制点曲率变化显著的情况下大幅减少内存使用。

当 computeBezierLines_parent 核函数中的某个线程确定了它的控制点组所需的工作量后，它会调用 computeBezierLines_child 核函数，并启动一个子网格来完成这些工作（图 21.7 中的第 19 行）。在我们的示例中，父网格中的每个线程都为分配给它的控制点组创建一个新网格。这样一来，每个线程块完成的工作量就是均衡的。每个子网格完成的工作量各不相同。

动态并行的核函数调用与主机发起的核函数调用具有相同的异步语义。也就是说，一旦子核函数被调用，调用它的父线程就可以继续执行后续代码，而无需等待子网格完成。如果父线程希望等待其子网格完成，它必须执行显式同步，与主机线程的做法类似。如果不进行显式同步，线程可以结束执行，但在结束时存在一次隐式同步。隐式同步确保父网格终止前所有子网格都已终止。关于父子网格同步语义的更多细节，请读者参阅 CUDA C++ 编程指南（NVIDIA Corporation, 2021）。

在 computeBezierLines_parent 终止后，核函数内部使用 cudaMalloc 分配的内存仍需要释放。为此，实现了一个额外的核函数 freeVertexMem（第 42–47 行），由主机调用。该核函数并行释放 bLines_d 数据结构中为顶点分配的所有存储空间（第 61 行）。这个核函数是必要的，因为设备核函数在设备上分配的顶点存储空间必须由设备核函数来释放。关于在设备上使用 cudaMalloc 和 cudaFree 的更多细节，请读者参阅 CUDA C++ 编程指南（NVIDIA Corporation, 2021）。

21.4 递归示例：四叉树

动态并行还允许程序员实现递归算法。在本节中，我们用四叉树（quadtree）（Finkel and Bentley, 1974）来说明如何利用动态并行实现递归。四叉树通过递归地将二维空间细分为四个大小相等的象限来划分该空间。每个象限被认为是四叉树的一个节点，其中包含一定数量的点。如果某个象限中的点数大于某个固定的最小值，该象限将被递归细分为四个象限，即四个子节点。

图 21.8 说明了使用动态并行构建四叉树的过程。在这个实现中，一个节点（象限）分配给一个线程块。最初（depth=0），一个线程块（线程块 0）被分配整个二维空间（四叉树的根节点），其中包含所有点。它把空间划分为四个象限，并为每个象限启动一个线程块（depth=1）。这些子线程块（线程块 00 至 03）如果包含的点数超过固定的最小值，将再次细分它们各自的象限。在本例中，我们假设最小值为 2，因此线程块 00 和 02 不启动子线程块，而线程块 01 和 03 各自启动一个含四个线程块的网格。

如图 21.8 右侧的流程图所示，线程块首先检查其象限中的点数是否大于进一步细分所需的最小值，以及是否尚未达到最大深度。如果两个条件中有任何一个不满足，该象限的工作就完成了，线程块返回。否则，线程块计算包围其象限的边界框的中心。该中心位于四个新象限的中间。随后统计每个新象限中的点数。使用一个四元素的扫描操作来计算各点存储位置的偏移量。然后对点进行重排，使同一象限中的点归在一起，放入点存储区中各自的分段。最后，线程块启动一个包含四个线程块的子网格，每个线程块对应四个新象限中的一个。

图 21.9 接着图 21.8 中的小示例，详细说明了在每个深度层级如何对点进行重排。在本例中，我们假设每个象限必须包含两个以上的点才能进一步划分。算法使用两个缓冲区来存储点并对其重排。算法结束时，点应当位于缓冲区 0 中。因此，如果在满足终止条件时点还在缓冲区 1 中，则在退出前可能有必要交换缓冲区内容。

在主机代码的初始核函数调用中（depth=0），线程块 0 被分配缓冲区 0 中的所有点，如图 21.9A 所示。线程块 0 进一步把象限划分为四个子象限，把同一子象限中的所有点归在一起，并按象限把点存入缓冲区 1，如图 21.9B 所示。它的四个子线程块（线程块 00 至 03）被分别分配四个新象限，如图 21.9B 中标记的范围所示。线程块 00 和 02 不会启动子线程块，因为它们各自被分配象限中的点数只有 2。线程块 01 和 03 对它们的点进行重排以归组同一象限中的点，并各自启动四个子线程块，如图 21.9C 所示。线程块 010、011、012、013、030、031 和 032 不启动子线程块（它们有 2 个或更少的点），也不需要交换点（它们已经在缓冲区 0 中）。只有线程块 033 对它的点进行重排并启动四个线程块，如图 21.9D 所示。线程块 0330 至 0333 在把它们的点交换到缓冲区 0 之后退出，这可以在图 21.9E 中看到。

21.5 重要考量

在本节中，我们将简要说明使用动态并行的程序在执行行为方面的一些重要考量。程序员要充分理解这些考量，才能自信地使用动态并行。

内存与数据可见性

当父线程向子网格传递内存指针时，它必须确保所指向的内存对子网格是可访问的，这样子网格就不会试图访问无效的内存。父线程及其子网格都能访问的内存包括全局内存、常量内存和纹理内存。父线程不应向子网格传递指向局部内存或共享内存的指针，因为局部内存和共享内存分别只对线程自身和线程块私有。

除了确保父线程传递给子网格的内存对子网格可访问之外，程序员还必须清楚父线程写入该内存的数据何时对子网格可见，反之亦然。在执行的进程中，父线程和子网格对内存有一致视图的时刻有两个：父线程启动子网格的时刻，以及父线程通过同步 API 调用的完成得知子网格完成之时。换句话说，当父线程启动子网格时，子网格能够看到该启动之前对内存的所有更新，但对该启动之后的更新则没有这种保证。同样，在父线程对子网格的完成进行同步之前，子网格对内存所做的任何更新也都没有保证对父线程可见。

关于父线程与子网格之间内存和数据可见性的更多细节，请读者参阅 CUDA C++ 编程指南（NVIDIA Corporation, 2021）。

待启动池配置

待启动池是一个缓冲区，用于跟踪正在执行或等待执行的核函数。该池被分配固定大小的空间，因此可以支持固定数量的待启动核函数调用（默认为 2048）。如果超出这个数量，就会使用虚拟化池，导致显著的性能下降，下降幅度可能达到一个数量级或更多。为了避免这种性能下降，程序员可以在主机函数中执行 cudaDeviceSetLimit() API 调用来设置 cudaLimitDevRuntimePendingLaunchCount 配置，从而增大固定池的大小。

例如，在第 21.3 节 的贝塞尔曲线计算中，如果 N_LINES 设为 4096，那么将启动 4096 个子网格，其中一半的启动将使用虚拟化池。这会造成严重的性能损失。然而，如果固定大小池设为 4096，执行时间将大幅缩短。

作为一般性建议，固定大小池的大小应设置为预期启动的网格数量（如果它超过默认大小的话）。在贝塞尔曲线示例中，我们会先调用 cudaDeviceSetLimit(cudaLimitDevRuntimePendingLaunchCount, N_LINES)，再调用 computeBezierLines_parent() 核函数。

流

正如主机代码可以使用流来并发执行核函数一样，设备线程在使用动态并行启动网格时也可以使用流。流的范围对其创建所在的线程块是私有的。当核函数调用未指定流时，线程块中所有线程都使用默认的 NULL 流。这意味着在同一线程块中启动的所有网格都将被串行化，即使它们是由不同线程启动的。然而，通常情况下，线程块中不同线程启动的网格是相互独立的，可以并发执行。因此，如果程序员希望避免串行化带来的性能损失，就必须注意在每个线程中显式使用不同的流。

第 21.3 节 的贝塞尔曲线示例启动的子网格数量与 computeBezierLines_parent() 核函数中的父线程数量相同（图 21.7 中的第 19 行）。如果使用默认的 NULL 流，同一父线程块启动的所有网格都将被串行化。因此，在启动 computeBezierLines_child() 核函数时使用默认 NULL 流，与不使用动态并行的原核函数相比，会大幅降低并行性。

如果需要更高的并发度，则必须在每个线程中创建并使用命名流。图 21.12 展示了应替换图 21.7 中第 19 行的代码。使用这段代码后，从同一线程块启动的核函数将被放入不同的流中，可以并发运行。这将更好地利用所有 SM，使执行时间显著缩短。

嵌套深度

通过动态并行启动的核函数本身可以调用其他核函数，而这些核函数又可以继续调用其他核函数，依此类推。我们在第 12.4 节 的四叉树应用中看到过这样的核函数示例。每一次下级启动都被视为一个新的嵌套层级，而达到的层级总数称为嵌套深度。当前硬件支持的最大嵌套深度为 24 层。因此，像四叉树示例中的那种核函数，在决定是否进行动态启动之前，应当检查这个限制。

在存在父子同步的情况下，由于系统需要存储父网格状态的内存数量，嵌套深度还会受到额外的限制。这一限制被称为同步深度。关于嵌套深度和同步深度的更多细节，请读者参阅 CUDA C++ 编程指南（NVIDIA Corporation, 2021）。

21.6 小结

CUDA 动态并行扩展了 CUDA 编程模型，允许核函数调用其他核函数。这使得每个线程能够动态发现工作，并根据新发现的工作量启动新的网格。它还支持线程动态分配设备内存。正如我们在贝塞尔曲线计算示例中所展示的，这些扩展可以带来更好的线程间和线程块间工作均衡，以及更高效的内存使用。CUDA 动态并行还帮助程序员实现递归算法，正如四叉树示例所示。

除了确保更好的工作均衡之外，动态并行在可编程性方面还提供了许多优势。然而，必须牢记的是，启动线程数很少的网格可能导致 GPU 资源的严重利用不足。一般性建议是启动包含大量线程块的子网格；如果线程块数量较少，则至少要启动包含大量线程的线程块。

类似地，嵌套并行可以被视为树处理的一种形式。当树节点较粗（即每个节点部署大量线程）和/或分支度数较大（即每个父节点有大量子节点）时，嵌套并行能提供更高的性能。由于嵌套深度在硬件上是有限制的，因此只有相对较浅的树才能被高效实现。

要有效使用动态并行，程序员需要理解内存内容可见性、待启动数量以及流等细节。在动态并行中，谨慎地使用父网格与子网格之间的内存和流，对于正确执行以及在启动子网格时达到期望的并行度至关重要。
