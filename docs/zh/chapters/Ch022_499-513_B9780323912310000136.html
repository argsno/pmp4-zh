高级实践与未来演进

特别贡献：Isaac Gelado 与 Mark Harris

摘要

本章简要回顾了 CUDA 的发展历史并展望了未来。本章阐明了主机-设备交互模型在几代产品中的能力与局限，包括零拷贝内存、统一虚拟地址空间和统一内存。本章还介绍了核函数执行期间处理页错误这一新能力所带来的额外功能。本章也介绍了核函数执行效率的演进，以及对多个核函数并行执行的支持。最后，本章概述了编程、性能分析和调试环境方面的最新进展。

本书始终聚焦于可扩展的并行编程。CUDA C 与 GPU 硬件主要充当了我们示例和练习的编程平台。不过，基于 CUDA C 学到的并行编程概念和技能可以轻松迁移到其他并行编程平台。例如，正如我们在第 20 章《编写异构计算集群程序：CUDA 流入门》中所见，消息传递接口（MPI）的大多数关键概念，如进程、进程号和屏障，在 CUDA C 中都有对应物。此外，正如我们也在第 20 章《编写异构计算集群程序》中讨论过的，支持 CUDA 的 GPU 已广泛应用于高性能计算（HPC）系统。对许多读者来说，CUDA C 很可能是一个重要的应用开发和部署平台，而不仅仅是学习工具。因此，读者有必要了解那些旨在支持应用级高性能编程的 CUDA C 高级特性和实践。例如，正如我们在第 20 章《编写异构计算集群程序》中所见，CUDA 流使 MPI HPC 应用能够将通信与计算重叠。这种能力对于达成整个应用的性能目标尤为重要。有鉴于此，本章将向读者概述 CUDA C 与 GPU 计算硬件的高级特性，这些特性对在应用中实现高性能与可维护性都很重要。对每个特性，我们都会介绍其基本概念，以及它在 GPU 计算各代产品中的演进简史。透彻理解这些概念和演进历史，有助于澄清人们对这些特性的一些常见困惑。其目标是帮助读者建立起一个概念框架，以便更深入地研究这些特性。

22.1 主机/设备交互模型

到目前为止，我们一直假定异构计算系统中主机与设备之间存在一种相当简单的交互模型。在这个简单模型中，正如第 2 章《异构数据并行计算》所介绍的，每个设备都有独立于主机内存（即系统内存）的设备内存（CUDA 全局内存）。要由设备上运行的核函数处理的数据，需要通过调用 cudaMemcpy()函数从主机内存传输到设备内存。设备产生的数据，也需要通过调用 cudaMemcpy()函数从设备内存传输到主机，才能被主机使用。这个模型虽然简单易懂，但在应用层面会导致若干问题。

首先，磁盘控制器和网络接口卡等 I/O 设备被设计为在主机内存上高效工作。由于设备内存与主机内存相互独立，输入数据需要从主机内存传输到设备内存，输出数据也需要从设备内存传输回主机内存，才能用于 I/O 操作。这些额外传输增加了 I/O 延迟，并降低了可达到的 I/O 吞吐量。对许多应用而言，如果 I/O 设备能够直接在设备内存上工作，将能提升整体应用性能并简化应用代码。

其次，传统编程系统将应用的数据结构存放在主机内存中。其中一些数据结构很大。与主机内存相比，早期几代支持 CUDA 的 GPU 的设备内存很小，这迫使应用开发者将大型数据结构划分成能放进设备内存的数据块。例如，在第 18 章《静电势图》中，三维（3D）静电能量网格数组被划分成二维切片，在主机内存与设备内存之间来回传输。对许多应用来说，如果整个数据结构都能驻留在设备内存中会好得多。对某些应用，甚至可能找不到把数据结构划分为更小块的好办法。对这些应用，最好的做法是让 GPU 直接访问主机内存中的数据，或者让 CUDA 运行时系统软件迁移核函数执行期间所用的数据。

主机/设备交互模型的这些局限，源于早期几代支持 CUDA 的 GPU 的内存体系结构的局限。在这些早期设备上，应用唯一可行的主机/设备交互模型，就是我们前几章一直假定的那个简单模型。随着越来越多的应用采用 GPU 计算，它们的需求促使 CUDA 系统软件开发者与 GPU 硬件设计者提供更好的解决方案。研究者们早就认识到这些需求，并从 CUDA 诞生之初就提出了解决方案（Gelado et al., 2010）。本节其余部分将简要回顾为解决这些局限而取得的进展。

零拷贝内存与统一虚拟地址空间

2009 年，CUDA 2.2 引入了对系统内存的零拷贝访问。这使得主机代码可以把一个指向主机内存的特殊设备数据指针提供给核函数。设备上运行的代码可以使用该指针，通过系统互连（如 PCIe 总线）直接访问主机内存，而无需调用 cudaMemcpy()。零拷贝内存是锁页主机内存（见第 20 章《编写异构计算集群程序》），通过调用 cudaHostAlloc()并以 cudaHostAllocMapped 作为 flag 参数的值来分配。我们之前提到过，flag 参数的其他取值用于更高级的用法。cudaHostAlloc()返回的数据指针不能直接传给核函数；主机代码必须先调用 cudaHostGetDevicePointer()获得一个有效的设备数据指针，再把这个函数返回的设备数据指针传给核函数。这意味着主机代码和设备代码使用不同的数据指针访问同一块物理内存。

正如我们在第 20 章《编写异构计算集群程序》中所解释的，主机内存页必须被锁定，以防操作系统在 GPU 访问这些数据时对它们意外执行换页操作。显然，这类访问会遭受系统互连的长延迟和有限带宽之苦。系统互连的带宽通常不到全局内存带宽的 10%。正如我们在第 5 章《内存体系结构与数据局部性》中学到的，除非我们使用分块技术大幅减少每次浮点运算所执行的全局内存访问次数，否则核函数的性能通常受限于全局内存带宽。如果核函数的大部分内存访问都针对零拷贝内存，那么核函数的执行速度受系统互连带宽的限制会更为严重。因此，零拷贝内存只应被用于 GPU 上运行的核函数偶尔、稀疏地访问的应用数据结构。

2011 年，CUDA 4 引入了统一虚拟寻址（Unified Virtual Addressing）。在此之前，主机和设备各自拥有自己的虚拟地址空间，各自把主机或设备数据指针映射到物理主机或设备内存位置。这些互不相交的虚拟地址空间意味着，同一物理内存位置可能被主机和设备的不同虚拟地址访问，使用零拷贝内存时实际就是这种情况。统一虚拟地址空间（UVAS）最早由 GMAC 库提出（Gelado et al., 2010），并于 CUDA 4 中采用，它使用一个由主机和设备共享的单一虚拟地址空间。UVAS 保证每个物理内存地址只映射到一个虚拟内存位置。这使得 CUDA 运行时只需检查指针的虚拟内存地址，就能判断该数据指针指向的是主机内存还是设备内存。这一特性使 cudaMemcpy()调用不再需要指定数据拷贝方向。

需要指出的是，CUDA 4 中的 UVAS 并不保证指针所引用数据的可访问性。例如，主机代码不能用 cudaMalloc()返回的设备指针直接访问设备内存，反之亦然。零拷贝内存是个例外：主机代码可以把指向零拷贝内存的指针作为核函数启动参数直接传给设备。当核函数代码解引用这个零拷贝指针时，指针值会被转换成物理系统内存位置，并通过 PCIe 总线直接访问。请注意，这种方法并不保证核函数代码一定能解引用从内存位置读出的指针值，例如在遍历链表数据结构时顺着指针链逐个访问——除非所有内存都是用 cudaHostAlloc()分配的。

零拷贝内存在所能支持的数据结构类型和数据访问带宽两方面都存在局限，这促使 GPU 体系结构在 UVAS 之外进一步改进其内存模型。

大型虚拟地址空间与物理地址空间

早期支持 CUDA 的 GPU 的一个根本局限在于其虚拟地址和物理地址的宽度。这些早期设备支持 32 位虚拟地址和最高 32 位物理地址。对这些设备而言，设备内存的大小被限制为 4 GB，这是 32 位物理地址所能寻址的最大内存量。此外，CUDA 核函数只能处理大小小于 4 GB 的数据集——即 32 位指针所能访问的最大虚拟内存位置数，无论该数据集驻留在主机内存还是设备内存中。另外，现代 CPU 基于 64 位虚拟地址，其中实际使用了 48 位。这些主机虚拟地址无法容纳于 GPU 所用的 32 位虚拟地址，这也就限制了零拷贝内存所能支持的数据结构类型。

为了消除这一局限，从 2013 年推出的 Kepler GPU 架构开始，各代 GPU 都采用了现代虚拟内存体系结构，具备 64 位虚拟地址和至少 40 位的物理地址。显而易见的好处是，这些 GPU 可以配备超过 4 GB 的 DRAM，CUDA 核函数现在也能处理大型数据集。扩大的虚拟和物理地址空间显然使大容量设备内存的使用成为可能，同时也为更好的主机/设备交互模型打开了大门。例如，现在主机和设备可以使用完全相同的指针值访问同一份数据，无论它位于主机内存还是设备内存中。

巨大的 GPU 物理地址空间还允许 CUDA 系统软件把系统中不同 GPU 的设备内存纳入一个统一的物理地址空间。好处是，一个 GPU 只需解引用一个映射到其他 GPU 物理地址的数据指针，就能直接访问连接到同一 PCIe 总线的任何其他 GPU 的内存。在 Kepler GPU 架构之前，不同 GPU 之间的通信（例如第 20 章《编写异构计算集群程序》模板示例中的光环交换）只能通过主机代码触发的设备到设备内存拷贝来进行。这导致额外的内存消耗（用于存放从其他 GPU 拷贝来的数据），以及由内存拷贝操作带来的额外性能开销。直接访问系统中的其他设备内存，使得只需在核函数调用中把设备指针传给另一个 GPU，并用它来加载和/或存储需要通信的数据。

统一内存

2013 年，CUDA 6 引入了统一内存，它创建了一个由 CPU 和 GPU 共享的托管内存池，弥合了 CPU 与 GPU 之间的鸿沟。托管内存可通过单个指针供 CPU 和 GPU 双方访问。托管内存中的变量可以驻留在 CPU 物理内存、GPU 物理内存，甚至同时驻留在两者中。CUDA 运行时软件和硬件实现了数据迁移与一致性支持，例如 GMAC 系统（Gelado et al., 2010）。总体效果是：对在 CPU 上运行的代码而言，托管内存看起来就像 CPU 内存；对在 GPU 上运行的代码而言，它又像 GPU 内存。当然，应用必须执行适当的同步操作，如屏障或原子操作，来协调对托管内存位置的并发访问。共享的全局虚拟地址空间使应用中的所有变量都具有唯一的地址。当编程工具和运行时系统把这种内存体系结构暴露给应用时，可以带来几项重大好处。

好处之一是，将 CPU 代码移植到 CUDA 所需的工作量大大减少。在图 22.1 中，我们在左侧展示了一个简单的 CPU 代码示例。借助统一内存，只需两处简单改动即可把该代码移植到 CUDA。第一处改动是用 cudaMallocManaged()和 cudaFree()替代 malloc()和 free()。第二处改动是启动一个核函数并执行设备同步，而不是调用 qsort()函数。显然，仍然需要编写或拥有一个并行 qsort 核函数。我们想说明的是，对主机代码的改动是直接了当且易于维护的。

CUDA 6 统一内存的性能受限于 Kepler 和 Maxwell GPU 架构的硬件能力。所有被 CPU 修改过的托管内存位置的内容，都必须在任何网格启动前刷新到 GPU 设备内存。CPU 和 GPU 不能同时访问同一托管内存分配，而且统一内存地址空间的大小受限于 GPU 物理内存的大小。这些局限源于这些 GPU 架构缺乏在主机内存与设备内存之间支持一致性的能力，而且数据迁移大多由软件完成。

2016 年，Pascal GPU 架构新增了一些特性，进一步简化 CPU 与 GPU 之间的内存编程和共享，并进一步降低借助 GPU 获得显著加速比所需付出的努力。两项主要的硬件特性促成了这些改进：对大型地址空间的支持和页错误处理能力。

Pascal GPU 架构把 GPU 的寻址能力扩展到 49 位虚拟寻址。这一扩展足以覆盖现代 CPU 的 48 位虚拟地址空间以及 GPU 自身的内存。这使统一内存程序能够把系统中所有 CPU 和 GPU 的完整地址空间当作单一虚拟地址空间来访问，而不是受限于能拷贝到设备内存的数据量。这样一来，CPU 和 GPU 可以真正共享指针值，使 GPU 能够遍历主机内存中基于指针的数据结构。

Pascal GPU 架构中的内存页错误处理支持是一项关键的新特性，它提供了更无缝的统一内存功能。结合全系统范围的虚拟地址空间，处理页错误的能力消除了 CUDA 系统软件在每次网格启动前将所有托管内存内容同步（刷新）到 GPU 的需要。CUDA 运行时可以通过如下方式实现一致性机制：当主机或设备修改托管内存中的变量时，允许另一方使其副本失效。这种失效可以通过页映射和保护机制来实现。启动网格时，CUDA 系统软件不再需要把托管内存数据的 GPU 副本全部更新到最新。如果网格访问的数据在设备内存中的副本已被主机置为失效，GPU 将处理一个页错误，把数据更新到最新后恢复执行。

如果 GPU 上运行的网格访问一个不在其设备内存中的页，它同样会产生页错误，使该页按需自动迁移到 GPU 内存。另一种做法是，如果预期数据只是偶尔被访问，则可以把该页映射进 GPU 地址空间，通过系统互连访问（按需映射有时比迁移更快）。请注意，统一内存是系统级的：GPU（和 CPU）既可以从 CPU 内存，也可以从系统中其他 GPU 的内存触发页错误并迁移内存页。如果某个 CPU 函数解引用指针并访问一个映射到 GPU 物理内存的变量，该数据访问仍然会被满足，只是延迟可能更长。这种能力使 CUDA 程序更容易调用尚未移植到 GPU 的遗留库。在之前的 CUDA 内存体系结构中，开发者必须手动把数据从设备内存传输到主机内存，才能在 CPU 上使用遗留库函数处理这些数据。

具备页错误处理能力的统一内存，使 CPU/GPU 交互机制比零拷贝内存通用得多。它允许 GPU 遍历主机内存中的大型数据结构。从 Pascal 架构开始，即使数据结构不驻留在零拷贝内存中，GPU 设备也能遍历链表数据结构。这是因为主机代码和设备代码使用相同的指针值来引用同一个变量。因此，主机构建的链表数据结构中嵌入的指针值，设备也可以遍历，反之亦然。在某些应用领域，如 CAD，主机物理内存系统可能拥有数百 GB 的容量。之所以需要这么大的物理内存系统，是因为这些应用要求整个数据集“常驻内存”。凭借直接访问超大型 CPU 物理内存的能力，GPU 加速这些应用变得切实可行。

虚拟地址空间控制

CUDA 11 引入了一组底层 API，让程序员在内存分配方面拥有更大的灵活性。新 API 可以使用 cuMemAddressReserve()预留一段虚拟地址空间。随后，程序员可以使用 cuMemCreate()在任何设备上分配物理内存，并使用 cuMemMap()把它映射到预留范围内的任意位置。这些 API 支持在多个设备之间构建自定义的数据结构布局。例如，可以用单个指针引用跨多个设备分配的 3D 体数据。

22.2 核函数执行控制

核函数中的函数调用

早期的 CUDA 版本不允许在核函数执行期间进行函数调用。尽管核函数的源代码看起来包含函数调用，但编译器必须能够把所有函数体内联进核函数对象，使核函数在运行时不存在任何函数调用。虽然对许多应用中性能关键的部分来说，这个模型运行得相当好，但它不支持更复杂应用中常见的软件工程实践。特别是，它不支持系统调用、动态链接库调用、递归函数调用，以及 C++ 等面向对象语言中的虚函数。

Kepler 等后来的设备架构支持在运行时于核函数中进行函数调用。CUDA 5 及以后版本都支持这一特性。编译器不再必须内联函数体，但仍可以把它作为性能优化手段。这一能力部分得益于为 CUDA 线程实现的大规模并行调用帧栈，其实现利用了缓存且速度很快。它使 CUDA 设备代码更具“可组合性”：不同的作者可以编写不同的 CUDA 核函数组件并把它们组装在一起，而无需付出高昂的重新设计成本。它还允许软件供应商在不提供源代码的情况下发布设备库，以保护知识产权。不过，仍然存在一些局限。例如，对虚函数的支持仅限于由设备代码构造的对象，而且设备代码的动态库不受支持。

运行时函数调用的支持还使递归成为可能，并大大减轻了程序员从传统面向 CPU 的算法转向 GPU 调优代码的负担。在某些情况下，开发者可以把 CPU 代码“剪切粘贴”进 CUDA 核函数，得到一个性能尚可的核函数，尽管持续的调优仍然会带来好处。

借助函数调用支持，核函数现在可以调用标准库函数，如 printf()和 malloc()。根据我们的经验，在核函数中调用 printf()的能力，为调试和支持生产软件中的核函数提供了一种微妙但重要的帮助。许多最终用户是非技术人员，很难教会他们运行调试器来向开发者提供崩溃前发生什么的更多细节。在核函数中调用 printf()的能力，使开发者可以在应用中增加一个转储内部状态的模式，这样最终用户就能提交有意义的错误报告。

CUDA 8 增加了对 C++11 的支持，并随之引入了另一种形式的函数调用：lambda 表达式。与元编程技术结合时，设备端 lambda 使高性能可复用代码的开发成为可能。CUDA 还支持把 lambda 函数作为参数传给 CUDA 核函数。这一特性可用于编写通用核函数（例如排序核函数），其中比较函数只是核函数的一个输入参数。CUDA 还增加了对“扩展 lambda”的实验性支持，通过–extended-lambda 编译器标志启用。该特性允许程序员用__host__ __device__修饰符标注 C++ lambda，进一步简化了可复用代码的编写。

核函数中的异常处理

早期的 CUDA 系统不支持核函数代码中的异常处理。虽然这对许多高性能应用中性能关键的部分来说不是重大局限，但在依赖异常来检测和处理罕见情况、无需显式编写测试代码的生产级应用中，它常常带来软件工程成本。

凭借有限的异常处理支持，CUDA 调试器允许用户逐步执行、设置断点，或运行核函数直到发生无效内存访问。无论哪种情况，用户都可以在执行挂起时检查核函数的局部变量和全局变量的值。根据我们的经验，CUDA 调试器是检测越界内存访问和潜在竞态条件的非常有用的工具。

多个网格的并发执行

最早的 CUDA 系统在任一时刻只允许一个网格在每台 GPU 设备上执行。多个网格可以通过 CUDA 流提交执行，但它们会在队列中缓冲，直到当前网格执行完毕后才释放下一个网格。Fermi GPU 架构及其后继架构允许同一应用的多个网格同时执行，这减轻了应用开发者为了更充分地利用设备而把多个核函数“打包”成一个更大核函数的压力。此外，有时把工作划分成可按不同优先级执行的块也是有益的。

同时执行多个网格的好处的一个典型例子是并行集群应用，这类应用把工作划分为“本地”和“远程”两个部分，其中远程工作涉及与其他节点的交互，并且处于全局进度的关键路径上（第 20 章《编写异构计算集群程序》）。在之前的 CUDA 系统中，网格需要执行大量工作才能高效利用设备，而且必须小心不能启动会阻塞全局工作的本地工作。这意味着要做出选择：要么在等待远程工作到达时让设备利用不足，要么急切地开始本地工作以保持设备高效，代价是完成远程工作单元的延迟增加（Phillips and Stone, 2009）。借助多网格执行，应用可以用小得多的网格尺寸来启动工作，因此当高优先级远程工作到达时，它可以低延迟地开始运行，而不是被大型本地计算网格挡在后面。

硬件队列与动态并行

在 Kepler 架构和 CUDA 5 中，多网格启动设施通过增加多个硬件队列而得到扩展，这些队列可以更高效地调度来自多个流的多个网格的线程块。此外，CUDA 动态并行（已在第 21 章《CUDA 动态并行》中介绍）允许在 GPU 上创建工作：GPU 网格可以异步、动态地启动子网格，并且启动方式可以依赖于数据或计算负载。这减少了 CPU 与 GPU 之间的交互和同步，因为 GPU 现在可以独立管理更复杂的工作负载，CPU 则得以腾出手来执行其他有用的计算。

可中断网格

Fermi GPU 架构允许“取消”正在运行的网格，从而能够创建这样的 CUDA 加速应用：用户可以在任何时候中止长时间运行的计算，而不需要程序员为此付出大量的设计工作。这使实现用户级任务调度系统成为可能，该系统可以在计算系统的 GPU 节点之间更好地进行负载均衡，并且可以更从容地处理某个 GPU 负载过重、运行速度可能慢于其他 GPU 的情况（Stone & Hwu, 2009）。

协作核函数

处理不规则数据的 GPU 核函数常常遭受负载不均衡之苦。CUDA 11 引入了协作核函数来缓解这一问题。协作核函数最多可以执行足以完全占满 GPU 的线程块数量，CUDA 运行时保证所有这些线程块会并发执行。这一并发性保证使线程块能够安全协作，而不会在共享互斥机制（例如互斥量）上发生死锁——这些机制可用于保护共享数据结构（例如工作队列）。协作核函数需要特殊的 APIcudaLaunchCooperativeKernel()，并提供设备端 API 来识别和划分线程组。协作核函数不限于单个设备，也可以使用 cudaLaunchCooperativeKernelMultiDevice()在多个设备上运行。

22.3 内存带宽与计算吞吐量

双精度速度

早期的设备执行双精度浮点算术时，与单精度相比速度大幅降低（大约慢 8 倍）。Fermi 及其后继架构的浮点运算单元得到了显著加强，双精度运算速度约为单精度的二分之一。大量进行双精度浮点运算的应用从中受益匪浅。

在实践中，获益最大的是把基于 CPU 的数值应用移植到 GPU 的开发者。凭借改进后的双精度速度，他们没有多大动力去花力气评估自己的应用或应用的一部分能否放进单精度。这显著降低了把 CPU 应用移植到 GPU 的开发成本，也回应了 HPC 社区在 GPU 问世之初对 GPU 的一大批评。

一些处理较小输入数据类型（8 位、16 位或单精度浮点）的应用，由于使用 32 位而非 64 位数据可降低带宽占用，继续从单精度运算中受益。医学成像、遥感、射电天文学、地震分析等应用，以及其他自然数据，常常属于这一类。Pascal GPU 架构为使用 16 位半精度数进行计算引入了新的硬件支持，以进一步提升数据能容纳进半精度表示的应用的性能和能效。例如，在基于 Ampere 架构的 A100 上，使用张量核心的 16 位半精度运算吞吐量达到 156 TFLOPS，相比其 19.5 TFLOPS 的单精度吞吐量是巨大的提升。

更好的控制流效率

从 Fermi GPU 架构开始，CUDA 系统采用了一种通用的编译器驱动的断言执行（predication）技术（Mahlke et al., 1995），比以往的 CUDA 系统能更有效地处理控制流。虽然该技术在 VLIW 系统中只是取得中等成功，但在 GPU 线程束式 SIMD 执行系统中却带来了更惊人的速度提升。这一能力拓宽了能够利用 GPU 的应用范围。特别是，对光线追踪、量子化学可视化、元胞自动机模拟等高度数据驱动的应用，有可能实现重大的性能收益。

可配置缓存与便笺存储器

早期 CUDA 系统中的共享内存充当程序员管理的便笺存储器，提升了那些关键数据结构具有局部化、可预测访问模式的应用的速度。从 Fermi GPU 架构开始，共享内存被增强为更大的片上内存，可以配置为一部分是缓存、一部分是共享内存，从而使可预测和较不可预测的访问模式都能受益于片上内存。这种可配置性使程序员可以根据应用的最佳匹配来分配资源。

处于早期设计阶段、直接从 CPU 代码移植的应用，将因缓存作为片上内存的主导部分而大受裨益。这进一步平滑了性能调优过程，提高了开发者把 CPU 应用移植到 GPU 时可获得的“轻松性能”水平。

现有的 CUDA 应用以及那些访问模式可预测的应用，可以在保持与上一代设备相同设备“占用率”的同时，增加对快速共享内存的使用。对性能或能力受共享内存大小限制的 CUDA 应用来说，共享内存容量的增加将是受欢迎的改进。例如，在模板计算中（第 8 章《模板》和第 20 章《编写异构计算集群程序》），如用于计算流体动力学的有限差分法，增加的共享内存容量改善了内存带宽效率和应用的性能。

增强的原子操作

Fermi GPU 架构中的原子操作比以往 CUDA 系统中的快得多，而 Kepler 中的原子操作更快。此外，Kepler 的原子操作更为通用。Maxwell GPU 架构中针对共享内存变量的原子操作，其吞吐量得到了进一步提升。原子操作常用于随机分散计算模式，如直方图（第 9 章《并行直方图：原子操作与私有化入门》）。更快的原子操作减少了对算法变换的需求，例如用扫描（第 11 章《前缀和（扫描）：并行算法中的工作效率入门》）（Sengupta et al., 2007）和排序（第 13 章《排序》）（Satish et al., 2009）来实现此类随机分散计算。这些变换往往会增加执行目标计算所需的核函数调用次数，以及操作总数。更快的原子操作还可以减少在需要进行集合操作或由多个线程块更新共享数据结构的算法中动用主机 CPU 的需求，从而减轻 CPU 与 GPU 之间的数据传输压力。

增强的全局内存访问

在 Fermi 和 Kepler 中，随机内存访问的速度比早期 GPU 架构快得多。程序员可以不必那么在意内存合并。这使更多 CPU 算法能够直接在 GPU 上用作可接受的基础，进一步铺平了移植那些访问多种多样数据结构的应用的路径，例如光线追踪，以及其他高度面向对象、可能难以转换成完美分块数组的应用。

Pascal GPU 架构采用了第二代高带宽内存（HBM2，High-Bandwidth Memory version 2）3D 堆叠 DRAM 内存，其内存带宽最高可达上一代 NVIDIA Maxwell 架构 GPU 的 3 倍。Pascal 还是第一个支持 NVLink 处理器互连的架构，NVLink 使 Tesla P100 的 GPU-GPU 和 GPU-CPU 通信性能达到 PCI Express 3.0 的 5 倍。这种互连极大地改善了节点内多 GPU 计算的可扩展性，以及 GPU 与支持 NVLink 的 CPU 之间数据共享的效率。

22.4 编程环境

统一的设备内存空间

在早期的 CUDA 设备中，共享内存、局部内存和全局内存各自拥有独立的地址空间。开发者可以使用指向全局内存的指针，但不能使用指向其他内存的指针。从 2009 年推出的 Fermi 架构开始，这些内存成为统一地址空间的一部分。这一统一地址空间使同一套加载/存储指令和指针地址就能访问任何 GPU 内存空间（全局、局部或共享内存），而不必为每种内存使用不同的指令和指针。这使得抽象掉“某个操作数存放在哪块内存”变得更容易，程序员只需在分配时考虑这一点，而且无论 CUDA 数据对象来自哪块内存区域，把它传给其他过程和函数都变得更简单。

这使 CUDA 代码模块更具“可组合性”。也就是说，CUDA 设备函数可以接受一个可能指向任何这些内存的指针。例如，如果没有统一的 GPU 地址空间，设备函数就需要为参数可能驻留的每种内存各编写一个实现。统一的 GPU 地址空间使所有主要类型 GPU 内存中的变量都能以相同方式访问，从而允许一个设备函数接受可驻留在不同类型 GPU 内存中的参数。如果函数参数指针指向共享内存位置，代码运行会更快；如果指向全局内存位置，则会慢一些。程序员仍然可以进行手动数据放置和传输作为性能优化。这一能力显著降低了构建生产级 CUDA 库的成本，还实现了完整的 C 和 C++ 指针支持，这在当时是一项重大进步。

未来的 CUDA 编译器将包含对 C++ 模板和核函数中虚函数调用的增强支持。虽然运行时函数调用能力等硬件增强已经就位，但编译器中增强的 C++ 语言支持需要更多时间。借助这些增强，未来的 CUDA 编译器将支持大多数主流的 C++ 特性。例如，在核函数中使用 new、delete、构造函数和析构函数等 C++ 特性已经得到支持。

新的和不断演进的编程接口继续提高异构并行程序员的生产力。OpenACC 允许开发者用编译器指令标注串行循环，使编译器能够生成 CUDA 核函数。开发者可以使用 Thrust 库中的并行泛型函数、类和迭代器来描述其计算，由底层机制生成并配置实现该计算的核函数。CUDA FORTRAN 让 FORTRAN 程序员可以用自己熟悉的语言开发 CUDA 核函数。特别是，CUDA FORTRAN 对多维数组的索引提供了强有力的支持。C++AMP 允许开发者把核函数描述为作用于逻辑数据结构（如 C++ 应用中的多维数组）的并行循环。我们完全相信，新的创新将不断涌现，进一步提振开发者在这个激动人心的领域中的生产力。

带关键路径分析的性能剖析

在 CPU 和 GPU 上都进行大量计算的异构应用中，确定在哪里投入优化努力可能颇具挑战。理想情况下，优化代码时，人们希望瞄准应用中能以最少努力带来最高加速比的位置。为此，CUDA 7.5 引入了 PC 采样，提供指令级性能剖析，使用户能够定位应用中耗时最多的具体代码行。

然而，这类性能分析器的用户面临的一个挑战是：应用中运行时间最长的核函数并不总是最关键、最值得优化的目标。如图 22.2 所示，核函数 X 是运行时间较长的核函数，但它的执行时间与 CPU 执行活动 A 完全重叠。如果不同时缩短 A 的执行时间，那么缩短核函数 X 执行时间的任何进一步改进都不太可能改善应用性能。核函数 Y 的执行时间虽然不如核函数 X 长，但它位于应用执行的关键路径上。CPU 在等待核函数 Y 完成时空闲。加速核函数 Y 将减少 CPU 等待的时间，因此它是最佳的优化目标。

2016 年，CUDA 8 中的 Visual Profiler 提供了 GPU 核函数与 CPU CUDA API 调用之间的关键路径分析，使优化努力能够更精准地投放。图 22.3 展示了 CUDA 8 Visual Profiler 中的关键路径分析。不在关键路径上的 GPU 核函数、拷贝和 API 调用都会变灰，只有位于应用执行关键路径上的活动才会以彩色高亮显示。这使用户能够轻松识别需要瞄准的核函数和其他活动，以便集中优化努力。

22.5 未来展望

CUDA 的演进持续增强对开发者生产力和现代软件工程实践的支持。凭借新的能力和编程语言支持，能够以最低开发成本获得合理性能的应用范围将显著扩大。与以往的 CUDA 系统相比，开发者已经体验到应用开发、移植和维护成本的下降。使用 Thrust 及类似自动生成 CUDA 代码的高级工具开发的现有应用，其性能也很可能会立即获得提升。内存体系结构、核函数执行控制和计算核心性能方面的硬件增强，其好处将在相应的 SDK 版本中显现，但这些增强的真正潜力可能需要数年时间才能在 SDK 和运行时中充分发挥。我们预测，未来几年，工业界和学术界在 GPU 计算的编程工具和运行时环境方面将迎来激动人心的创新时代。
