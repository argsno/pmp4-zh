数据并行指的是这样一种现象：对数据集不同部分所要执行的计算工作可以彼此独立完成，因而可以相互并行执行。许多应用展现出丰富的数据并行性，使其适合可扩展的并行执行。因此，并行程序员熟悉数据并行这一概念，以及利用数据并行编写代码所需的并行编程语言构造，就显得十分重要。在本章中，我们将使用 CUDA C 语言构造来开发一个简单的数据并行程序。

2.1 数据并行

当现代软件应用运行缓慢时，问题通常出在数据上——需要处理的数据太多了。图像处理应用要处理包含数百万到数万亿像素的图像或视频。科学应用使用数十亿个网格点对流体动力学进行建模。分子动力学应用必须模拟数千到数十亿个原子之间的相互作用。航班调度要处理数千个航班、机组人员和机场登机口。这些像素、粒子、网格点、相互作用、航班等大多都可以在很大程度上彼此独立地处理。例如，在图像处理中，把彩色像素转换为灰度只需要该像素本身的数据。图像模糊需要把每个像素的颜色与相邻像素的颜色进行平均，只需要这一小片相邻像素的数据。即使是看似全局的操作，例如求一幅图像中所有像素的平均亮度，也可以分解为许多可以独立执行的更小计算。这种对数据的不同部分进行独立求值，正是数据并行的基础。编写数据并行代码需要围绕数据来（重新）组织计算，使我们可以并行执行这些独立的计算，从而更快地完成整体任务——通常要快得多。

下面我们用一个彩色到灰度转换的例子来说明数据并行这一概念。图 2.1 显示了一幅彩色图像（左侧），它由许多像素组成，每个像素都包含一个红色、绿色和蓝色的分数值（r、g、b），取值从 0（黑色）到 1（全强度）。

为了把彩色图像（图 2.1 的左侧）转换为灰度图像（右侧），我们对每个像素应用如下加权和公式来计算其亮度值 L：

L=r*0.21+g*0.72+b*0.07

RGB 彩色图像表示

在 RGB 表示中，图像中的每个像素存储为 (r, g, b) 值的一个元组。图像一行的格式是 (r g b) (r g b) … (r g b)，如下面的示意图所示。每个元组指定红色（R）、绿色（G）和蓝色（B）的一种混合。也就是说，对每个像素而言，r、g、b 的值分别表示渲染该像素时红、绿、蓝三种光源的强度（0 表示暗，1 表示全强度）。

这三种颜色的实际允许混合方式因行业规定的色彩空间而异。这里，AdbobeRGB™ 色彩空间中三种颜色的有效组合显示为三角形的内部区域。每种混合的纵坐标（y 值）和横坐标（x 值）表示像素强度中应分配给 G 和 R 的比例，像素强度的剩余比例 (1-y–x) 应分配给 B。要渲染一幅图像，需要使用每个像素的 r、g、b 值来计算该像素的总强度（亮度）以及混合系数 (x, y, 1-y-x)。

如果我们将输入视为按 RGB 值数组 I 组织的一幅图像，将输出视为相应的亮度值数组 O，就得到图 2.2 所示的简单计算结构。例如，O[0] 是通过按上面的公式计算 I[0] 中 RGB 值的加权和得到的；O[1] 是通过计算 I[1] 中 RGB 值的加权和得到的；O[2] 是通过计算 I[2] 中 RGB 值的加权和得到的；依此类推。这些逐像素的计算互不依赖，全部可以独立执行。显然，彩色到灰度转换展现出丰富的数据并行性。当然，完整应用中的数据并行可能更为复杂，而本书有相当多的篇幅正是用于讲解发现和利用数据并行所必需的并行思维。

任务并行与数据并行

数据并行并不是并行编程中使用的唯一一种并行方式，任务并行也在并行编程中被广泛使用。任务并行通常通过应用的任务分解来体现。例如，一个简单的应用可能需要做一次向量加法和一次矩阵-向量乘法，其中的每一个都是一个任务。如果这两个任务可以独立完成，就存在任务并行。I/O 和数据传输也是常见的任务来源。

在大型应用中，通常会有更多的独立任务，因此也就有更大程度的任务并行。例如，在分子动力学模拟器中，自然任务清单包括振动作用力、转动作用力、非键合力的邻居识别、非键合力、速度与位置，以及基于速度与位置的其他物理属性。

一般来说，数据并行是并行程序可扩展性的主要来源。面对大规模数据集，人们通常能发现丰富的数据并行，从而充分利用大规模并行处理器，让应用性能随着每一代拥有更多执行资源的硬件而增长。尽管如此，任务并行在实现性能目标方面也能发挥重要作用。我们将在后文引入流（streams）时再讨论任务并行。

2.2 CUDA C 程序结构

我们现在就来学习如何编写一个利用数据并行实现更快执行的 CUDA C 程序。CUDA C1 以最少的语法和库函数扩展了广受欢迎的 ANSI C 编程语言，让程序员能够面向同时包含 CPU 核心和大规模并行 GPU 的异构计算系统进行编程。顾名思义，CUDA C 建立在 NVIDIA 的 CUDA 平台之上。CUDA 目前是进行大规模并行计算最成熟的框架，在高性能计算行业中得到广泛应用，编译器、调试器和性能分析器等关键工具在主流操作系统上均可使用。

CUDA C 程序的结构反映了计算机中主机（CPU）与一个或多个设备（GPU）共存这一事实。每个 CUDA C 源文件都可以同时包含主机代码和设备代码。默认情况下，任何传统 C 程序都是一个只包含主机代码的 CUDA 程序。我们可以向任何源文件中添加设备代码，设备代码用特殊的 CUDA C 关键字明确标记。设备代码包含一些函数，即核函数，这些函数的代码以数据并行方式执行。

CUDA 程序的执行过程如图 2.3 所示。执行从主机代码（CPU 串行代码）开始。当调用核函数时，会在设备上启动大量线程来执行该核函数。一次核函数调用所启动的所有线程合称为一个网格。这些线程是 CUDA 平台上并行执行的主要载体。图 2.3 显示了两个线程网格的执行过程。我们很快会讨论这些网格是如何组织的。当一个网格的所有线程都执行完毕时，该网格终止，执行回到主机上继续，直到启动另一个网格。请注意，图 2.3 显示的是一个简化模型，其中 CPU 执行与 GPU 执行并不重叠。许多异构计算应用会设法让 CPU 与 GPU 的执行相互重叠，以同时发挥 CPU 和 GPU 的优势。

启动一个网格通常会生成大量线程，以利用数据并行。在彩色到灰度转换的例子中，每个线程可用来计算输出数组 O 的一个像素。此时，网格启动应生成的线程数等于图像中的像素数。对于大图像，将生成大量的线程。得益于高效的硬件支持，CUDA 程序员可以假设这些线程的生成与调度只需要很少的时钟周期。这一假设与传统 CPU 线程形成鲜明对比——传统的 CPU 线程通常需要数千个时钟周期来生成和调度。在下一章中，我们将展示如何实现彩色到灰度转换和图像模糊的核函数。为了简单起见，本章其余部分将使用向量加法作为贯穿示例。

线程

线程是现代计算机中处理器如何执行串行程序的一种简化视图。一个线程由程序的代码、代码中正在执行的执行点，以及其变量和数据结构的取值构成。就用户而言，线程的执行是串行的。我们可以使用源代码级调试器来监视线程的执行进度：一次执行一条语句，查看下一条将要执行的语句，并在执行过程中检查变量和数据结构的取值。

线程在编程中已经使用了很多年。如果程序员想在应用中启动并行执行，他/她会使用线程库或专用语言来创建并管理多个线程。在 CUDA 中，每个线程的执行同样也是串行的。CUDA 程序通过调用核函数来启动并行执行，这会促使底层的运行时机制启动一个线程网格，并行处理数据的不同部分。

2.3 向量加法核函数

我们使用向量加法来演示 CUDA C 程序的结构。向量加法可以说是最简单的一种数据并行计算——相当于串行编程中的“Hello World”。在展示向量加法的核函数代码之前，先回顾一下传统的向量加法（主机代码）函数是如何工作的，会很有帮助。图 2.4 显示了一个由 main 函数和一个向量加法函数组成的简单传统 C 程序。在本书的所有示例中，只要需要区分主机数据和设备数据，我们就会给主机使用的变量名加上“_h”后缀，给设备使用的变量名加上“_d”后缀，以提醒自己这些变量的用途。由于图 2.4 中只有主机代码，所以我们只看到以“_h”为后缀的变量。

通过语句 P=&V 把 V 的地址赋给 P，我们让 P“指向”V。此时 *P 成为 V 的同义词。例如，U=*P 会把 V 的值赋给 U；再如，*P=3 会把 V 的值改为 3。

假设要相加的向量存储在数组 A 和 B 中，这两个数组在 main 程序中分配并初始化。输出向量存放在数组 C 中，它同样在 main 程序中分配。为简洁起见，我们不展示 A、B 和 C 在 main 函数中是如何分配或初始化的。这些数组的指针与包含向量长度的变量 N 一起传给 vecAdd 函数。请注意，vecAdd 函数的形参都以“_h”为后缀，以强调它们供主机使用。这一命名约定在接下来引入设备代码时会很有帮助。

图 2.4 中的 vecAdd 函数使用 for 循环遍历向量元素。在第 i 次迭代中，输出元素 C_h[i]接收 A_h[i]与 B_h[i]之和。向量长度参数 n 用于控制循环，使迭代次数与向量长度一致。该函数通过指针 A_h、B_h 和 C_h 分别读取 A 与 B 的元素，并写入 C 的元素。当 vecAdd 函数返回后，main 函数中其后的语句就可以访问 C 的新内容。

并行执行向量加法的一种直接做法是修改 vecAdd 函数，把它的计算搬到设备上。修改后的 vecAdd 函数的结构如图 2.5 所示。函数的第一部分在设备（GPU）内存中分配空间，以存放 A、B 和 C 三个向量的副本，并把 A 和 B 向量从主机内存复制到设备内存。第二部分调用真正的向量加法核函数，在设备上启动一个线程网格。第三部分把求和向量 C 从设备内存复制回主机内存，并从设备内存中释放这三个数组。

请注意，修订后的 vecAdd 函数本质上是一个外包代理：它把输入数据送到设备上，在设备上激活计算，再从设备取回结果。这个代理以这样的方式行事，使 main 程序甚至无需知道向量加法现在其实是在设备上完成的。在实践中，这种“透明”的外包模型可能非常低效，因为要来回复制大量数据。人们通常会把大型、重要的数据结构留在设备上，直接从主机代码调用作用在这些结构上的设备函数。不过，眼下我们仍将使用这种简化的透明模型来介绍 CUDA C 程序的基本结构。修订版函数的细节以及核函数的编写方法，将是本章剩余部分的主题。

2.4 设备全局内存与数据传输

在当前的 CUDA 系统中，设备通常是自带动态随机存取存储器的硬件卡，这种存储器称为设备全局内存，或简称为全局内存。例如，NVIDIA Volta V100 自带 16GB 或 32GB 的全局内存。把它称为“全局”内存，是为了与程序员同样可以访问的其他类型的设备内存相区别。CUDA 内存模型以及不同类型的设备内存的细节将在第 5 章（内存体系结构与数据局部性）中讨论。

对于向量加法核函数，在调用核函数之前，程序员需要在设备全局内存中分配空间，并把数据从主机内存传输到设备全局内存中分配好的空间。这对应图 2.5 中的第 1 部分。类似地，在设备执行完毕之后，程序员需要把结果数据从设备全局内存传回主机内存，并释放设备全局内存中不再需要的已分配空间。这对应图 2.5 中的第 3 部分。CUDA 运行时系统（通常在主机上运行）提供应用程序编程接口（API）函数，代表程序员执行这些操作。从现在起，为简洁起见，我们将把“数据从主机传输到设备”作为“数据从主机内存复制到设备全局内存”的简称。反方向同样如此。

在图 2.5 中，vecAdd 函数的第 1 部分和第 3 部分需要使用 CUDA API 函数：为 A、B 和 C 分配设备全局内存；把 A 和 B 从主机传输到设备；在向量加法完成后把 C 从设备传输到主机；并释放 A、B 和 C 的设备全局内存。我们先讲解内存分配和释放函数。

图 2.6 显示了用于分配和释放设备全局内存的两个 API 函数。cudaMalloc 函数可以从主机代码中调用，为一个对象分配一块设备全局内存。读者应当注意到 cudaMalloc 与标准 C 运行时库中的 malloc 函数惊人地相似。这是有意为之：CUDA C 就是只做了最小扩展的 C。CUDA C 使用标准 C 运行时库的 malloc 函数来管理主机内存 2，并把 cudaMalloc 作为 C 运行时库的扩展加入。通过让接口尽可能贴近原有的 C 运行时库，CUDA C 把 C 程序员重新学习这些扩展用法所需的时间降到了最低。

cudaMalloc 函数的第一个参数是一个指针变量的地址，该指针变量将被设置指向所分配的对象。这个指针变量的地址应强制转换为 (void **)，因为该函数期望接收一个通用指针；内存分配函数是通用的，不限于任何特定类型的对象。3 这一参数使 cudaMalloc 函数能够把所分配内存的地址写入传入的指针变量，而无论其类型如何。4 调用核函数的主机代码会把这个指针值传给需要访问该内存对象的核函数。cudaMalloc 函数的第二个参数给出要分配的数据的大小，以字节为单位。第二个参数的用法与 C 的 malloc 函数的 size 参数一致。

我们现在用下面这个简单的代码示例来说明 cudaMalloc 和 cudaFree 的用法：

float *A_d
int size=n*sizeof(float);
cudaMalloc((void**)&A_d, size);
…

cudaFree(A_d);

这是图 2.5 中示例的延续。为了清晰起见，我们给指针变量加上“_d”后缀，表示它指向设备全局内存中的对象。传给 cudaMalloc 的第一个参数是指针 A_d 的地址（即 &A_d），并转换为 void 指针。当 cudaMalloc 返回时，A_d 将指向为向量 A 分配的设备全局内存区域。传给 cudaMalloc 的第二个参数是要分配的区域的大小。由于 size 以字节为单位，程序员在确定 size 的取值时，需要把数组的元素个数换算成字节数。例如，为一个包含 n 个单精度浮点元素的数组分配空间时，size 的值等于 n 乘以单精度浮点数的大小，在今天的计算机中也就是 4 字节。因此 size 的值将是 n*4。计算完成后，以指针 A_d 为实参调用 cudaFree，从设备全局内存中释放向量 A 的存储空间。请注意，cudaFree 不需要改变 A_d 的值；它只需要利用 A_d 的值把所分配的内存归还给可用内存池。因此，作为实参传入的只是 A_d 的值，而不是它的地址。

A_d、B_d 和 C_d 中的地址指向设备全局内存中的位置。这些地址不应当在主机代码中解引用，而应当用于调用 API 函数和核函数。在主机代码中对设备全局内存指针进行解引用可能会引发异常或其他类型的运行时错误。

读者应当为图 2.5 中 vecAdd 示例的第 1 部分补充类似的内容：声明 B_d 和 C_d 指针变量，以及与之对应的 cudaMalloc 调用。此外，图 2.5 中的第 3 部分可以通过对 B_d 和 C_d 的 cudaFree 调用来完成。

一旦主机代码在设备全局内存中为数据对象分配好了空间，就可以请求把数据从主机传输到设备。这通过调用某个 CUDA API 函数来实现。图 2.7 显示了这样一个 API 函数：cudaMemcpy。cudaMemcpy 函数接受四个参数。第一个参数是指向复制目标位置的指针，第二个参数指向源位置，第三个参数指定要复制的字节数，第四个参数指明复制涉及的存储器类型：从主机到主机、从主机到设备、从设备到主机，以及从设备到设备。例如，这个内存拷贝函数可以用于把数据从设备全局内存中的一个位置复制到设备全局内存中的另一个位置。

vecAdd 函数调用 cudaMemcpy 函数，在相加之前把 A_h 和 B_h 向量从主机内存复制到设备内存中的 A_d 和 B_d，并在相加完成之后把 C_d 向量从设备内存复制回主机内存中的 C_h。假设 A_h、B_h、A_d、B_d 以及 size 的值已经按照前面讨论的方式设置好，下面展示三个 cudaMemcpy 调用。两个符号常量 cudaMemcpyHostToDevice 和 cudaMemcpyDeviceToHost 是 CUDA 编程环境中已识别、预定义的常量。请注意，通过恰当地安排源指针和目标指针的顺序，并使用与传输类型对应的常量，同一个函数可以用于双向传输数据。

cudaMemcpy(B_d, B_h, size, cudaMemcpyHostToDevice);

一般来说，程序对错误进行检查和处理是很重要的。CUDA API 函数在处理请求后会返回标志，指示是否发生了错误。大多数错误是由调用中使用了不当的实参值造成的。

为简洁起见，我们在示例中不展示错误检查代码。例如，图 2.9 展示了对 cudaMalloc 的一次调用：

在实践中，我们应该在调用前后加上检测错误条件并打印错误信息的代码，让用户能够知道发生了错误。这种检查代码的一个简单版本如下：

cudaError_t  err=cudaMalloc((void**) &A_d, size);

2.5 核函数与线程

我们现在可以更详细地讨论 CUDA C 核函数以及调用这些核函数的效果了。在 CUDA C 中，核函数规定了并行阶段所有线程要执行的代码。由于所有这些线程执行的是同一份代码，CUDA C 编程是众所周知的单程序多数据（SPMD）（Atallah, 1998）并行编程风格的一个实例——这是一种在并行计算系统中很流行的编程风格。5

当程序的主机代码调用核函数时，CUDA 运行时系统会启动一个线程网格，这些线程按两级层次组织。每个网格组织为线程块的数组，为简洁起见，我们以后把线程块简称为块。网格中所有线程块的大小相同；在当前的系统中，每个线程块最多可以包含 1024 个线程。6 图 2.9 显示了一个示例，其中每个线程块由 256 个线程组成。每个线程用从一个方框引出的曲线箭头表示，方框上标有该线程在块中的索引号。

内置变量

许多编程语言都有内置变量。这些变量具有特殊的意义和用途，其值通常由运行时系统预先初始化，在程序中一般是只读的。程序员不应出于任何其他目的重新定义这些变量。

每个线程块中的线程总数由主机代码在调用核函数时指定。同一个核函数可以在主机代码的不同位置以不同的线程数来调用。对于给定的线程网格，块中的线程数可以从名为 blockDim 的内置变量中获取。blockDim 是一个结构体，包含三个无符号整数字段（x、y 和 z），帮助程序员把线程组织成一维、二维或三维数组。一维组织只使用 x 字段；二维组织使用 x 和 y 字段；三维结构则使用全部三个字段 x、y 和 z。组织线程时维度的选择通常反映数据的维度。这是合理的，因为创建线程正是为了并行处理数据，线程的组织反映数据的组织是再自然不过的事。在图 2.9 中，每个线程块都组织为一维线程数组，因为数据是一维向量。blockDim.x 变量的值表示每个块中的线程总数，在图 2.9 中为 256。一般来说，出于硬件效率的考虑，建议线程块每一维上的线程数都是 32 的倍数。我们稍后会再讨论这一点。

CUDA 核函数还可以访问另外两个内置变量（threadIdx 和 blockIdx），它们让线程能够彼此区分，并确定每个线程要处理的数据区域。threadIdx 变量给线程块中的每个线程一个唯一的坐标。在图 2.9 中，由于我们使用一维线程组织方式，只使用 threadIdx.x。每个线程的 threadIdx.x 值显示在图 2.9 中每个线程的小阴影方框里。每个线程块中的第一个线程其 threadIdx.x 变量值为 0，第二个线程为 1，第三个线程为 2，依此类推。

层次化组织

与 CUDA 线程类似，现实世界中的许多系统也是按层次组织的，美国的电话系统就是一个很好的例子。在最高层，电话系统由若干“区域”组成，每个区域对应一个地理区域。同一区域内的所有电话线路共享同一个 3 位“区号”。一个电话区域有时比一个城市还要大。例如，伊利诺伊州中部的许多县市就属于同一个电话区域，共享区号 217。在区域内部，每条电话线路有一个 7 位本地电话号码，这使得每个区域最多可以容纳约一千万个号码。

我们可以把每条电话线路看作一个 CUDA 线程，把区号看作 blockIdx 的值，把 7 位本地号码看作 threadIdx 的值。这种层次化组织让系统能够容纳非常多的电话线路，同时保留拨打同一区域内电话的“局部性”：也就是说，拨打同一区域内的电话线路时，打电话的人只需要拨本地号码。只要大部分电话都是在本区域内拨打，我们几乎不需要拨区号。如果偶尔需要拨打另一区域的电话线路，我们需要先拨 1 和区号，然后再拨本地号码。（这正是任何区域的本地号码都不能以 1 开头的原因。）CUDA 线程的层次化组织同样提供了一种形式的局部性。我们很快就会研究这种局部性。

blockIdx 变量给一个块中的所有线程一个共同的块坐标。在图 2.9 中，第一个块中的所有线程其 blockIdx.x 变量值都为 0，第二个线程块中的线程为 1，依此类推。借用电话系统的类比，我们可以把 threadIdx.x 看作本地电话号码，把 blockIdx.x 看作区号。两者结合起来，就给全国每条电话线路分配了一个唯一的电话号码。类似地，每个线程都可以把它的 threadIdx 和 blockIdx 值组合起来，在整个网格内为自己构造一个唯一的全局索引。

在图 2.9 中，唯一的全局索引 i 按 i=blockIdx.x * blockDim.x + threadIdx.x 计算。回顾一下，在我们的示例中 blockDim 为 256。块 0 中线程的 i 值范围是 0 到 255，块 1 中线程的 i 值范围是 256 到 511，块 2 中线程的 i 值范围是 512 到 767。也就是说，这三个块中线程的 i 值连续覆盖了 0 到 767。由于每个线程用 i 访问 A、B 和 C，这些线程就覆盖了原循环的前 768 次迭代。通过启动包含更多线程块的网格，可以处理更大的向量；通过启动包含 n 个或更多线程的网格，可以处理长度为 n 的向量。

图 2.10 展示了用于向量加法的核函数。请注意，在核函数中我们不使用“_h”和“_d”约定，因为这里不存在混淆的可能；在我们的示例中也访问不到主机内存。核函数的语法是 ANSI C，外加一些值得注意的扩展。首先，在 vecAddKernel 函数的声明前面有一个 CUDA C 特有的关键字“__global__”。这个关键字表示该函数是一个核函数，可以被调用来在设备上生成一个线程网格。

总的来说，CUDA C 为 C 语言扩展了三个可用于函数声明的限定符关键字，这些关键字的含义总结在图 2.11 中。“__global__”关键字表示所声明的函数是 CUDA C 核函数。请注意，“global”这个词的两侧各有两个下划线字符。这种核函数在设备上执行，可以从主机调用。在支持动态并行的 CUDA 系统中，它也可以从设备调用，我们将在第 21 章（CUDA 动态并行）中看到这一点。它的重要特征是：调用这样的核函数会在设备上启动一个新的线程网格。

“__device__”关键字表示所声明的函数是一个 CUDA 设备函数。设备函数在 CUDA 设备上执行，只能从核函数或其他设备函数调用。设备函数由调用它的设备线程执行，不会导致任何新的设备线程被启动。7

“__host__”关键字表示所声明的函数是一个 CUDA 主机函数。主机函数就是传统 C 函数，在主机上执行，只能从其他主机函数调用。默认情况下，CUDA 程序中的所有函数只要声明中没有包含任何 CUDA 关键字，就都是主机函数。这很合理，因为许多 CUDA 应用是从仅使用 CPU 的执行环境移植过来的。在移植过程中，程序员会添加核函数和设备函数，原有的函数仍然是主机函数。让所有函数默认成为主机函数，免去了程序员修改所有原有函数声明的繁琐工作。

请注意，在函数声明中可以同时使用“__host__”和“__device__”。这种组合告诉编译系统为同一个函数生成两个版本的目标代码：一个在主机上执行，只能从主机函数调用；另一个在设备上执行，只能从设备函数或核函数调用。这支持了一种常见的使用场景——同一份函数源代码可以重新编译生成设备版本。许多用户库函数很可能属于这一类。

图 2.10 中第二个值得注意的 C 扩展是内置变量“threadIdx”、“blockIdx”和“blockDim”。回顾一下，所有线程都执行相同的核函数代码，因此需要有办法让它们彼此区分，并把每个线程引导到数据的特定部分。这些内置变量正是线程访问硬件寄存器的途径，这些寄存器向线程提供标识性的坐标。不同线程在其 threadIdx.x、blockIdx.x 和 blockDim.x 变量中会看到不同的值。为了便于阅读，在后面的讨论中我们有时会把一个线程表示为 threadblockIdx.x,threadIdx.x。

图 2.10 中有一个自动（局部）变量 i。在 CUDA 核函数中，自动变量对每个线程是私有的。也就是说，每个线程都会生成一个 i 的副本。如果网格以 10,000 个线程启动，就会有 10,000 个 i，每个线程一个。线程赋给其 i 变量的值对其他线程不可见。我们将在第 5 章（内存体系结构与数据局部性）中更详细地讨论这些自动变量。

把图 2.4 和图 2.10 稍作比较，就能对 CUDA 核函数得出一个重要的认识。图 2.10 中的核函数没有与图 2.4 中那个循环相对应的循环。读者应该会问：循环到哪里去了？答案是：循环现在被线程网格取代了，整个网格就相当于原来的循环。网格中的每个线程对应原循环的一次迭代。这种形式有时被称为循环级并行——原串行代码的各次迭代由线程并行执行。

请注意，图 2.10 中的 addVecKernel 里有一条 if (i<n) 语句。这是因为并非所有向量长度都能表示成线程块大小的整数倍。例如，假设向量长度为 100。最小的高效线程块维数为 32。假设我们把线程块大小选为 32，那么需要启动 4 个线程块才能处理全部 100 个向量元素。然而，4 个线程块会有 128 个线程。我们需要禁用线程块 3 中的最后 28 个线程，不让它们执行原程序预期之外的工作。由于所有线程都要执行同一份代码，所有线程都会把自己的 i 值与 n（即 100）比较。有了 if (i<n) 语句，前 100 个线程将执行加法，而最后 28 个线程不会。这使核函数可以被调用来处理任意长度的向量。

2.6 调用核函数

实现了核函数之后，剩下的步骤就是从主机代码调用该函数来启动网格，如图 2.12 所示。主机代码调用核函数时，通过执行配置参数来设置网格和线程块的维度。配置参数放在传统 C 函数实参之前的一对“<<<”与“>>>”之间。第一个配置参数给出网格中的线程块数，第二个指定每个块中的线程数。在这个例子中，每个块有 256 个线程。为了确保网格中的线程数足以覆盖全部向量元素，我们需要把网格中的线程块数设置为所需线程数（本例中为 n）除以线程块大小（本例中为 256）后的向上取整除法结果（即把商向上舍入到紧邻的更高整数）。实现向上取整除法有很多方法。一种方法是对 n/256.0 应用 C 的向上取整函数。使用浮点值 256.0 可以保证除法产生浮点值，使向上取整函数能够正确地向上舍入。例如，如果我们想要 1000 个线程，就启动 ceil(1000/256.0)=4 个线程块。这样一来，该语句会启动 4×256=1024 个线程。借助核函数中如图 2.10 所示的 if (i < n) 语句，前 1000 个线程将对 1000 个向量元素执行加法，其余 24 个线程不会执行。

图 2.13 展示了 vecAdd 函数中最终的主机代码。这段源代码补全了图 2.5 中的骨架。图 2.12 和图 2.13 合起来说明了一个由主机代码和设备核函数组成的简单 CUDA 程序。这段代码硬性规定使用每个 256 个线程的线程块。8 不过，所用线程块的数目取决于向量的长度（n）。如果 n 为 750，将使用 3 个线程块；如果 n 为 4000，将使用 16 个线程块；如果 n 为 2,000,000，将使用 7813 个线程块。请注意，所有这些线程块处理的是向量的不同部分，它们可以以任意顺序执行，程序员不得对执行顺序做任何假设。执行资源较少的小型 GPU 可能只并行执行其中的一两个线程块，而较大的 GPU 可能并行执行 64 或 128 个线程块。这使 CUDA 核函数的执行速度随硬件而具有可扩展性：也就是说，同一份代码在小型 GPU 上运行较慢，在较大的 GPU 上运行较快。我们将在第 4 章（计算体系结构与调度）中再讨论这一点。

有必要再次指出，这里使用向量加法只是因为它简单。在实践中，分配设备内存、输入数据传输（从主机到设备）、输出数据传输（从设备到主机）以及释放设备内存所带来的开销，很可能使最终代码比图 2.4 中原来的串行代码更慢。这是因为核函数完成的计算量相对于处理或传输的数据量来说很小——两个浮点输入操作数和一个浮点输出操作数只做一次加法。真实应用中的核函数相对于处理的数据量通常需要多得多的计算，因此额外的开销是值得的。真实应用还倾向于在多次核函数调用之间把数据保留在设备内存中，从而分摊这些开销。我们后面会介绍几个这样的应用示例。

2.7 编译

我们已经看到，实现 CUDA C 核函数需要使用各种不属于 C 的扩展。一旦代码中使用了这些扩展，传统的 C 编译器就不再接受它了。代码需要用能够识别并理解这些扩展的编译器来编译，例如 NVCC（NVIDIA C 编译器）。如图 2.14 顶部所示，NVCC 编译器处理 CUDA C 程序时，利用 CUDA 关键字把主机代码和设备代码分开。主机代码是纯粹的 ANSI C 代码，由主机上标准的 C/C++ 编译器编译，并作为传统的 CPU 进程运行。设备代码用指定 CUDA 核函数及其相关辅助函数和数据结构的 CUDA 关键字标记，由 NVCC 编译成称为 PTX 文件的虚拟二进制文件。这些 PTX 文件再由 NVCC 的运行时组件进一步编译为真正的目标文件，并在支持 CUDA 的 GPU 设备上执行。

2.8 小结

本章快速而简化地概述了 CUDA C 编程模型。CUDA C 扩展了 C 语言以支持并行计算。本章我们讨论了这些扩展中必不可少的一个部分。为了方便读者，我们把本章讨论过的扩展总结如下：

2.8.1 函数声明

CUDA C 扩展了 C 的函数声明语法，以支持异构并行计算。这些扩展总结在图 2.12 中。使用“__global__”、“__device__”或“__host__”中的任何一个，CUDA C 程序员就可以指示编译器生成核函数、设备函数或主机函数。所有不包含这些关键字的函数声明都默认为主机函数。如果函数声明中同时使用了“__host__”和“_device__”，编译器会生成该函数的两个版本，一个用于设备，一个用于主机。如果函数声明不包含任何 CUDA C 扩展关键字，该函数默认为主机函数。

2.8.2 核函数调用与网格启动

CUDA C 通过由 <<< 和 >>> 括起的核函数执行配置参数扩展了 C 的函数调用语法。这些执行配置参数只在调用核函数以启动网格时使用。我们讨论了用于定义网格维度和每个线程块维度的执行配置参数。关于核函数启动扩展以及其他类型的执行配置参数的更多细节，读者应参阅 CUDA 编程指南（NVIDIA, 2021）。

2.8.3 内置（预定义）变量

CUDA 核函数可以访问一组内置的、预定义的只读变量，它们让每个线程能够与其他线程区分开来，并确定要处理的数据区域。本章我们讨论了 threadIdx、blockDim 和 blockIdx 变量。在第 3 章（多维网格与数据）中，我们将更详细地讨论这些变量的用法。

2.8.4 运行时应用程序编程接口

CUDA 支持一组为 CUDA C 程序提供服务的 API 函数。本章我们讨论的服务包括 cudaMalloc、cudaFree 和 cudaMemcpy 函数。主机代码调用这些函数，分别代表调用程序分配设备全局内存、释放设备全局内存，以及在主机与设备之间传输数据。其他 CUDA API 函数请读者参阅 CUDA C 编程指南。

本章的目标是介绍 CUDA C 的核心概念，以及编写简单 CUDA C 程序所需的 CUDA 对 C 的基本扩展。本章绝不是对所有 CUDA 特性的全面介绍，其中一些特性会在本书其余部分介绍。不过，我们的重点是这些特性所支持的关键并行计算概念。我们只会引入代码示例中演示并行编程技术所需要的 CUDA C 特性。总的来说，我们鼓励读者随时查阅 CUDA C 编程指南，以了解 CUDA C 特性的更多细节。
