到目前为止，我们一直专注于使用一个主机和一个设备编写异构计算系统程序。在高性能计算（HPC）中，应用程序需要计算节点集群的聚合计算能力。如今许多 HPC 集群的每个节点都有一个或多个主机和一个或多个设备。历史上，这些集群主要使用消息传递接口（MPI）来编程。本章我们将介绍 MPI/CUDA 联合编程。我们只介绍程序员在集群环境中将异构应用扩展到多个节点所需理解的 MPI 概念。特别是，我们将重点介绍在将 CUDA 核函数扩展到多个节点的背景下，域划分、点对点通信和集合通信。

20.1 背景

尽管在 2009 年之前几乎没有顶级超级计算机使用 GPU，但对更高能效的需求促使近年来 GPU 被快速采用。如今世界上许多顶级超级计算机在每个节点中同时使用 CPU 和 GPU。这一方法的有效性已通过它们在 Green500 榜单上的高排名得到验证，而该榜单正反映了它们的高能效。

当今计算集群的主导编程接口是 MPI（Gropp et al., 1999），它是一组用于计算集群中各进程之间通信的 API 函数。MPI 采用分布式内存模型，进程之间通过相互发送消息来交换信息。当应用程序使用 API 通信函数时，它无需处理互连网络的细节。MPI 实现允许进程使用逻辑编号相互寻址，这与电话系统中使用电话号码的方式非常相似：电话用户可以用电话号码互相拨号，而无需确切知道被叫者身在何处以及呼叫是如何被路由的。

在典型的 MPI 应用中，数据和任务在进程之间划分。如图 20.1 所示，每个节点可以包含一个或多个进程，图中以节点内的云朵表示。随着这些进程的运行，它们可能彼此需要对方的数据。这种需求通过发送和接收消息来满足。在某些情况下，进程在协作完成大型任务时，还需要彼此同步并产生集合结果，这通过集合通信 API 函数来完成。

20.2 一个运行示例

作为运行示例，我们将使用在第 8 章“模板”中介绍过的三维（3D）模板计算。我们假设该计算基于有限差分法计算热传递，用于求解描述热传递物理规律的偏微分方程。特别是，我们将使用雅可比迭代法：在每一次迭代或时间步中，网格点的值被计算为邻居（北、东、南、西、上、下）的加权和与其上一时间步自身值的和。为获得较高的数值稳定性，在计算一个网格点时还会使用每个方向上的多个间接邻居。正如我们在第 8 章“模板”中所讨论的，这是一种高阶模板计算。就本章而言，我们假设每个方向使用四个点。

如图 20.2 所示，计算一个网格点在下一个时间步的值总共需要 24 个邻居点。网格中的每个点都有 x、y 和 z 坐标。对于一个坐标值为 x = i、y = j、z = k，即（i，j，k）的网格点，其 24 个邻居是（i − 4，j，k）、（i − 3，j，k）、（i − 2，j，k）、（i − 1，j，k）、（i + 1，j，k）、（i + 2，j，k）、（i + 3，j，k）、（i + 4，j，k）、（i，j − 4，k）、（i，j − 3，k）、（i，j − 2，k）、（i，j − 1，k）、（i，j + 1，k）、（i，j + 2，k）、（i，j + 3，k）、（i，j + 4，k）、（i，j，k − 4）、（i，j，k − 3）、（i，j，k − 2）、（i，j，k − 1）、（i，j，k + 1）、（i，j，k + 2）、（i，j，k + 3）和（i，j，k + 4）。由于每个网格点下一步的数据值是基于 25 个点（24 个邻居和它自身）的当前数据值计算得出的，因此这是一个 25 点模板计算。

我们假设系统被建模为结构化网格，在每个方向上网格点之间的间距是恒定的。这使得我们可以使用一个 3D 数组，其中每个元素存储一个网格点的状态，正如我们在第 8 章“模板”中讨论的那样。每个维度上相邻元素之间的物理距离可以用一个网格间距变量来表示。请注意，这种网格数据结构与第 18 章“静电势图”中静电势计算所用的数据结构类似。图 20.3 展示了一个表示矩形通风管道的 3D 数组，其中 x 和 y 维度构成管道的横截面，z 维度是热量沿管道流动的方向。

我们假设数据按行主序布局放置在内存空间中，其中 x 是最低维，y 次之，z 是最高维。也就是说，所有 y = 0 且 z = 0 的元素将按照它们的 x 坐标存放在连续的内存位置中。图 20.4 展示了网格数据布局的一个小示例。这个小示例中网格只有 16 个数据元素：x 维两个、y 维两个、z 维四个。x 维的两个元素在 y = 0 且 z = 0 时最先放入内存，随后是 y = 1 且 z = 0 的所有元素，再下一组是 y = 0 且 z = 1 的元素。

使用计算集群时，常见的做法是将输入数据划分为若干分区（称为域分区），并将每个分区分配给集群中的一个节点。在图 20.3 中，我们展示了 3D 数组被划分为四个域分区：D0、D1、D2 和 D3。每个分区将被分配给一个 MPI 计算进程。

域分区可以用图 20.4 进一步说明。第一个区段（即切片）包含四个元素（z = 0），位于第一个分区；第二个区段（z = 1）位于第二个分区；第三个区段（z = 2）位于第三个分区；第四个区段（z = 3）位于第四个分区。这显然是一个玩具示例。在真实应用中，每个维度通常有数百甚至数千个元素。在本章剩余部分，记住以下事实很有用：一个 z 切片中的所有元素位于连续的内存位置中。

20.3 消息传递接口基础

与 CUDA 一样，MPI 程序基于单程序多数据（SPMD）并行编程模型。所有 MPI 进程执行相同的程序。MPI 系统提供一组 API 函数来建立通信系统，使进程能够相互通信。图 20.5 展示了为 MPI 应用程序建立和拆除通信系统的五个基本 MPI 函数。

我们将使用一个简单的 MPI 程序（如图 20.6 所示）来说明这些 API 函数的用法。要在集群中启动一个 MPI 应用程序，用户需要将程序的可执行文件提供给集群登录节点上的 mpirun 命令或 mpiexec 命令。每个进程首先通过调用 MPI_Init()（第 05 行）来初始化 MPI 运行时。这会为运行该应用程序的所有进程初始化通信系统。MPI 运行时初始化完成后，每个进程调用两个函数来准备通信。第一个函数是 MPI_Comm_rank()（第 06 行），它向每个调用进程返回一个唯一编号，称为该进程的 MPI 进程号或进程 ID。进程收到的编号从 0 到进程数减 1。一个进程的 MPI 进程号类似于 CUDA 线程的表达式 blockIdx.x*blockDim.x+threadIdx.x。它唯一标识一次通信中的进程，也相当于电话系统中的电话号码。主要的区别是，MPI 进程号是一维的。

图 20.6 第 06 行中的 MPI_Comm_rank()函数接受两个参数。第一个参数是 MPI 内置类型 MPI_Comm，它指定请求的作用域，即由 MIP_Comm 变量标识的进程组。每个 MPI_comm 类型的变量通常被称为通信域。MPI_Comm 和其他 MPI 内置类型在“mpi.h”头文件（第 01 行）中定义，所有使用 MPI 的 C 程序文件都应包含该头文件。MPI 应用程序可以创建一个或多个通信域，每个通信域是出于通信目的的一组 MPI 进程。MPI_Comm_rank()为通信域中的每个进程分配一个唯一 ID。在图 20.6 中，传入的参数值是 MPI_COMM_WORLD，它被用作默认值，表示该通信域包含运行该应用程序的所有 MPI 进程。1

MPI_Comm_rank()函数的第二个参数是一个指向整型变量的指针，函数会将返回的进程号值存入该变量。在图 20.6 中，为此声明了一个变量 pid。在 MPI_Comm_rank()返回之后，pid 变量将包含调用进程的唯一 ID。

第二个 API 函数是 MPI_Comm_size()（第 07 行），它返回通信域中运行的 MPI 进程总数。MPI_Comm_size()函数接受两个参数。第一个参数是 MPI_Comm 类型，给出请求的作用域。在图 20.6 中，传入的参数值是 MPI_COMM_WORLD，这意味着 MPI_Comm_size()的作用域是应用程序中的所有进程。由于作用域覆盖所有 MPI 进程，返回值就是运行该应用程序的 MPI 进程总数。该值由用户在通过 mpirun 命令或 mpiexec 命令执行应用程序时配置。不过，用户可能没有请求足够数量的进程，而且系统也可能无法创建用户请求的全部进程。因此，MPI 应用程序检查实际运行的进程数量是一个好习惯。

第二个参数是一个指向整型变量的指针，MPI_Comm_size()函数会将返回值存入该变量。在图 20.6 中，为此声明了一个变量 np。函数返回后，变量 np 包含运行该应用程序的 MPI 进程数。在图 20.6 中，我们假设该应用程序至少需要 3 个 MPI 进程，因此它检查进程数是否至少为 3（第 08 行）。如果不是，它就调用 MPI_Comm_abort()函数终止通信连接，并以错误标志值 1 返回（第 10 行）。

图 20.6 还展示了报告错误或其他事务的常见模式。虽然存在多个 MPI 进程，但我们只需要报告一次错误。应用程序代码指定由 pid = 0 的进程来执行报告（第 09 行）。这与 CUDA 核函数中的模式类似：某些任务只需由线程块中的一个线程来完成。

如图 20.5 所示，MPI_Comm_abort()函数接受两个参数（第 10 行）。第一个参数设置请求的作用域。在图 20.6 中，作用域被设置为 MPI_COMM_WORLD，即运行该应用程序的所有 MPI 进程。第二个参数是一个代码，表示导致中止的错误类型。任何非 0 的数字都表示发生了错误。

如果进程数满足要求，应用程序程序就继续进行计算。在图 20.6 中，应用程序使用 np − 1 个进程（pid 从 0 到 np − 2）执行计算（第 12–13 行），并使用一个进程（pid 为 np − 1 的最后一个进程）为其他进程执行 I/O 服务（第 14–15 行）。我们将执行 I/O 服务的进程称为数据服务器，将执行计算的进程称为计算进程。在图 20.6 中，如果一个进程的 pid 在 0 到 np − 2 范围内，它就是计算进程，并调用 compute_process()函数（第 13 行）。如果进程的 pid 是 np − 1，它就是数据服务器，并调用 data_server()函数（第 15 行）。这与线程根据其线程 ID 执行不同操作的模式类似。

应用程序完成计算后，通过调用 MPI_Finalize()通知 MPI 运行时，该调用释放分配给应用程序的所有 MPI 通信资源（第 16 行）。随后应用程序可以以返回值 0 退出，表示没有发生错误（第 17 行）。

20.4 消息传递接口点对点通信

MPI 支持两大类型的通信。第一种是点对点类型，涉及一个源进程和一个目标进程。源进程调用 MPI_Send()函数，目标进程调用 MPI_Recv()函数。这类似于电话系统中主叫方拨号、被叫方接听电话的情形。

图 20.7 展示了 MPI_Send()函数的语法。第一个参数是指向内存区域起始位置的指针，待发送的数据位于该区域中。第二个参数是一个整数，给出要发送的数据元素个数。第三个参数是 MPI 内置类型 MPI_Datatype，它指明就 MPI 库实现而言每个待发送数据元素的类型。MPI_Datatype 类型的变量或参数可以持有的值在 mpi.h 中定义，包括 MPI_DOUBLE（双精度浮点数）、MPI_FLOAT（单精度浮点数）、MPI_INT（整数）和 MPI_CHAR（字符）。这些类型的确切大小取决于主机处理器中相应 C 类型的大小。有关 MPI 类型的更复杂用法，请参阅 MPI 参考手册（Gropp et al., 1999）。

MPI_Send()的第四个参数是一个整数，给出目标进程的 MPI 进程号。第五个参数给出一个标记（tag），可用于对同一进程发送的消息进行分类。第六个参数是一个通信域，指定目标 MPI 进程号在其中定义的作用域（上下文）。

图 20.8 展示了 MPI_Recv()函数的语法。第一个参数是指向内存中接收数据存放区域的指针。第二个参数是一个整数，给出 MPI_Recv()函数允许接收的最大元素个数。第三个参数是一个 MPI_Datatype，指明每个待接收元素的类型。第四个参数是一个整数，给出消息来源进程的进程 ID。第五个参数是一个整数，指定目标进程所期望的标记值。如果目标进程不想被限定于特定的标记值，可以使用 MPI_ANY_TAG，它表示接收方愿意接受来自源进程的任何标记值的消息。

我们首先使用数据服务器来说明点对点通信的用法。在真实应用中，数据服务器进程通常为计算进程执行数据输入和输出操作。然而，输入和输出具有太多与系统相关的复杂性。由于 I/O 不是我们讨论的重点，我们将避开集群环境中 I/O 操作的复杂性。也就是说，我们不从文件系统读取数据，而是让数据服务器用随机数初始化数据，并将其分发给计算进程。数据服务器代码的第一部分如图 20.9 所示。

数据服务器函数接受四个参数。前三个参数指定 3D 网格的大小：x 维的元素个数 dimx、y 维的元素个数 dimy 和 z 维的元素个数 dimz。第四个参数指定需要对网格中所有数据点执行的迭代次数。

在图 20.9 中，第 02 行声明了变量 np，它将保存运行该应用程序的进程数。第 03 行调用 MPI_Comm_size()，将运行该应用程序的进程数存入 np。第 04 行声明并初始化了几个辅助变量。变量 num_comp_procs 保存计算进程数。由于我们保留一个进程作为数据服务器，因此有 np − 1 个计算进程。变量 first_proc 给出第一个计算进程的进程 ID，即 0。变量 last_proc 给出最后一个计算进程的进程 ID，即 np − 2。也就是说，第 04 行将前 np − 1 个进程（0 到 np − 2）指定为计算进程，进程号最大的进程充当数据服务器。这体现了设计决策，该决策也会在计算进程代码中体现。

第 05 行声明并初始化了 num_points 变量，它给出需要处理的网格数据点总数，也就是每个维度的元素个数之积，即 dimx * dimy * dimz。第 06 行声明并初始化了 num_bytes 变量，它给出存储所有网格数据点所需的总字节数。由于每个网格数据点是一个 float，该值为 num_points * sizeof(float)。

第 07 行声明了两个指针变量：input 和 output。这两个指针将分别指向输入数据缓冲区和输出数据缓冲区。第 08 行和第 09 行为输入和输出缓冲区分配内存，并将它们的地址赋给各自的指针。第 10 行检查内存分配是否成功。如果任一内存分配失败，对应的指针将从 malloc()函数收到 NULL 指针。在这种情况下，代码会中止应用程序并报告错误（第 11–12 行）。

第 15 行和第 16 行计算应发送给每个计算进程的网格点数组元素个数。如图 20.3 所示，有两类计算进程：边界进程和内部进程。第一个进程（计算 D1 的进程 0）和最后一个进程（计算 D4 的进程 3）计算一个仅在一侧有邻居的边界分区。分配给进程 0 的分区 D1 只在右侧（D2）有邻居。分配给最后一个计算进程的分区 D4 只在左侧（D3）有邻居。我们把计算边界分区的计算进程称为边界进程。其他每个进程计算一个两侧都有邻居的内部分区。例如，进程 1 计算分区 D2，它有一个左邻居（D1）和一个右邻居（D3）。我们把计算内部分区的进程称为内部进程。

回顾一下，在雅可比迭代法中，网格点的每一个计算步骤都需要其相邻点在上一步的值。这就使得分区左右边界处的网格点需要光环单元，在图 20.3 中，这些单元以每个分区边缘处由虚线界定的切片表示。请注意，这些光环切片与第 8 章“模板”中介绍的模板模式中的光环切片类似。由于我们计算的是每个方向有四个元素的 25 点模板，每个进程需要接收四片光环单元，其中包含其分区边界网格点每一侧的所有邻居。例如，在图 20.3 中，分区 D2 需要来自 D1 的四片光环切片和来自 D3 的四片光环切片。请注意，D2 的一片光环切片就是 D1 或 D3 的一片边界切片。

回顾一下，网格点总数为 dimx*dimy*dimz。由于我们沿着 z 维划分网格，每个分区中的网格点数应为 dimx*dimy*(dimz/num_comp_procs)。回顾一下，为了计算每个分区内的值，我们在每个方向需要四片邻居切片。因此，应发送给每个内部进程的网格点数为 dimx*dimy*((dimz/num_comp_procs) + 8)。对于边界进程，只有一个邻居。与卷积的情况一样，我们假设幽灵单元使用零值，并且不需要为它们发送任何输入数据。例如，分区 D1 只需要来自右侧 D2 的四片邻居切片。因此，发送给一个边界进程的网格点数为 dimx*dimy*((dimz/num_comp_procs) + 4)。也就是说，每个进程从每一侧的邻居分区接收四片光环网格点切片。

图 20.9 的第 17 行将 send_address 指针设置为指向输入网格点数组的开头。为了向每个进程发送适当的分区，我们需要为每次 MPI_Send()在该起始地址上加上适当的偏移量。我们稍后会回到这一点。

现在我们可以完成数据服务器的代码了。第 18 行将进程 0 的分区发送给它。由于这是第一个分区，它的起始地址也就是第 17 行设置的整个网格的起始地址。进程 0 是一个边界进程，没有左邻居。因此，要发送的网格点数是 edge_num_points，即 dimx*dimy*((dimz/num_comp_procs) + 4)。第三个参数指明每个元素的类型是 MPI_FLOAT，即 C 的 float（单精度，4 字节）。第四个参数指明 first_node 的值（即 0）是目标进程的 MPI 进程号。第五个参数为 MPI 标记指定 0。这是因为我们不使用标记来区分数据服务器发送的消息。第六个参数指明用于解释消息的发送方和接收方进程号的通信域应为当前应用程序的所有 MPI 进程。

我们现在把注意力转向从数据服务器进程接收输入的计算进程。在图 20.10 中，第 03–04 行建立该进程的进程 ID 和应用程序的进程总数。第 05 行确定数据服务器是进程 np − 1。第 06–07 行计算每个内部进程应处理的网格点数和字节数。第 08–09 行计算每个光环（4 片）中的网格点数和字节数。

20.5 计算与通信重叠

执行计算步骤的一种简单方式是：每个计算进程先对整个分区执行一个计算步骤，然后与左右邻居交换光环数据，如此反复。虽然这是一个非常简单的策略，但效率不高。原因是该策略迫使系统处于两种模式之一。在第一种模式中，所有计算进程都在执行计算步骤，此时通信网络未被使用。在第二种模式中，所有计算进程都在与左右邻居交换光环数据，此时计算硬件没有得到充分利用。理想情况下，我们希望同时利用通信网络和计算硬件以获得更好的性能。这可以通过将每个计算进程的计算任务划分为两个阶段来实现，如图 20.12 所示。

在第一阶段（阶段 1），每个计算进程计算其边界切片，这些边界切片将在下一次迭代中作为光环单元被其邻居使用。我们继续假设使用四片光环数据。图 20.12 将四片光环切片显示为一个虚线透明件，将四片边界切片显示为一个彩色件。请注意，进程 i 的彩色件将在下一次通信中被复制到进程 i + 1 的虚线件中，而进程 i + 1 的彩色件将被复制到进程 i 的虚线件中。对于进程 0，第一阶段计算右侧四片边界数据。对于内部节点，它计算其边界数据左侧四片和右侧四片。对于进程 n − 2，它计算其边界数据左侧四片。这样做的理由是，这些边界切片在下次迭代中被其邻居所需要。如果先计算这些边界切片，那么计算进程在计算其余内部网格点的同时，就可以将数据传送给邻居。

在第二阶段（阶段 2），每个计算进程并行执行两项活动。第一项是将新的边界值传送给其邻居进程，做法是先将数据从设备内存复制到主机内存，然后向邻居发送 MPI 消息。正如我们稍后将讨论的，我们需要小心，确保从邻居收到的数据用于下一次迭代而不是当前迭代。第二项是计算分区中的其余数据。如果通信活动所需的时间比计算活动短，我们就能隐藏通信延迟并始终充分利用计算硬件。这通常通过在每个分区的内部部分设置足够的切片来实现，使每个计算进程能够执行足够的计算来隐藏通信。

为了支持阶段 2 中的并行活动，我们需要使用 CUDA 编程模型的两项高级特性：锁页内存分配和流。锁页内存分配要求所分配的内存不被操作系统换出页面。这是通过 cudaHostAlloc()API 调用完成的。图 20.11 的第 21–24 行为左右边界切片和左右光环切片分配了锁页内存缓冲区。左右边界切片需要从设备内存发送到左右邻居进程，这些缓冲区用作设备向其中复制数据的主机内存中转区，随后又用作 MPI_Send()向邻居进程发送时的源缓冲区。左右光环切片需要从邻居进程接收，这些缓冲区用作 MPI_Recv()的目标缓冲区的主机内存中转区，之后再将数据从其中复制到设备内存。这些缓冲区有时被称为弹跳缓冲区（bounce buffers），因为其主要作用是充当临时缓冲区，使数据可以从设备内存弹跳到远程 MPI 进程，反之亦然。

请注意，弹跳缓冲区的主机内存分配使用 cudaHostAlloc()函数，而不是标准的 malloc()函数。区别在于 cudaHostAlloc()函数分配的是锁页内存缓冲区，有时也称为锁页内存缓冲区。为了充分理解锁页内存缓冲区的概念，我们需要再多了解一些操作系统中内存管理的背景知识。

在现代计算机系统中，操作系统为应用程序管理虚拟内存空间。每个应用程序都可以访问一个很大且连续的地址空间。实际上，系统的物理内存有限，需要在所有正在运行的应用程序之间共享。这种共享通过将虚拟内存空间划分为页面，并且只将活跃使用的页面映射到物理内存中来实现。当内存需求很大时，操作系统需要将部分页面从物理内存换出到磁盘等大容量存储设备。因此，应用程序的数据在其执行期间的任何时候都可能被换出。

cudaMemcpy()的实现使用一种称为直接内存访问（DMA）设备的硬件。当调用 cudaMemcpy()函数在主机和设备内存之间进行复制时，其实现使用 DMA 操作来完成该任务。在主机内存一侧，DMA 硬件操作的是物理地址；也就是说，操作系统需要向 DMA 设备提供一个转换后的物理地址。然而，数据有可能在 DMA 操作完成之前被换出页面。数据对应的物理内存位置可能被重新分配给对应不同虚拟内存位置的其他数据。在这种情况下，DMA 操作有可能被破坏，因为其数据可能被换页活动覆盖。

解决这种数据破坏问题的一种常见方法是让 CUDA 运行时分两步执行复制操作。对于主机到设备的复制，CUDA 运行时先将源主机内存数据复制到锁页内存缓冲区中，这意味着这些内存位置被标记，换页机制不会将数据换出。然后它使用 DMA 设备将数据从锁页内存缓冲区复制到设备内存。对于设备到主机的复制，CUDA 运行时先使用 DMA 设备将数据从设备内存复制到锁页内存缓冲区，然后将数据从锁页内存缓冲区复制到目标主机内存位置。通过使用额外的锁页内存缓冲区，DMA 复制将不受任何换页活动的影响。

这种方法有两个问题。一是额外的复制给 cudaMemcpy()操作增加了延迟。二是所涉及的额外复杂性导致 cudaMemcpy()函数实现为同步的。也就是说，在 cudaMemcpy()函数完成操作并返回之前，主机程序不能继续执行。这使得所有复制操作串行化。为了支持更多并行性的快速复制，CUDA 提供了 cudaMemcpyAsync()函数。

cudaMemcpyAsync()函数要求主机内存缓冲区作为锁页内存缓冲区分配。这在图 20.11 的第 21–24 行中完成，针对的是左边界、右边界、左光环和右光环切片的主机内存缓冲区。这些缓冲区使用 cudaHostAlloc()函数分配，该函数确保分配的内存被锁定（即锁页）而不受换页活动的影响。请注意，cudaHostAlloc()函数接受三个参数。前两个与 cudaMalloc()相同。第三个指定一些用于更高级用法的选项。对于大多数基本用例，我们可以直接使用默认值 cudaHostAllocDefault。

用于计算与通信重叠的第二项 CUDA 高级特性是流，一项支持 CUDA API 函数受控并发执行的功能。流是一个有序的操作序列。当主机代码调用 cudaMemcpyAsync()函数或启动核函数时，可以将一个流指定为参数之一。通过在 cudaMemcpyAsync()调用中指定一个流，复制操作就被放入该流中。同一流中的所有操作将按照放入该流的顺序依次执行。然而，不同流中的操作可以并行执行，不受任何排序约束。

图 20.11 的第 25 行声明了两个 CUDA 内置类型 cudaStream_t 的变量。然后这些变量被用于调用 cudaStreamCreate()函数。每次调用 cudaStreamCreate()都会创建一个新流，并将该流的标识符存入其参数中。在第 26 行和第 27 行的调用之后，主机代码可以在后续的 cudaMemcpyAsync()调用和核函数调用中使用流 0 或流 1。

图 20.13 展示了计算进程代码的第 3 部分。第 28 行声明了一个 MPI 状态变量，将用于 MPI 发送和接收。第 29–30 行计算计算进程的左右邻居的进程 ID。left_neighbor 和 right_neighbor 变量将被计算进程用作与邻居发送和接收消息时的参数。对于进程 0，没有左邻居，因此第 29 行将 MPI 常量 MPI_PROC_NULL 赋给 left_neighbor 以记录这一事实。对于进程 np − 2，没有右邻居，因此第 30 行将 MPI_PROC_NULL 赋给 right_neighbor。对于所有内部进程，第 29–30 行将 pid − 1 赋给 left_neighbor，将 pid + 1 赋给 right_neighbor。

图 20.13 的第 31 行调用一个函数，将模板系数复制到 GPU 常量内存中。这里不展示其细节，因为读者应当已经熟悉常量内存。第 32–36 行设置了若干偏移量，这些偏移量将用于调用核函数和交换数据，以便计算与通信能够重叠。这些偏移量定义了图 20.13 每个阶段需要计算的网格点区域，它们也在图 20.12 中可视化。

请注意，每个设备内存中的切片总数为：四片左光环点（白色虚线）加上四片左边界点，再加上 dimx*dimy*(dimz − 8)个内部点，加上四片右边界点，再加上四片右光环点（白色虚线）。如图 20.14 所示，变量 left_stage1_offset 定义计算左边界切片所需切片的起始位置，包括 12 片数据：四片左邻居光环点、四片边界点和四片内部点。这些切片位于分区的最左侧，因此第 34 行将偏移值设置为 0。变量 right_stage2_offset 定义计算右边界切片所需切片的起始位置，同样包括 12 片：四片内部点、四片右边界点和四片右光环单元。这 12 片的起始位置可以通过从切片总数 dimz + 8 中减去 12 得出，因此第 35 行将这 12 片的起始偏移量设置为 dimx*dimy*(dimz − 4)（图 20.12）。

图 20.13 的第 37 行是 MPI 屏障同步，类似于线程块内各线程之间的 CUDA __syncthreads()。MPI 屏障强制输入参数指定的所有 MPI 进程相互等待。在所有进程都到达该点之前，任何进程都不能继续越过该点执行。我们在这里需要屏障同步的原因，是要确保所有计算节点都已收到输入数据并准备好执行计算步骤。由于它们将相互交换数据，我们希望它们几乎同时开始，这样就不会出现几个拖沓的进程在数据交换期间拖延所有其他进程的情况。MPI_Barrier()是一个集合通信函数。我们将在下一节更详细地讨论集合通信 API 函数。

第 38 行开始一个执行计算步骤的循环。每次迭代中，每个计算进程将执行图 20.12 所示两阶段过程的一个周期。第 39 行调用一个函数，在阶段 1 生成左边界点的四片。我们假设该函数将设置网格配置，并调用模板核函数，对一片网格点区域执行一个计算步骤，如第 8 章“模板”所述。call_stencil_kernel()函数接受若干参数。第一个参数是指向核函数输出数据区域的指针，第二个参数是指向输入数据区域的指针。在这两种情况下，我们都对设备内存中的输入和输出数据加上 left_stage1_offset。接下来的三个参数指定待处理网格部分的尺寸。请注意，为了正确计算四片左边界切片中的所有点，我们每侧都需要四片。第 40 行在阶段 1 中对右边界点做同样的事情。请注意，这些核函数将在流 0 中调用并按顺序执行。

第 41 行调用 call_stencil_kernel()函数，它将调用一个模板核函数，在阶段 2 生成 dimx*dimy*(dimz − 8)个内部点。请注意，这每侧还需要四片输入边界值，因此输入切片总数为 dimx*dimy*dimz。该核函数在流 1 中调用，将与第 39 行和第 40 行调用的核函数并行执行。

图 20.15 展示了计算进程代码的第 4 部分。第 42 行将四片左边界点复制到主机内存，为与左邻居进程的数据交换做准备。第 43 行将四片右边界点复制到主机内存，为与右邻居进程的数据交换做准备。两者都是流 0 中的异步复制，将等待流 0 中的两个核函数完成后才开始复制数据。第 44 行是一个同步操作，强制进程等待流 0 中的所有操作完成才能继续，从而确保左右边界点在进程进行数据交换之前已位于主机内存中。

在数据交换阶段，我们将让所有 MPI 进程把它们的边界切片发送给左邻居，也就是说，所有进程的右邻居都会向它们发送数据。因此，如果有一个 MPI 函数既能向目标发送数据又能从源接收数据，就会很方便，这可以减少 MPI 函数调用的次数。图 20.16 中的 MPI_Sendrecv()函数就是这样一个函数。它是 MPI_Send()和 MPI_Recv()的组合，因此我们不再详细说明参数的含义。

第 45 行将四片左边界点发送给左邻居，并从右邻居接收四片右光环点。第 46 行将四片右边界点发送给右邻居，并从左邻居接收四片左光环点。对于进程 0，其 left_neighbor 已在第 27 行被设置为 MPI_PROC_NULL，因此 MPI 运行时不会为进程 0 发送第 45 行的消息或接收第 46 行的消息。同样，MPI 运行时也不会为进程 np − 2 接收第 45 行的消息或发送第 46 行的消息。因此，图 20.13 第 29 行和第 30 行中的条件赋值消除了第 45 行和第 46 行中对特殊 if-then-else 语句的需求。

在 MPI 消息发送和接收完成后，第 47 行和第 48 行将新接收的光环点传输到设备内存的 d_output 缓冲区。这些复制在流 0 中执行，因此它们将与第 38 行在流 1 中启动的核函数并行执行。

第 49 行是对所有设备活动的同步操作。该调用强制进程等待所有设备活动（包括核函数和数据复制）完成。当 cudaDeviceSynchronize()函数返回时，当前计算步骤的所有 d_output 数据都已就位：来自左邻居进程的左光环数据、第 36 行启动的核函数产生的边界数据、第 38 行启动的核函数产生的内部数据、第 37 行启动的核函数产生的右边界数据，以及来自右邻居的右光环数据。

第 50 行和第 51 行交换 d_input 和 d_output 指针。这把当前计算步骤 d_ouput 数据的输出变为下一个计算步骤的 d_input 数据。然后执行进入第 35 行循环的下一次迭代，继续下一个计算步骤，直到所有计算进程完成参数 nreps 指定的计算次数。

图 20.17 展示了计算进程代码的第 5 部分，即最后一部分。第 53 行是一个屏障同步，强制所有进程相互等待，直到完成各自的计算步骤。第 54–56 行交换 d_output 和 d_input。这是因为第 50 行和第 51 行为了准备下一个计算步骤交换了 d_output 和 d_input，但对最后一个计算步骤而言这种交换是不必要的，所以我们用第 54–56 行撤销交换。第 57 行将最终输出复制到主机内存。第 58 行将输出发送给数据服务器。第 59 行等待所有进程完成。第 60–63 行在返回主程序之前释放所有资源。

图 20.18 展示了数据服务器代码的第 2 部分，即最后一部分，它接着图 20.9 继续。第 24 行是一个屏障同步，等待所有计算节点完成各自的计算步骤并发送它们的输出。这个屏障对应于计算进程第 59 行的屏障。第 26 行和第 27 行从所有计算进程接收输出数据。第 28 行将输出存储到外部存储中。最后，第 29 行和第 30 行在返回主程序之前释放资源。

20.6 消息传递接口集合通信

在上一节中，我们看到了 MPI 集合通信 API 的一个示例：MPI_Barrier。其他常用的组集合通信类型是广播（broadcast）、归约（reduce）、汇聚（gather）和分散（scatter）（Gropp et al., 1999）。屏障同步 MPI_Barrier()可能是最常用的集合通信函数。正如我们在模板示例中看到的，屏障用于确保所有 MPI 进程在开始彼此交互之前都已就绪。我们将不详细阐述其他类型的 MPI 集合通信函数，但鼓励读者自行阅读这些函数的细节。一般来说，集合通信函数由 MPI 运行时开发者和系统厂商高度优化。使用它们通常比尝试用发送和接收调用的组合来实现同样的功能能带来更好的性能，同时也更易读、更具生产力。

20.7 CUDA 感知的 MPI

现代 MPI 实现了解 CUDA 编程模型，并设计用于最小化 GPU 之间的通信延迟。目前，MVAPICH2、IBM Platform MPI 和 OpenMPI 支持 CUDA 与 MPI 之间的直接交互。

CUDA 感知的 MPI 实现能够将一个节点的 GPU 内存中的消息发送到另一个节点的 GPU 内存中。这实际上消除了发送 MPI 消息之前进行设备到主机数据传输、以及接收 MPI 消息之后进行主机到设备数据传输的需要。这有可能简化主机代码和内存数据布局。在我们的模板示例中，如果使用 CUDA 感知的 MPI 实现，我们将不再需要主机锁页内存分配和异步内存复制。

第一个简化是我们不再需要分配主机锁页内存缓冲区来将光环点传输到主机内存，以准备 MPI_Send()。这意味着我们可以安全地删除图 20.11 中的第 21–24 行。然而，我们仍然需要使用 CUDA 流和两个独立的 GPU 核函数，以便在光环元素计算完成后尽快开始跨节点通信。

第二个简化是我们不再需要在 MPI_Recv()之后将光环数据从主机异步复制到设备内存。因此，我们也可以删除图 20.15 中的第 42 行和第 43 行。由于 MPI 调用现在接受设备内存地址，我们需要修改对 MPI_SendRecv 的调用以使用这些地址。请注意，这些内存地址实际上对应于之前版本中异步内存复制的设备地址。由于 CUDA 感知的 MPI 实现将直接更新 GPU 内存的内容，我们还删除了图 20.15 中的第 47 行和第 48 行。图 20.19 展示了图 20.15 中第 45 行和第 46 行对 MPI_SendRecv 语句所做的修改，使它们直接从设备内存读取和写入。

除了在使用 MPI_SendRecv()进行光环交换时删除数据传输之外，还可以通过直接从 GPU 内存接收/发送输入/输出来删除最初和最终的内存复制。

20.8 小结

在本章中，我们介绍了面向具有异构计算节点的 HPC 集群的 CUDA/MPI 联合编程的基本模式。MPI 应用程序中的所有进程运行相同的程序。然而，每个进程可以遵循不同的控制流和函数调用路径来专门化自己的角色，正如我们示例中的数据服务器和计算进程所示。我们还使用模板模式展示了计算进程如何交换数据。我们介绍了使用 CUDA 流和异步数据传输来实现计算与通信的重叠。我们还展示了如何使用 MPI 屏障来确保所有进程都已准备好相互交换数据。最后，我们简要概述了使用 CUDA 感知的 MPI 来简化设备内存中数据的交换。我们想指出，虽然 MPI 是一个非常不同的编程系统，但我们在本章中介绍的所有主要 MPI 概念，即单程序多数据（SPMD）、MPI 进程号和屏障，在 CUDA 编程模型中都有对应物。这印证了我们的信念：通过用一种模型把并行编程教好，我们的学生可以快速轻松地掌握其他编程模型。我们鼓励读者在本章提供的基础上继续学习更高级的 MPI 特性和其他重要的模式。
