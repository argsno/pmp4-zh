Chapter 5

内存体系结构与数据局部性

摘要

本章介绍 GPU 的片上内存体系结构、访存受限应用的概念，以及改善访存受限应用性能的技术。本章以矩阵乘法为例，说明减少全局内存访问次数的机会；接着介绍分块技术，该技术利用屏障同步协调各线程的执行时机，从而改善数据局部性并减少全局内存访问。不过，分块技术会在边界检查方面引入额外的复杂性。本章继续以矩阵乘法为例，说明一个分块核函数要适用于任意规模的矩阵，需要额外进行哪些边界检查。本章最后概述共享内存和寄存器的使用会如何影响每个流式多处理器（SM）所能容纳的线程块数量。

到目前为止，我们已经学会了如何编写 CUDA 核函数，以及如何配置和协调由大量线程执行的核函数。我们也已经了解了当前 GPU 硬件的计算体系结构，以及线程如何被调度到这些硬件上执行。本章将聚焦于 GPU 的片上内存体系结构，开始研究如何组织和放置数据，以便大量线程能够高效地访问。我们迄今研究过的 CUDA 核函数，很可能只能发挥底层硬件潜在速度的一小部分。性能之所以如此低下，是因为全局内存通常由片外 DRAM 实现，往往具有较长的访问延迟（数百个时钟周期）和有限的访问带宽。虽然执行时有大量线程可用，理论上可以容忍较长的内存访问延迟，但很容易出现这样的情形：全局内存访问路径上的流量拥塞使得除极少数线程以外的所有线程都无法取得进展，从而让流式多处理器（SM）中的部分核心处于空闲状态。为了规避这种拥塞，GPU 提供了一系列额外的片上内存资源来访问数据，可以消除与全局内存之间的大部分往来流量。本章将研究如何使用不同类型的内存来提升 CUDA 核函数的执行性能。

5.1 内存访问效率的重要性

我们可以通过计算图 3.11 中矩阵乘法核函数代码中执行次数最多的部分（该部分在图 5.1 中有所复现）的预期性能水平，来说明内存访问效率的影响。就执行时间而言，核函数最重要的部分，是计算 M 的一行与 N 的一列的点积的 for 循环。

在循环的每次迭代中，都要执行两次全局内存访问，对应一次浮点乘法和一次浮点加法。这两次全局内存访问分别从 M 数组和 N 数组中取出元素。浮点乘法运算把这两个元素相乘，浮点加法运算则把乘积累加到 Pvalue 中。因此，浮点运算次数（FLOP）与从全局内存访问的字节数（B）之比为 2 FLOP 对 8 B，即 0.25 FLOP/B。我们把这一比值称为计算访存比，其定义为：程序某一区域内每从全局内存访问一个字节所执行的 FLOP 数。在文献中，这一比值有时也被称为算术强度或计算强度。

计算访存比对 CUDA 核函数的性能具有重大影响。例如，Ampere A100 GPU 的峰值全局内存带宽为 1555 GB/秒。由于矩阵乘法核函数每字节执行 0.25 OP，全局内存带宽把核函数所能执行的单精度浮点运算吞吐量限制为每秒 389 十亿次浮点运算（GFLOPS），即 1555 GB/秒乘以 0.25 FLOP/B。然而，389 GFLOPS 仅占 A100 GPU 峰值单精度运算吞吐量（19500 GFLOPS）的 2%。A100 还配有称为张量核心的专用单元，可用于加速矩阵乘法运算。如果考虑 A100 张量核心 156000 GFLOPS 的峰值单精度浮点吞吐量，389 GFLOPS 仅占其峰值的 0.25%。因此，矩阵乘法核函数的执行严重受限于数据从内存传送到 GPU 核心的速率。我们把执行速度受内存带宽限制的程序称为访存受限程序。

一个点相对这两条线的位置，说明了应用的效率。接近两条线的点表示应用在高效地利用内存带宽或计算单元，而远低于这两条线的应用则表明对资源的利用效率不高。这两条线的交点所对应的算术强度值，是应用从访存受限过渡到计算受限的分界点。算术强度较低的应用属于访存受限，受内存带宽限制，无法达到峰值吞吐量；算术强度较高的应用属于计算受限，不受内存带宽限制。

例如，点 A1 和 A2 都代表访存受限的应用，而 A3 代表计算受限的应用。A1 高效地利用资源，运行在接近峰值内存带宽的水平，而 A2 则不然。对于 A2，或许还有通过改善内存带宽利用率来进一步提高吞吐量的优化空间。然而，对于 A1，提高吞吐量的唯一途径是提高应用的算术强度。

为了进一步提高这个核函数的性能，我们需要通过减少它所执行的全局内存访问次数，来提高核函数的计算访存比。例如，要充分利用 A100 GPU 提供的 19500 GFLOPS，至少需要 (19500 GOP/秒)/(1555 GB/秒)=12.5 OP/B 的比值。这意味着每访问一个 4 字节的浮点数值，就必须执行大约 50 次浮点运算！这个比值能在多大程度上达到，取决于当前计算所固有的数据重用程度。我们请读者参阅“Roofline 模型”边栏，那里提供了一个有用的模型，可用于根据程序的算术强度分析其潜在性能。

正如我们将看到的，矩阵乘法为减少全局内存访问提供了机会，而这些机会可以用相对简单的技术来把握。矩阵乘法函数的执行速度可能相差若干数量级，具体取决于全局内存访问的减少程度。因此，矩阵乘法为这类技术提供了一个极好的入门示例。本章将介绍一种常用的减少全局内存访问次数的技术，并在矩阵乘法上演示这一技术。

5.2 CUDA 内存类型

CUDA 设备包含多种类型的内存，可以帮助程序员提高计算访存比。图 5.2 展示了这些 CUDA 设备内存。在图的底部，我们可以看到全局内存和常量内存。这两种内存都可以由主机写入（W）和读取（R）。全局内存还可以由设备写入和读取，而常量内存支持设备进行低延迟、高带宽的只读访问。我们在第 2 章“异构数据并行计算”中介绍了全局内存，并将在第 7 章“卷积”中详细研究常量内存。

另一种内存类型是局部内存，它同样可以被读取和写入。局部内存实际上位于全局内存之中，具有相似的访问延迟，但它不在线程之间共享。每个线程都有自己的一段全局内存，用作其私有的局部内存，存放对该线程而言私有、但无法分配到寄存器中的数据。这些数据包括静态分配的数组、溢出的寄存器，以及线程调用栈中的其他元素。

图 5.2 中的寄存器和共享内存都是片上内存。存放于这两种内存中的变量，可以以非常高的速度、高度并行地被访问。寄存器分配给各个线程；每个线程只能访问自己的寄存器（见“CPU 与 GPU 的寄存器体系结构”边栏）。核函数通常使用寄存器来保存各线程私有的、被频繁访问的变量。共享内存分配给线程块；一个线程块中的所有线程都可以访问为该线程块声明的共享内存变量。共享内存是线程之间共享输入数据和中间结果、从而进行协作的一种高效手段。通过在某种 CUDA 内存类型中声明一个 CUDA 变量，CUDA 程序员就决定了该变量的可见性和访问速度。

CPU 与 GPU 的寄存器体系结构

CPU 与 GPU 不同的设计目标导致了不同的寄存器体系结构。正如我们在第 4 章、“计算体系结构与调度”一章中所见，CPU 在线程之间进行上下文切换时，会把离开线程的寄存器保存到内存中，并从内存中恢复进入线程的寄存器。相比之下，GPU 通过在处理块（block）的寄存器文件中保存调度到该处理块的所有线程的寄存器，实现了零开销调度。这样，在线程束之间切换是瞬时完成的，因为进入线程的寄存器已经位于寄存器文件之中。因此，GPU 的寄存器文件需要比 CPU 的寄存器文件大得多。

我们还在第 4 章、“计算体系结构与调度”中看到，GPU 支持动态资源划分：一个 SM 可以给每个线程配备少量寄存器并执行大量线程，也可以给每个线程配备更多寄存器而执行较少的线程。因此，GPU 的寄存器文件需要设计为支持这种寄存器动态划分。相比之下，CPU 的寄存器体系结构为每个线程分配一组固定的寄存器，而不考虑线程对寄存器的实际需求。

为了充分理解寄存器、共享内存和全局内存之间的区别，我们需要更深入地了解这些不同类型的内存在现代处理器中是如何实现和使用的。正如我们在第 4 章“计算体系结构与调度”的“线程束与 SIMD 硬件”边栏中讨论的那样，几乎所有现代处理器都源于约翰·冯·诺依曼于 1945 年提出的模型，如图 5.3 所示。CUDA 设备也不例外。CUDA 设备中的全局内存对应于图 5.3 中的“内存”方框。处理器方框对应我们今天通常看到的处理器芯片边界。全局内存在处理器芯片之外，采用 DRAM 技术实现，这意味着较长的访问延迟和相对较低的访问带宽。寄存器对应于冯·诺依曼模型中的“寄存器文件”。寄存器文件位于处理器芯片上，与全局内存相比，访问延迟非常短，访问带宽也高得多。在典型的设备中，所有 SM 上所有寄存器文件的聚合访问带宽至少比全局内存高两个数量级。此外，只要变量存放在寄存器中，对它的访问就不再消耗片外全局内存带宽。这将体现为计算访存比的提高。

最后，还有一个更微妙的理由说明为什么把操作数值放在寄存器中是更好的选择。在现代计算机中，从寄存器文件访问一个数值所消耗的能量，至少比从全局内存访问一个数值低一个数量级。从寄存器访问数值在能效上比从全局内存访问数值有巨大优势。我们很快将更详细地研究在现代计算机中访问这两种硬件结构在速度和能量上的差异。另一方面，正如我们很快将了解到的，在当今的 GPU 中，每个线程可用的寄存器数量相当有限。正如我们在第 4 章“计算体系结构与调度”中所见，如果满占用率场景下的寄存器使用量超过上限，应用的占用率就会降低。因此，只要有可能，我们也需要避免过度占用这一有限资源。

图 5.4 展示了 CUDA 设备中的共享内存和寄存器。虽然两者都是片上内存，但在功能和访问成本上差别很大。共享内存是位于处理器芯片上的内存空间的一部分。当处理器访问存放在共享内存中的数据时，它需要执行一次内存加载操作，就像访问全局内存中的数据一样。然而，由于共享内存位于片上，它的访问延迟比全局内存低得多，吞吐量也高得多。由于需要执行加载操作，共享内存的延迟比寄存器长，带宽比寄存器低。用计算机体系结构的术语来说，共享内存是一种便笺存储器。

CUDA 中共享内存与寄存器的一个重要区别是：存放在共享内存中的变量可以被一个线程块中的所有线程访问。这与寄存器数据形成对比——寄存器数据对单个线程是私有的。也就是说，共享内存的设计目标，是支持线程块内线程之间高效、高带宽的数据共享。如图 5.4 所示，CUDA 设备 SM 通常采用多个处理单元，让多个线程能够同时取得进展（见第 2 章“异构数据并行计算”中的“线程”边栏）。一个线程块中的线程可以分布在这些处理单元上。因此，这些 CUDA 设备中共享内存的硬件实现通常被设计成允许多个处理单元同时访问其内容，以支持线程块内线程之间的高效数据共享。我们将学习几种重要的并行算法类型，它们都能从这种线程间高效的数据共享中受益匪浅。

到现在应该已经清楚了：寄存器、局部内存、共享内存和全局内存具有不同的功能、延迟和带宽。因此，理解如何声明变量，使它存放在所期望的内存类型中，是很重要的。表 5.1 给出了把程序变量声明到各种内存类型中的 CUDA 语法。每种这样的声明也会赋予所声明的 CUDA 变量一个作用域和生命周期。作用域标识可以访问该变量的线程集合：仅单个线程、一个线程块的所有线程，还是所有网格的所有线程。如果变量的作用域是单个线程，那么将为每个线程创建该变量的一个私有版本；每个线程只能访问其私有的变量版本。例如，如果一个核函数声明了一个作用域为单个线程的变量，并且该核函数以一百万个线程启动，那么将创建一百万个该变量的版本，以便每个线程初始化并使用自己的变量版本。

我们把不是数组的变量称为标量变量。如表 5.1 所示，在核函数和设备函数中声明的所有自动标量变量都被放入寄存器。这些自动变量的作用域局限于各个线程。当一个核函数声明一个自动变量时，会为执行该核函数的每个线程生成该变量的一个私有副本。当一个线程终止时，它的所有自动变量都不复存在。在图 5.1 中，变量 blurRow、blurCol、curRow、curCol、pixels 和 pixVal 都是自动变量，属于这一类。注意，访问这些变量非常快且高度并行，但必须小心不要超出硬件实现中寄存器存储的有限容量。使用大量寄存器会对每个 SM 的占用率产生不利影响，正如我们在第 4 章“计算体系结构与调度”中所见。

自动数组变量不会存放在寄存器中。1 相反，它们被存入线程的局部内存，可能会带来较长的访问延迟和潜在的访问拥塞。这些数组的作用域与自动标量变量一样，局限于各个线程。也就是说，每个线程都会创建并使用每个自动数组的一个私有版本。一旦线程结束执行，其自动数组变量的内容就不复存在。根据我们的经验，在核函数和设备函数中很少需要使用自动数组变量。

如果变量声明前带有__shared__关键字（每个“__”由两个“_”字符组成），就在 CUDA 中声明了一个共享变量。也可以在声明中把可选的__device__加到__shared__前面，以达到相同的效果。这种声明通常在核函数或设备函数中进行。共享变量存放在共享内存中。共享变量的作用域限于一个线程块内；也就是说，一个线程块中的所有线程看到的是共享变量的同一个版本。在核函数执行期间，每个线程块都会创建并使用共享变量的一个私有版本。共享变量的生命周期与核函数执行的持续时间一致。当一个核函数结束其网格的执行时，其共享变量的内容就不复存在。正如我们前面讨论过的，共享变量是线程块内线程相互协作的一种高效手段。从共享内存访问共享变量非常快，而且高度并行。CUDA 程序员经常使用共享变量来保存在核函数的某个执行阶段中被频繁使用和复用的那部分全局内存数据。可能需要调整算法，以创建高度聚焦于全局内存数据小部分的执行阶段，正如我们将用第 5.4 节中的矩阵乘法所演示的那样。

如果变量声明前带有__constant__关键字（每个“__”由两个“_”字符组成），就在 CUDA 中声明了一个常量变量。也可以在声明中把可选的__device__加到__constant__前面，以达到相同的效果。常量变量的声明必须在任何函数体之外。常量变量的作用域覆盖所有网格，也就是说，所有网格中的所有线程看到的是同一个常量变量版本。常量变量的生命周期覆盖整个应用的执行。常量变量通常用于为核函数提供输入值的变量。核函数代码不能改变常量变量的值。常量变量存放在全局内存中，但会被缓存以便高效访问。在适当的访问模式下，访问常量内存非常快且高度并行。目前，一个应用中常量变量的总大小被限制为 65,536 字节。可能需要拆分输入数据量，以适应这一限制。我们将在第 7 章“卷积”中演示常量内存的使用。

一个变量，如果其声明只以关键字__device__开头（每个“__”由两个“_”字符组成），就是全局变量，会被放在全局内存中。对全局变量的访问速度较慢。在较新的设备中，访问全局变量的延迟和吞吐量已通过缓存得到改善。全局变量的一个重要优点是：它对所有核函数的所有线程可见。它们的内容也会在整段执行期间持续存在。因此，全局变量可以作为线程跨线程块协作的手段。不过，必须注意：目前除了使用原子操作或终止当前核函数的执行之外，还没有简便的方法在不同线程块之间进行同步，或确保不同线程访问全局内存时数据的一致性。2 因此，全局变量通常用于把信息从一个核函数调用传递到另一个核函数调用。

在 CUDA 中，可以使用指针指向全局内存中的数据对象。在核函数和设备函数中，指针的使用通常有两种典型方式。第一种，如果对象由主机函数分配，指向对象的指针由内存分配 API 函数（如 cudaMalloc）初始化，并可以作为参数传给核函数，正如我们在第 2 章“异构数据并行计算”和第 3 章“多维网格与数据”中所见。第二种使用方式是，把在全局内存中声明的变量的地址赋给指针变量。例如，核函数中的语句{float* ptr=&GlobalVar;}把 GlobalVar 的地址赋给自动指针变量 ptr。读者应参考 CUDA Programming Guide，了解在其他内存类型中使用指针的方法。

5.3 减少内存流量的分块

在 CUDA 中，使用设备内存存在一个内在的权衡：全局内存大但慢，而共享内存小但快。一种常见策略是把数据划分成称为分块的子集，使每个分块都能放入共享内存。分块一词借用了这样一个类比：一堵大墙（即全局内存数据）可以用小瓷砖（即每个都能放入共享内存的子集）铺满。一个重要的标准是，核函数对这些分块的计算可以相互独立地进行。注意，对于任意给定的核函数，并非所有数据结构都能划分成分块。

分块的概念可以用第 3 章“多维网格与数据”中的矩阵乘法示例来说明。图 3.13 展示了一个小的矩阵乘法示例，它对应于图 3.11 中的核函数。我们在图 5.5 中复现了这个示例，方便查阅。为简洁起见，我们把 P[y*Width+x]、M[y*Width+x] 和 N[y*Width+x] 分别简写为 Py,x、My,x 和 Ny,x。这个示例假设我们使用四个 2×2 的线程块来计算 P 矩阵。P 矩阵中的粗线方框标明了每个线程块处理的 P 元素。图 5.5 突出了线程块 0,0 的四个线程所完成的计算。这四个线程计算 P0,0、P0,1、P1,0 和 P1,1。线程块 0,0 的线程 0,0 和线程 0,1 对 M 和 N 元素的访问用黑色箭头标出。例如，线程 0,0 读取 M0,0 和 N0,0，接着读取 M0,1 和 N1,0，再读取 M0,2 和 N2,0，最后读取 M0,3 和 N3,0。

图 5.6 展示了线程块 0,0 中所有线程完成的全局内存访问。线程沿垂直方向列出，访问时间沿水平方向从左向右递增。注意，每个线程在执行期间都要访问 M 的四个元素和 N 的四个元素。在被突出的四个线程中，它们访问的 M 和 N 元素有相当大的重叠。例如，线程 0,0 和线程 0,1 都访问 M0,0 以及 M 第 0 行的其余元素。同样，线程 0,1 和线程 1,1 都访问 N0,1 以及 N 第 1 列的其余元素。

图 3.11 中的核函数的编写方式是：线程 0,0 和线程 0,1 都从全局内存访问 M 的第 0 行元素。如果我们能以某种方式让线程 0,0 和线程 0,1 协作，使这些 M 元素只从全局内存加载一次，就可以把对全局内存的访问总次数减少一半。事实上，我们可以看到，在线程块 0,0 的执行过程中，每个 M 和 N 元素都恰好被访问两次。因此，如果我们能让这四个线程在访问全局内存时相互协作，就可以把全局内存流量减少一半。

读者应该验证：在矩阵乘法示例中，全局内存流量的潜在减少量与所用线程块的维数成正比。使用 Width×Width 的线程块时，全局内存流量的潜在减少量可达到 Width 倍。也就是说，如果我们使用 16×16 的线程块，通过线程之间的协作，就可以把全局内存流量潜在减少到原来的 1/16。

我们现在介绍一种分块矩阵乘法算法。其基本思想是：在线程各自把这些 M 和 N 元素用于点积计算之前，让线程们协作地把 M 和 N 元素的子集加载到共享内存中。要记住，共享内存的容量相当小，在把这些 M 和 N 元素加载到共享内存时，必须小心不要超出共享内存的容量。这可以通过把 M 和 N 矩阵划分成更小的分块来实现。这些分块的大小要选择得能放入共享内存。在最简单的形式中，分块的维数与线程块的维数相等，如图 5.7 所示。

在图 5.7 中，我们按照粗线所划分的那样，把 M 和 N 分成 2×2 的分块。每个线程执行的点积计算现在被划分成多个阶段。在每个阶段中，线程块中的所有线程协作，把一个 M 分块和一个 N 分块加载到共享内存中。这可以通过让线程块中的每个线程把一个 M 元素和一个 N 元素加载到共享内存来实现，如图 5.8 所示。图 5.8 的每一行展示一个线程的执行活动。注意，时间从左向右推进。我们只需要展示线程块 0,0 中线程的活动；其他线程块的行为完全相同。用于 M 元素的共享内存数组称为 Mds，用于 N 元素的共享内存数组称为 Nds。在阶段 1 开始时，线程块 0,0 的四个线程协作地把一个 M 分块加载到共享内存：线程 0,0 把 M0,0 加载到 Mds0,0，线程 0,1 把 M0,1 加载到 Mds0,1，线程 1,0 把 M1,0 加载到 Mds1,0，线程 1,1 把 M1,1 加载到 Mds1,1。这些加载显示在图 5.8 的第二列。一个 N 分块也以类似方式加载，显示在图 5.8 的第三列。

在两个 M 和 N 分块被加载到共享内存之后，这些元素就被用于点积的计算。注意，共享内存中的每个值都被使用两次。例如，由线程 1,1 加载到 Mds1,1 的 M1,1 值被使用两次，一次由线程 1,0 使用，一次由线程 1,1 使用。通过把每个全局内存值加载到共享内存，使它可以被多次使用，我们减少了访问全局内存的次数。在这种情况下，访问全局内存的次数减少了一半。读者应该验证：如果分块是 N×N 个元素，减少量就是 N 倍。

注意，每个点积的计算现在分两个阶段进行，即图 5.8 中的阶段 1 和阶段 2。在每个阶段中，每个线程把两对输入矩阵元素的乘积累加到 Pvalue 变量中。注意，Pvalue 是自动变量，所以会为每个线程生成一个私有版本。我们加上下标只是为了说明这些是为每个线程创建的 Pvalue 变量的不同实例。第一阶段的计算显示在图 5.8 的第四列，第二阶段显示在第七列。一般来说，如果输入矩阵的维数为 Width，分块大小为 TILE_WIDTH，那么点积将分 Width/TILE_WIDTH 个阶段进行。这些阶段的形成是减少对全局内存访问的关键。由于每个阶段聚焦于输入矩阵值的一个小子集，线程们可以协作地把该子集加载到共享内存，并用共享内存中的值来满足本阶段相互重叠的输入需求。

还要注意，Mds 和 Nds 会在各阶段之间复用。在每个阶段，相同的 Mds 和 Nds 被复用来存放该阶段用到的 M 和 N 元素子集。这样，小得多的共享内存就可以满足大部分对全局内存的访问。这是因为每个阶段都聚焦于输入矩阵元素的一个小子集。这种聚焦的访问行为称为数据局部性。当一个算法表现出数据局部性时，就有机会使用小而高速的内存来满足大部分访问，把这些访问从全局内存中移除。数据局部性对于在多核 CPU 上取得高性能，与在多线程 GPU 上一样重要。我们将在第 6 章“性能考量”中回到数据局部性这一概念。

5.4 分块矩阵乘法核函数

我们现在准备介绍一个使用共享内存来减少全局内存流量的分块矩阵乘法核函数。图 5.9 所示的核函数实现了图 5.8 中说明的阶段。在图 5.9 中，第 04 行和第 05 行分别把 Mds 和 Nds 声明为共享内存数组。回忆一下，共享内存变量的作用域是一个线程块。因此，每个线程块都会创建一组 Mds 和 Nds 数组，线程块中的所有线程都可以访问同一个 Mds 和 Nds 版本。这一点很重要，因为线程块中的所有线程都必须能够访问由同伴加载到 Mds 和 Nds 中的 M 和 N 元素，以便用这些值满足自己的输入需求。

第 07 行和第 08 行把 threadIdx 和 blockIdx 的值保存到名称更短的自动变量中，使代码更简洁。回忆一下，自动标量变量会被放入寄存器。它们的作用域在单个线程内。也就是说，运行时系统会为每个线程创建 tx、ty、bx 和 by 各一个私有版本，它们位于该线程可访问的寄存器中。这些变量用 threadIdx 和 blockIdx 的值初始化，并在线程的生命周期内被多次使用。线程一旦结束，这些变量的值就不复存在。

第 11 行和第 12 行分别确定线程要生成的 P 元素的行索引和列索引。代码假设每个线程负责计算一个 P 元素。如第 12 行所示，线程要生成的 P 元素的水平（x）位置，即列索引，可以计算为 bx*TILE_WIDTH+tx。这是因为每个线程块在水平方向上覆盖 P 的 TILE_WIDTH 个元素。线程块 bx 中的一个线程，前面有 bx 个线程块，即(bx*TILE_WIDTH)个线程；它们覆盖 P 的 bx*TILE_WIDTH 个元素。同一线程块中的另外 tx 个线程会再覆盖 tx 个元素。因此，具有 bx 和 tx 的线程应负责计算 x 索引为 bx*TILE_WIDTH+tx 的 P 元素。以图 5.7 中的示例为例，线程块 1,0 中线程 0,1 要计算的 P 元素的水平（x）索引为 0*2+1=1。这个水平索引被保存在该线程的变量 Col 中，也在图 5.10 中作了说明。

类似地，线程要处理的 P 元素的垂直（y）位置，即行索引，计算为 by*TILE_WIDTH+ty。回到图 5.7 中的示例，线程块 1,0 中线程 0,1 要计算的 P 元素的 y 索引为 1*2+0=2。这个垂直索引被保存在线程的变量 Row 中。如图 5.10 所示，每个线程计算位于第 Col 列、第 Row 行的 P 元素。因此，线程块 1,0 中线程 0,1 要计算的 P 元素是 P2,1。

图 5.9 的第 16 行标记了循环的开始，该循环遍历计算 P 元素的各个阶段。循环的每次迭代对应图 5.8 所示计算的一个阶段。ph 变量表示点积已经完成的阶段数。回忆一下，每个阶段使用一个 M 分块和一个 N 分块。因此，在每个阶段开始时，前面的阶段已经处理了 ph*TILE_WIDTH 对 M 和 N 元素。

在每个阶段中，图 5.9 的第 19 行和第 20 行分别把相应的 M 和 N 元素加载到共享内存中。既然我们已经知道线程要处理的 M 的行和 N 的列，现在把注意力转向 M 的列索引和 N 的行索引。如图 5.10 所示，每个线程块有 TILE_WIDTH2 个线程，它们将协作地把 TILE_WIDTH2 个 M 元素和 TILE_WIDTH2 个 N 元素加载到共享内存中。因此，我们只需给每个线程分配一个 M 元素和一个 N 元素来加载。使用 blockIdx 和 threadIdx 就可以方便地做到这一点。注意，要加载的 M 元素段的起始列索引为 ph*TILE_WIDTH。因此，一个简单的方法是让每个线程加载一个距该起始点 tx（即 threadIdx.x 的值）个位置的元素。类似地，要加载的 N 元素段的起始行索引也是 ph*TILE_WIDTH。因此，每个线程加载一个距该起始点 ty（即 threadIdx.y 的值）个位置的元素。

这正是我们在第 19 行和第 20 行所做的。在第 19 行，每个线程加载 M[Row*Width + ph*TILE_WIDTH + tx]，其中的线性化索引由行索引 Row 和列索引 ph*TILE_WIDTH + tx 构成。由于 Row 的值是 ty 的线性函数，这 TILE_WIDTH2 个线程中的每一个都会把一个唯一的 M 元素加载到共享内存，因为每个线程都有唯一的 tx 和 ty 组合。这些线程合起来将加载图 5.10 中 M 的深色方块子集。类似地，在第 20 行，每个线程使用线性化索引(ph*TILE_WIDTH + ty)*Width + Col 把相应的 N 元素加载到共享内存。读者应该使用图 5.7 和图 5.8 中的小示例来验证地址计算对各个线程是否正确。

第 21 行的屏障__syncthreads()确保所有线程都已完成把 M 和 N 分块加载到 Mds 和 Nds 的工作，之后任何线程才能继续前进。回忆第 4 章“计算体系结构与调度”中的内容，调用__syncthreads()可以让线程块中的所有线程等待彼此到达屏障，然后任何线程才能继续。这一点很重要，因为线程要使用的 M 和 N 元素可能由其他线程加载。需要确保所有元素都被正确加载到共享内存中之后，任何线程才能开始使用这些元素。第 23 行的循环随后基于分块元素执行一个阶段的点积。线程 ty, tx 的循环推进过程显示在图 5.10 中，M 和 N 元素的访问方向沿着标有 k 的箭头，k 是第 23 行中的循环变量。注意，这些元素将从 Mds 和 Nds 中访问，它们是存放这些 M 和 N 元素的共享内存数组。第 26 行的屏障__syncthreads()确保所有线程都已完成对共享内存中 M 和 N 元素的使用，之后任何线程才能进入下一次迭代并从下一组分块加载元素。这样，就不会有线程过早地加载元素，从而破坏其他线程的输入值。

第 21 行和第 26 行的两次__syncthreads()调用展示了并行程序员在协调线程时常需要分析的两种不同类型的数据依赖。第一种称为写后读依赖，因为线程必须先等待其他线程把数据写到适当位置，然后才能读取它。第二种称为读后写依赖，因为线程必须先等待所有需要该数据的线程读完，然后才能覆盖它。写后读依赖和读后写依赖的别名分别是真依赖和伪依赖。写后读依赖是真依赖，因为读线程确实需要写线程提供的数据，所以它别无选择，只能等待。读后写依赖是伪依赖，因为写线程不需要读线程的任何数据。这种依赖是由它们复用同一个内存位置造成的；如果它们使用不同的位置，这种依赖就不会存在。

分块算法的收益是显著的。对于矩阵乘法，全局内存访问减少了 TILE_WIDTH 倍。使用 16×16 的分块，可以把全局内存访问减少 16 倍。这把计算访存比从 0.25 OP/B 提高到 4 OP/B。这一改进使 CUDA 设备的内存带宽能够支持更高的计算速率。例如，在全局内存带宽为 1555 GB/秒的 A100 GPU 上，这一改进使设备能达到 (1555 GB/秒)*(4 OP/B)=6220 GFLOPS，这比未使用分块的核函数所达到的 389 GFLOPS 要高得多。

虽然分块大幅提高了吞吐量，但 6220 GFLOPS 仍然只占设备峰值吞吐量 19500 GFLOPS 的 32%。可以进一步优化代码，减少全局内存访问次数并提高吞吐量。我们将在本书后面看到其中一些优化，而另一些高级优化则不会涉及。由于矩阵乘法在许多领域中的重要性，已经有高度优化的库，如 cuBLAS 和 CUTLASS，它们已经整合了许多这类高级优化。程序员可以使用这些库，在其线性代数应用中立即获得接近峰值的性能。

分块在提高矩阵乘法乃至一般应用的吞吐量方面的有效性，并非 GPU 独有。在 CPU 上应用分块（或阻塞）技术以提高性能，已有很长的历史，其原理是确保 CPU 线程在特定时间窗口内复用的数据能够在缓存中找到。一个关键区别是：CPU 上的分块技术隐式地依靠 CPU 缓存把复用的数据保留在片上，而 GPU 上的分块技术则显式地使用共享内存把数据保留在片上。原因是 CPU 核心通常一次只运行一两个线程，因此线程可以依靠缓存把最近使用的数据保留在身边。相比之下，GPU SM 同时运行大量线程以隐藏延迟。这些线程可能会争用缓存槽位，使 GPU 缓存不那么可靠，因此对于要复用的重要数据，有必要使用共享内存。

虽然分块矩阵乘法核函数的性能提升令人印象深刻，但它确实做了几个简化假设。首先，假设矩阵的宽度是线程块宽度的倍数。这使核函数无法正确处理任意宽度的矩阵。第二个假设是矩阵是方阵。这在实际中并不总是成立。在下一节中，我们将介绍一个带边界检查的核函数，它消除了这些假设。

5.5 边界检查

我们现在扩展分块矩阵乘法核函数，使其能够处理任意宽度的矩阵。这些扩展必须允许核函数正确处理宽度不是分块宽度倍数的矩阵。我们把图 5.7 中的小示例改为使用 3×3 的 M、N 和 P 矩阵。修改后的示例显示在图 5.11 中。注意，矩阵的宽度为 3，不是分块宽度（2）的倍数。图 5.11 展示了线程块 0,0 在第二阶段的内存访问模式。我们看到，线程 0,1 和线程 1,1 会尝试加载不存在的 M 元素。类似地，线程 1,0 和线程 1,1 会尝试访问不存在的 N 元素。

访问不存在的元素在两方面有问题。对于访问越过行末尾的不存在元素（图 5.11 中线程 0,1 和线程 1,1 对 M 的访问），这些访问会落到错误的元素上。在我们的示例中，线程会尝试访问不存在的 M0,3 和 M1,3。那么这些内存加载会发生什么？要回答这个问题，我们需要回到二维矩阵的线性化布局。在线性化布局中，M0,2 之后的下一个元素是 M1,0。虽然线程 0,1 尝试访问 M0,3，但它最终会得到 M1,0。在随后的内积计算中使用这个值，显然会破坏输出值。

访问越过列末尾的元素也会出现类似问题（图 5.11 中线程 1,0 和线程 1,1 对 N 的访问）。这些访问指向数组已分配区域之外的内存位置。在某些系统中，它们会从其他数据结构返回随机值。在其他系统中，这些访问会被拒绝，导致程序中止。无论哪种方式，这类访问的结果都是不可取的。

从我们迄今的讨论来看，似乎有问题的访问只出现在线程执行的最后一个阶段。这会让我们认为，可以在分块核函数执行的最后阶段采取特殊措施来处理。遗憾的是，事实并非如此。有问题的访问可能出现在所有阶段。图 5.12 展示了线程块 1,1 在阶段 0 期间的内存访问模式。我们看到，线程 1,0 和线程 1,1 尝试访问不存在的 M 元素 M3,0 和 M3,1，而线程 0,1 和线程 1,1 尝试访问不存在的 N0,3 和 N1,3。

注意，这些有问题的访问不能简单地通过排除那些不计算有效 P 元素的线程来防止。例如，线程块 1,1 中的线程 1,0 不计算任何有效的 P 元素。然而，它在阶段 0 期间需要为线程块 1,1 中的其他线程加载 M2,1 供它们使用。此外，注意有些计算有效 P 元素的线程也会尝试访问不存在的 M 或 N 元素。例如，正如我们在图 5.11 中看到的，线程块 0,0 的线程 0,1 计算有效的 P 元素 P0,1。然而，它在阶段 1 期间尝试访问不存在的 M0,3。这两个事实表明，我们需要为加载 M 分块、加载 N 分块以及计算/存储 P 元素使用不同的边界条件测试。一条经验法则是：每一次内存访问都需要有相应的检查，确保访问所用的索引在所用数组的边界之内。

我们先从加载输入分块的边界测试条件说起。当一个线程要加载一个输入分块元素时，它应该测试它试图加载的输入元素是否是有效元素。这可以通过检查 y 和 x 索引来轻松完成。例如，在图 5.9 的第 19 行，线性化索引由 y 索引 Row 和 x 索引 ph*TILE_WIDTH + tx 推导而来。边界条件测试将是这两个索引都小于 Width：Row < Width && (ph*TILE_WIDTH+tx) < Width。如果条件为真，线程就应该继续加载 M 元素。读者应该验证，加载 N 元素的测试条件是(ph*TILE_WIDTH+ty) < Width && Col < Width。

如果条件为假，线程就不应加载该元素。问题是，共享内存位置中应该放入什么。答案是 0.0，一个即使在内积计算中被使用也不会造成任何损害的值。如果有任何线程在内积计算中使用这个 0.0 值，内积的值不会发生任何变化。

5.6 内存使用对占用率的影响

回忆第 4 章“计算体系结构与调度”中的内容，我们讨论了最大化 SM 上线程占用率对于容忍长延迟操作的重要性。核函数的内存使用在占用率调优中起着重要作用。虽然 CUDA 寄存器和共享内存在减少全局内存访问次数方面可以极其有效，但必须小心不要超出 SM 对这些内存的容量。每个 CUDA 设备提供的资源有限，这限制了对给定应用而言可以同时驻留在 SM 中的线程数量。一般来说，每个线程需要的资源越多，每个 SM 中可以驻留的线程就越少。

我们在第 4 章“计算体系结构与调度”中看到，寄存器使用如何成为占用率的限制因素。共享内存的使用也会限制可以分配给每个 SM 的线程数量。例如，A100 GPU 可以配置为每个 SM 最多 164 KB 的共享内存，并且支持每个 SM 最多 2048 个线程。因此，要使用全部 2048 个线程槽位，一个线程块平均使用的共享内存不应超过 (164 KB)/(2048 个线程)=82 B/线程。在分块矩阵乘法示例中，每个线程块有 TILE_WIDTH2 个线程，并使用 TILE_WIDTH2*4B 的共享内存存放 Mds，使用 TILE_WIDTH2*4B 的共享内存存放 Nds。因此，该线程块平均使用 (TILE_WIDTH2*4B + TILE_WIDTH2*4B)/(TILE_WIDTH2 个线程)=8 B/线程 的共享内存。因此，分块矩阵乘法核函数的占用率不受共享内存的限制。

然而，考虑一个线程块使用 32 KB 共享内存、每个线程块有 256 个线程的核函数。在这种情况下，核函数平均使用 (32 KB)/(256 个线程)=132 B/线程 的共享内存。在如此高的共享内存使用量下，核函数无法达到满占用率。每个 SM 最多只能容纳 (164 KB)/(132 B/线程)=1272 个线程。因此，这个核函数能达到的最大占用率为 (1272 个已分配线程)/(2048 个最大线程)=62%。

注意，每个 SM 中共享内存的大小也因设备而异。每一代或每一种型号的设备，其每个 SM 中的共享内存数量都可能不同。核函数通常希望能够根据硬件中可用的共享内存数量来使用不同量的共享内存。也就是说，我们可能希望主机代码动态地确定共享内存的大小，并调整核函数使用的共享内存量。这可以通过调用 cudaGetDeviceProperties 函数来完成。假设变量&devProp 被传给该函数。在这种情况下，字段 devProp.sharedMemPerBlock 给出每个 SM 中可用的共享内存量。程序员随后可以确定每个线程块应使用的共享内存量。

5.7 小结

总而言之，在现代处理器中，程序的执行速度可能严重受限于内存的速度。为了充分利用 CUDA 设备的执行吞吐量，需要努力在核函数代码中获得较高的计算访存比。如果这个比值较低，核函数就是访存受限的。也就是说，它的执行速度受限于从内存访问其操作数的速率。

CUDA 提供对寄存器、共享内存和常量内存的访问。这些内存比全局内存小得多，但访问速度要高得多。有效使用这些内存需要对算法进行重新设计。我们以矩阵乘法为例说明分块，这是一种增强数据访问局部性、实现共享内存有效利用的常用策略。在并行编程中，分块使用屏障同步，强制多个线程在每个执行阶段共同聚焦于输入数据的一个子集，以便该子集数据可以被放入这些特殊类型的内存中，从而实现高得多的访问速度。

然而，CUDA 程序员必须意识到这些特殊类型内存的有限容量。它们的容量取决于具体实现。一旦超出这些容量，它们就会限制每个 SM 中能同时执行的线程数量，并可能对 GPU 的计算吞吐量及其容忍延迟的能力产生不利影响。在开发应用时具备对硬件限制的推理能力，是并行编程的一个关键方面。

虽然我们是在 CUDA C 编程的语境下介绍分块算法的，但它在几乎所有类型的并行计算系统中都是实现高性能的有效策略。原因是应用必须在数据访问中表现出局部性，才能有效利用这些系统中的高速内存。例如，在多核 CPU 系统中，数据局部性使应用能够有效利用片上数据缓存来降低内存访问延迟并实现高性能。这些片上数据缓存同样容量有限，要求计算表现出局部性。因此，读者在使用其他编程模型为其他类型的并行计算系统开发并行应用时，也会发现分块算法很有用。

本章的目标是介绍局部性、分块以及不同类型 CUDA 内存的概念。我们介绍了一个使用共享内存的分块矩阵乘法核函数。我们还进一步研究了在应用分块技术时，为支持任意数据维度而进行边界测试的必要性。我们还简要讨论了动态大小共享内存分配的使用，使核函数能够根据硬件能力调整每个线程块使用的共享内存大小。我们没有讨论分块中寄存器的使用。我们将在本书第二部分讨论并行算法模式时，解释分块算法中寄存器的使用。
