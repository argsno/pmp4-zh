摘要

本章首先回顾把异构并行计算推向主流的那些历史事件，以此引入全书内容。本章区分了面向延迟的多核 CPU 与面向吞吐量的多线程 GPU，它们是现代异构计算系统中两类主要的计算设备。随后，本章讨论应用不断要求更高速度的主要原因，以及阿姆达尔定律——一条关于真实应用并行化的重要观察。接着，本章说明全书如何应对并行算法与并行编程中的主要挑战，以及从本书中学到的、以 CUDA（本书编程实例与习题所选用的语言）为基础的技能，如何推广到其他并行编程接口。最后，本章点明全书的总体目标，并介绍其余各章的内容与编排理由。

自计算诞生之日起，就有许多高价值的应用所要求的执行速度和资源超出了计算设备所能提供的水平。早期应用依靠处理器速度、内存速度和内存容量的提升来增强应用层面的能力，例如天气预报的时效性、工程结构分析的精度、计算机生成图形的逼真程度、每秒处理的机票预订数量以及每秒处理的资金转账笔数。近年来，深度学习等新型应用所要求的执行速度和资源，甚至超出了最好的计算设备所能提供的水平。在过去五十年里，这些应用需求推动了计算设备能力的快速进步，并且在可预见的未来还将继续如此。

以单个中央处理器（CPU）为基础、看上去按顺序逐步执行指令的微处理器（例如 Intel 和 AMD 的×86 处理器），凭借快速攀升的时钟频率和硬件资源，在 20 世纪 80 年代和 90 年代推动了计算机应用性能的迅速提升与成本的迅速下降。在这二十年的增长期里，这些单 CPU 微处理器把 GFLOPS，即每秒十亿（109）次浮点运算，带到了桌面，把 TFLOPS，即每秒万亿（1012）次浮点运算，带到了数据中心。这种对性能提升的不懈追求，使应用软件能够提供更多功能、拥有更好的用户界面，并产生更有用的结果。而用户一旦习惯了这些改进，反过来又会要求更多改进，从而为计算机产业造就了一个正向（良性）循环。

然而，由于功耗和散热问题，这一势头自 2003 年起放缓。这些问题限制了时钟频率的提高，也限制了单个 CPU 在维持“按顺序逐步执行指令”这一表象的前提下、每个时钟周期内所能完成的有效工作。此后，几乎所有微处理器厂商都转向了这样一种模式：在每块芯片中使用多个物理 CPU（称为处理器核心）来提升处理能力。在这一模式下，传统 CPU 可以看作单核心 CPU。要从多个处理器核心中获益，用户必须拥有多条能在这些处理器核心上同时执行的指令序列，无论它们来自同一个应用还是不同应用。而要让某个特定应用从多个处理器核心中获益，就必须把它的工作划分为能在这些处理器核心上同时执行的多条指令序列。从单个 CPU 按顺序逐步执行指令，转变为多个核心并行执行多条指令序列，这一转变给软件开发者群体带来了巨大冲击。

传统上，绝大多数软件应用都写成串行程序，由冯·诺依曼在 1945 年那份开创性报告中所设想的处理器来执行（von Neumann et al., 1972）。人们可以把这些程序的执行理解为：依据程序计数器（文献中也称为指令指针）的概念，顺序地逐条走过代码。程序计数器中存放着处理器将要执行的下一条指令的内存地址。应用这样顺序、逐步地执行所产生的指令执行活动序列，在文献中称为执行线程，简称线程。线程这一概念极为重要，本书其余部分将对它给出更正式的定义，并广泛使用。

从历史上看，大多数软件开发者依靠硬件的进步——例如时钟频率的提高，以及在底层同时执行多条指令——来提升其串行应用的速度；每推出一代新处理器，同样的软件只需照旧运行就会更快。计算机用户也逐渐形成了这样的预期：每换一代微处理器，这些程序就会跑得更快。这一预期已经有十多年不再成立了。串行程序只会在其中一个处理器核心上运行，而单个核心的速度并不会随着代际更替显著提升。没有了性能提升，应用开发者就无法在新微处理器问世时为软件引入新特性和新能力；这会减少整个计算机产业的增长机会。

相反，能够随着每一代新微处理器持续获得显著性能提升的应用软件，将是并行程序——其中多个执行线程协同工作，从而更快地完成任务。并行程序相对于串行程序这种新的、急剧扩大的优势，被称为并发革命（Sutter and Larus, 2005）。并行编程的实践绝非新事物。高性能计算（HPC）领域几十年来一直在开发并行程序。这些并行程序通常运行在昂贵的大型计算机上。只有少数重要应用值得动用这类计算机，因此并行编程的实践一直局限于少量应用开发者。如今所有新的微处理器都是并行计算机，需要以并行程序形式开发的应用数量急剧增加。软件开发者现在亟需学习并行编程，而这正是本书的主题。

1.1 异构并行计算

自 2003 年以来，半导体产业在微处理器设计上确立了两条主要路线（Hwu et al., 2008）。多核路线力求在走向多个核心的同时，保持串行程序的执行速度。多核处理器最初只有两个核心，此后核心数量随每一代半导体工艺不断增加。近期的一个例子是 Intel 的一款多核服务器微处理器，最多拥有 24 个处理器核心，每个核心都是实现完整 ×86 指令集的乱序、多发射处理器，支持两个硬件线程的超线程，其设计目标是最大化串行程序的执行速度。另一个例子是近期的 ARM Ampere 多核服务器处理器，拥有 128 个处理器核心。

相比之下，多线程路线更关注并行应用的执行吞吐量。多线程路线一开始就使用大量线程，同样地，线程数量也随每一代不断增加。近期的代表是 NVIDIA Tesla A100 图形处理器（GPU），它拥有数万个线程，在大量简单的顺序流水线中执行。自 2003 年以来，多线程处理器（尤其是 GPU）一直在浮点性能的竞赛中领先。截至 2021 年，A100 GPU 的峰值浮点吞吐量为：64 位双精度 9.7 TFLOPS，32 位单精度 156 TFLOPS，16 位半精度 312 TFLOPS。相比之下，近期 Intel 24 核心处理器的峰值浮点吞吐量为双精度 0.33 TLOPS、单精度 0.66 TFLOPS。近几年来，多线程 GPU 与多核 CPU 之间的峰值浮点计算吞吐量之比一直在增大。这些并不一定是应用能达到的速度，而只是这些芯片中的执行资源在理论上可能支持的原始速度。

多核与多线程之间如此巨大的峰值性能差距，相当于积聚起了可观的“电势”，到某个时刻总要释放出来。我们已经到了那个时刻。迄今为止，这一巨大的峰值性能差距已经促使许多应用开发者把软件中计算密集的部分搬到 GPU 上执行。也许更重要的是，并行执行性能的大幅提升，催生了深度学习这类革命性的新应用，它们本质上就由计算密集的部分构成。不难理解，这些计算密集的部分同样是并行编程的首要目标：要做的工作越多，把工作分配给相互协作的并行工作者（也就是线程）的机会就越多。

有人可能会问，为什么多线程 GPU 与多核 CPU 之间的峰值性能差距会如此之大。答案在于这两类处理器在基本设计理念上的差异，如图 1.1 所示。如图 1.1A 所示，CPU 的设计针对串行代码的性能做了优化。其算术单元和操作数传送逻辑的设计目标，是把算术运算的有效延迟降到最低，代价是每个单元占用更多的芯片面积和功耗。大容量的末级片上缓存用于捕获频繁访问的数据，把一部分长延迟的内存访问转化为短延迟的缓存访问。复杂的分支预测逻辑和执行控制逻辑则用来缓解条件分支指令的延迟。通过降低各类操作的延迟，CPU 硬件降低了每个线程的执行延迟。然而，低延迟的算术单元、复杂的操作数传送逻辑、大容量缓存和控制逻辑，都会占用芯片面积和功耗，而这些资源本可以用来提供更多的算术执行单元和内存访问通道。这种设计思路通常称为面向延迟的设计。

另一方面，GPU 的设计理念则由高速增长的电子游戏产业所塑造：高级游戏要求每一视频帧都能完成海量的浮点计算和内存访问，这带来了巨大的经济压力。这一需求促使 GPU 厂商想方设法，把尽可能多的芯片面积和功耗预算投入到浮点计算与内存访问吞吐量上。

在图形应用中，视点变换、物体渲染等任务需要每秒完成海量浮点计算，这一点很容易理解。此外，每秒完成海量内存访问的需求同样重要，甚至可能更为重要。许多图形应用的速度，受限于数据在内存系统与处理器之间往返传送的速率。GPU 必须能够把极其庞大的数据量搬入和搬出其 DRAM（动态随机存取存储器）中的图形帧缓冲区，因为正是这种搬运让视频画面丰富、令玩家满意。游戏应用普遍接受的宽松内存模型（即各类系统软件、应用和 I/O 设备对其内存访问行为的预期方式），也让 GPU 更容易支持大规模并行的内存访问。

相比之下，通用处理器必须满足既有操作系统、应用和 I/O 设备提出的种种要求，这些要求给支持并行内存访问带来了更多挑战，也使提高内存访问吞吐量（通常称为内存带宽）变得更加困难。结果是，图形芯片的内存带宽一直约为同期 CPU 芯片的 10 倍，而且我们预计在未来一段时间内，GPU 在内存带宽方面仍将保持优势。

一个重要的观察是：就功耗和芯片面积而言，降低延迟远比提高吞吐量昂贵。例如，把算术单元的数量翻倍就可以让算术吞吐量翻倍，代价是芯片面积和功耗翻倍。然而，要把算术延迟减半，可能需要把电流加倍，代价是所用芯片面积增加一倍以上、功耗变为四倍。因此，GPU 中通行的做法是针对海量线程的执行吞吐量进行优化，而不是降低单个线程的延迟。这种设计思路允许流水化的内存通道和算术运算具有较长的延迟，从而节省芯片面积和功耗。内存访问硬件与算术单元在面积和功耗上的缩减，使 GPU 设计者能够在一块芯片上放置更多这样的单元，进而提高总的执行吞吐量。图 1.1 直观地展示了两种设计思路的差异：图 1.1A 中的 CPU 设计采用较少而较大的算术单元和较少的内存通道，与之相对，图 1.1B 中则是数量更多但更小的算术单元和更多的内存通道。

为这些 GPU 编写的应用软件，需要包含大量并行线程。当其中一部分线程在等待长延迟的内存访问或算术运算时，硬件可以利用数量众多的线程找到其他可做的工作。图 1.1B 中的小容量缓存用于帮助控制这类应用的带宽需求，使访问同一内存数据的多个线程不必都去访问 DRAM。这种设计风格通常称为面向吞吐量的设计，因为它力求最大化大量线程的总执行吞吐量，同时允许单个线程的执行时间可能长得多。

显然，GPU 被设计成并行的、面向吞吐量的计算引擎，因此在某些 CPU 本就擅长的任务上表现不佳。对于只有一个或极少线程的程序，操作延迟更低的 CPU 能取得远高于 GPU 的性能；而当程序拥有大量线程时，执行吞吐量更高的 GPU 就能取得远高于 CPU 的性能。因此可以预料，许多应用会同时使用 CPU 和 GPU：把串行部分放在 CPU 上执行，把数值密集的部分放在 GPU 上执行。这正是 NVIDIA 于 2007 年推出的 Compute Unified Device Architecture（CUDA）编程模型被设计为支持应用的 CPU-GPU 协同执行的原因。

还要注意的是，应用开发者在为自己的应用挑选处理器时，速度并不是唯一的决定因素，另有几个因素甚至可能更为重要。首要的一点是，所选处理器必须在市场上占有很大份额，这被称为该处理器的装机量。原因很简单：软件开发的成本，只有靠庞大的客户群体才最划算。运行在市场份额很小的处理器上的应用，不会拥有庞大的客户基础。对传统并行计算系统而言，这一直是个大问题——与通用微处理器相比，它们的市场份额微不足道。在这些传统并行计算系统上，只有少数由政府和大公司资助的重要应用被成功开发出来。多线程 GPU 的出现改变了这一局面。由于在 PC 市场上广受欢迎，GPU 的销量已达数亿。几乎所有台式 PC 和高端笔记本电脑中都装有 GPU。迄今为止，投入使用的支持 CUDA 的 GPU 已超过 10 亿块。如此庞大的市场规模，使这些 GPU 成为对应用开发者极具经济吸引力的目标。

另一个重要的决定因素是实用的外形尺寸与易获取性。在 2006 年之前，并行软件应用都运行在数据中心服务器或部门级集群上，而这类执行环境往往限制了这些应用的使用。例如在医学影像这类应用中，基于一台 64 节点的集群机器发表论文是没问题的，但磁共振成像（MRI）设备上真正的临床应用，一直是基于 PC 与专用硬件加速器的某种组合。原因很简单：GE 与 Siemens 这样的厂商无法把需要成排服务器机柜的 MRI 设备卖到临床场景中，尽管这在高校院系环境中很常见。事实上，美国国立卫生研究院（NIH）曾有一段时间拒绝资助并行编程项目；他们认为并行软件的影响有限，因为基于大型集群的机器在临床环境中行不通。如今，许多公司出售配备 GPU 的 MRI 产品，NIH 也资助使用 GPU 计算的研究。

在 2006 年之前，图形芯片非常难用，因为程序员必须借助图形应用程序编程接口（API）函数之类的手段来访问其处理单元，也就是说，要用 OpenGL 或 Direct3D 技术来给这些芯片编程。说得更直白些，一段计算必须表达成“以某种方式给像素上色”的函数，才能在这些早期 GPU 上执行。这种技术被称为 GPGPU，即使用 GPU 进行通用编程。即便有了更高层的编程环境，底层代码仍然必须套进那些为像素上色而设计的 API。这些 API 限制了人们真正能为早期 GPU 编写的应用种类。因此，GPGPU 并未成为一种普及的编程现象。尽管如此，这项技术仍然足够激动人心，激发出一些了不起的努力和出色的研究成果。

2007 年，随着 CUDA 的发布（NVIDIA, 2007），一切都改变了。CUDA 不只代表软件上的变化，芯片上还增加了额外的硬件。NVIDIA 确实拿出了硅片面积来降低并行编程的难度。在面向并行计算的 G80 及其后续芯片中，GPGPU 程序完全不必再经过图形接口，取而代之的是硅片上一个新的通用并行编程接口，直接服务于 CUDA 程序的请求。这个通用编程接口极大地拓宽了人们能够轻松为 GPU 开发的应用类型。其他所有软件层也一并重做，使程序员可以使用熟悉的 C/C++ 编程工具。

虽然 GPU 是异构并行计算中一类重要的计算设备，但异构计算系统中还有其他重要类型的计算设备被用作加速器。例如，现场可编程门阵列已被广泛用于加速网络应用。本书以 GPU 为学习载体所讲的技术，同样适用于这些加速器的编程工作。

1.2 为什么需要更高的速度或并行性？

正如我们在 Section 1.1 中所说，大规模并行编程的主要动因，是让应用能够在未来的硬件世代中持续享受速度提升。正如我们将在讲解并行模式、高级模式与应用的各章（Parts II 和 III，Chapters 7 至 19）中讨论的那样，当一个应用适合并行执行时，它在 GPU 上的良好实现可以比在单个 CPU 核心上串行执行快 100 倍以上。如果应用中包含我们所说的“数据并行”，那么往往只需几个小时的工作，就能获得 10× 的加速比。

有人可能会问，为什么应用还会不断要求更高的速度？我们今天拥有的许多应用似乎已经跑得足够快了。然而，尽管当今世界的计算应用五花八门，未来许多令人兴奋的大众市场应用，正是我们过去所认为的超级计算应用，或者说超级应用。例如，生物学研究界正越来越深入地走向分子层面。显微镜大概是分子生物学中最重要的仪器，它过去一直依赖光学或电子学手段。然而，用这些仪器所能做出的分子级观测是有限的。要有效突破这些限制，可以引入一个计算模型，在传统仪器所设定的边界条件下模拟底层的分子活动。借助仿真，我们能够测量到更多细节、检验更多假设，其数量之多是仅凭传统仪器所无法想象的。在可预见的未来，这些仿真将继续从计算速度的提升中受益：能够建模的生物系统规模更大，能够在可容忍的响应时间内仿真的反应时长也更长。这些进步将对科学和医学产生巨大影响。

对于视频和音频编码与处理这类应用，不妨想想我们对数字高清（HD）电视相比老式 NTSC 电视的满意程度。一旦体验过高清电视画面的细节水平，就很难再回到旧技术。但也要想想高清电视所需的全部处理量——那是一个高度并行的过程，三维（3D）成像与可视化也是如此。未来，视点合成、低分辨率视频的高分辨率显示等新功能，会要求电视具备更强的计算能力。在消费级层面，我们将看到越来越多改善画面对焦、光照及其他关键要素的视频与图像处理应用。

更高的计算速度所带来的好处之一，是大为改善的用户界面。智能手机用户如今享有远为自然的交互方式，其高分辨率触摸屏足以媲美大屏电视。毫无疑问，这些设备的未来版本将会集成具有 3D 视角的传感器和显示屏、把虚拟空间与物理空间信息结合起来以提升可用性的应用，以及基于语音和计算机视觉的界面，而这些都需要更高的计算速度。

消费电子游戏领域也在发生类似的演进。过去，在游戏中开车不过是一组事先编排好的场景。如果你的车撞上障碍物，车辆的行进路线并不会改变，改变的只有游戏得分。车轮不会变形或损坏，即便掉了一个轮子，驾驶也不会变得更难。随着计算速度的提高，游戏可以建立在动态仿真而非事先编排的场景之上。可以预期，未来我们会体验到更多这类逼真效果：事故会损坏你的车轮，你的在线驾驶体验也会真实得多。精确建模物理现象的能力，已经催生了数字孪生（digital twin）的概念——物理对象在仿真空间中拥有精确的模型，从而能以低得多的成本充分开展压力测试和劣化预测。众所周知，逼真地建模和仿真物理效应需要极大的计算能力。

计算吞吐量的急剧提升所催生的新应用中，一个重要例子是基于人工神经网络的深度学习。虽然神经网络自 20 世纪 70 年代以来一直是活跃的研究课题，但在实际应用中一直收效不佳，因为训练这些网络需要太多带标注的数据和太多计算。互联网的兴起提供了数量惊人的带标注图片，GPU 的兴起则带来了计算吞吐量的激增。结果是，自 2012 年以来，基于神经网络的应用在计算机视觉和自然语言处理领域被迅速采纳。这一采纳彻底改变了计算机视觉与自然语言处理应用，并触发了自动驾驶汽车和家庭助理设备的快速发展。

我们提到的所有新应用，都涉及以不同方式、在不同层次上仿真和/或表示一个物理的、并发的世界，并处理海量数据。面对如此巨量的数据，大部分计算可以在数据的不同部分上并行完成，尽管在某个时刻它们必须被汇总协调。在大多数情况下，有效管理数据的传送会对并行应用可达到的速度产生重大影响。虽然做到这一点的技术往往为少数每天与此类应用打交道的专家所熟知，但绝大多数应用开发者仍能从对这些技术更直观的理解和更实用的操作知识中获益。

我们希望以直观的方式，把数据管理技术呈现给那些正规教育背景可能并非计算机科学或计算机工程的应用开发者。我们还希望提供大量实用的代码示例和动手习题，帮助读者获得可操作的知识，而这需要一个便于并行实现、并支持妥善管理数据传送的实用编程模型。CUDA 正提供了这样一个编程模型，并已经过庞大开发者社区的充分检验。

1.3 加速真实应用

并行化一个应用能带来多大的加速？某应用在计算系统 A 上相对计算系统 B 的加速比，定义为在系统 B 上执行该应用所用时间与在系统 A 上执行同一应用所用时间之比。例如，若某应用在系统 A 上执行需要 10 秒，而在系统 B 上执行需要 200 秒，那么系统 A 相对系统 B 的加速比就是 200/10=20，称为 20×（20 倍）加速比。

并行计算系统相对串行计算系统所能达到的加速比，取决于应用中可并行化部分所占的比例。例如，如果花在可并行化部分上的时间占比为 30%，那么把并行部分加速 100× 也只能把应用的总执行时间减少不到 29.7%。也就是说，整个应用的加速比只有大约 1/(1−0.297)=1.42×。事实上，即使并行部分获得无限大的加速，也最多只能砍掉 30% 的执行时间，整体加速比不超过 1.43×。通过并行执行所能达到的加速水平会被应用中可并行化的部分严重限制，这一事实被称为阿姆达尔定律（Amdahl, 2013）。另一方面，如果 99% 的执行时间处于并行部分，那么把并行部分加速 100× 就能把应用的执行时间压缩到原来的 1.99%，从而使整个应用获得 50× 的加速比。因此，要让大规模并行处理器有效加速某个应用的执行，该应用的绝大部分执行时间都处于并行部分就非常重要。

研究人员已经在某些应用上实现了超过 100× 的加速比。然而，这通常只有在算法经过增强、使超过 99.9% 的应用工作量都落在并行部分之后，再经过大量的优化与调优才能实现。

影响应用所能达到的加速比水平的另一个重要因素，是数据从内存读出和写入内存的速度。在实践中，对应用直接进行并行化往往会使内存（DRAM）带宽饱和，结果只能获得大约 10× 的加速比。诀窍在于找出绕开内存带宽限制的方法，这需要进行各类变换，以利用 GPU 专门的片上内存，从而大幅减少对 DRAM 的访问次数。然而，人们还必须进一步优化代码，以绕开诸如片上内存容量有限之类的限制。本书的一个重要目标，就是帮助读者充分理解这些优化技术，并熟练地运用它们。

请注意，相对于单核 CPU 执行所能达到的加速比，也反映出 CPU 对该应用的适配程度。在某些应用中，CPU 表现非常出色，使得用 GPU 来提升性能变得更加困难。大多数应用都有一些部分更适合由 CPU 来执行。必须给 CPU 一个公平发挥的机会，并确保代码编写成让 GPU 能够补足 CPU 的执行，从而妥善地利用组合式 CPU/GPU 系统的异构并行计算能力。时至今日，将多核心 CPU 与众核心 GPU 相结合的面向大众市场的计算系统，已把万亿次级计算带到了笔记本电脑，把百亿亿次级计算带到了计算集群。

图 1.2 展示了一个典型应用的主要组成部分。真实应用的代码大多倾向于顺序执行。这些顺序部分被表示为桃子的“核”区域；试图对这些部分应用并行计算技术，就好比咬到桃核——感觉可不好！这些部分非常难以并行化。CPU 往往在这些部分上表现得很好。好消息是，尽管这些部分可能占据代码的很大一部分，但它们通常只占超级应用执行时间的很小一部分。

接下来是所谓的“果肉”部分。这些部分很容易并行化，一些早期的图形应用也是如此。在异构计算系统中进行并行编程，能够大幅提升这些应用的速度。如图 1.2 所示，早期的 GPGPU 编程接口只覆盖了果肉部分的很小一块，这类似于最令人兴奋的应用的很小一部分。正如我们将看到的，CUDA 编程接口的设计目标是覆盖令人兴奋的应用的果肉中更大得多的部分。并行编程模型及其底层硬件仍在快速演进，以使应用中更大范围的区域也能高效地并行化。

1.4 并行编程中的挑战

是什么让并行编程变得困难？有人曾说，如果你不在乎性能，并行编程就非常容易。你真能在一个小时内写出一个并行程序。但既然你不在乎性能，又何必费心去写并行程序呢？

本书探讨了在并行编程中取得高性能所面临的若干挑战。首先也是最重要的一点，设计出在算法（计算）复杂度上与顺序算法处于同一水平的并行算法，可能颇具挑战性。许多并行算法与其顺序版本执行相同数量的工作。然而，有些并行算法比其顺序版本做更多的工作。事实上，有时它们做的工作多出太多，以至于在处理大规模输入数据集时反而运行得更慢。这尤其是个问题，因为快速处理大规模输入数据集正是并行编程的重要动机。

例如，许多现实世界的问题最自然地是用数学递推来描述的。将这些问题并行化，往往需要以非直觉的方式来思考，并且在执行过程中可能需要冗余工作。有一些重要的算法原语，例如前缀和（扫描），能够帮助把问题的顺序式、递归式的表述转化为更具并行性的形式。我们将更正式地引入工作效率这一概念，并借助重要的并行模式——例如第 11 章“前缀和（扫描）”中所介绍的前缀和——来说明，如何设计出在算法复杂度上与其顺序版本相当的并行算法，以及其中的方法与权衡。

其次，许多应用的执行速度受限于内存访问的延迟和/或吞吐量。我们把这类应用称为访存受限（的）；相比之下，计算受限的应用则受限于每字节数据所执行的指令条数。在访存受限的应用中实现高性能的并行执行，常常需要改善内存访问速度的方法。我们将在第 5 章“内存体系结构与数据局部性”与第 6 章“性能考量”中介绍针对内存访问的优化技术，并将这些技术应用于若干关于并行模式与应用的章节中。

第三，并行程序的执行速度往往比其顺序版本更容易受到输入数据特征的影响。许多现实应用需要处理特征差异很大的输入，例如大小不定或难以预测的数据量，以及不均匀的数据分布。这些在大小与分布上的变化，会导致分配给各个并行线程的工作量不均匀，从而显著降低并行执行的有效性。并行程序的性能有时会随着这些特征而剧烈波动。在介绍并行模式与应用的章节中，我们将引入一些技术，通过对数据分布进行规整化、以及动态地精细调整线程数量，来应对这些挑战。

第四，有些应用可以并行化，却几乎不需要不同线程之间的协作。这类应用常被称为易并行（的）。另一些应用则要求线程彼此协作，这就要用到同步操作，例如屏障或原子操作。这些同步操作会给应用带来开销，因为线程常常发现自己是在等待其他线程，而不是在做有用的工作。我们将在全书中讨论各种用以降低这种同步开销的策略。

幸运的是，研究人员已经解决了这些挑战中的大部分。不同应用领域之间也存在着一些共同的模式，使我们可以把一个领域中所得到的解决方案，应用到其他领域的挑战上。这正是我们之所以要在重要的并行计算模式与应用的背景下，介绍应对这些挑战的关键技术的主要原因。

1.5 相关的并行编程接口

在过去几十年中，人们提出了许多并行编程语言与模型（Mattson et al., 2004）。其中使用最为广泛的是用于共享内存多处理器系统的 OpenMP（Open, 2005），以及用于可扩展集群计算的消息传递接口（MPI）（MPI, 2009）。二者都已成为由主要计算机厂商支持的标准化编程接口。

OpenMP 的实现由一个编译器和一个运行时组成。程序员向 OpenMP 编译器给出关于某个循环的指令（命令）与编译指示（提示）。借助这些指令与编译指示，OpenMP 编译器便生成并行代码。运行时系统通过管理并行线程与资源，来支持这些并行代码的执行。OpenMP 最初是为 CPU 执行而设计的，后来被扩展以支持 GPU 执行。OpenMP 的主要优势在于，它提供了编译器自动化与运行时支持，把许多并行编程的细节从程序员那里抽象掉。这样的自动化与抽象，有助于使应用代码在由不同厂商生产的系统、以及同一厂商不同代的系统之间更具可移植性。我们把这一性质称为性能可移植性。然而，要在 OpenMP 中有效地编程，程序员仍然需要理解其中涉及的所有并行编程细节。由于 CUDA 让程序员能显式控制这些并行编程细节，即便对那些希望以 OpenMP 作为主要编程接口的人来说，它也是一种极佳的学习载体。此外，根据我们的经验，OpenMP 编译器仍在不断演进和改进。许多程序员很可能还需要在 OpenMP 编译器力有不逮的部分，使用 CUDA 风格的接口。

另一方面，MPI 是一种编程接口，其中的集群计算节点之间并不共享内存（MPI, 2009）。所有的数据共享与交互都必须通过显式的消息传递来完成。MPI 在 HPC 中得到了广泛应用。用 MPI 编写的应用已经成功地运行在拥有超过 100,000 个节点的集群计算系统上。如今，许多 HPC 集群都采用异构的 CPU/GPU 节点。由于缺乏跨计算节点的共享内存，把一个应用移植到 MPI 所需的工作量可能相当大。程序员需要进行区域分解，以在各个节点之间划分输入与输出数据。在区域分解的基础上，程序员还需要调用消息发送与接收函数，来管理节点之间的数据交换。相比之下，CUDA 为 GPU 中的并行执行提供共享内存，从而化解了这一困难。虽然 CUDA 对每个节点而言都是一种高效的接口，但大多数应用开发者仍需要使用 MPI 在集群层面编程。此外，CUDA 通过 NVIDIA 集合通信库（NCCL）等 API，对多 GPU 编程的支持也在不断增强。因此，HPC 中的并行程序员理解如何在采用多 GPU 节点的现代计算集群中进行 MPI/CUDA 联合编程，就显得十分重要，这一主题将在第 20 章“异构计算集群编程”中介绍。

2009 年，包括 Apple、Intel、AMD/ATI 和 NVIDIA 在内的几家主要行业厂商，共同开发了一种称为开放计算语言（OpenCL）的标准化编程模型（The Khronos Group, 2009）。与 CUDA 类似，OpenCL 编程模型定义了语言扩展与运行时 API，使程序员能够在大规模并行处理器中管理并行性与数据交付。与 CUDA 相比，OpenCL 更多地依赖 API，而较少依赖语言扩展。这使得各厂商能够快速调整其现有的编译器与工具来处理 OpenCL 程序。OpenCL 是一种标准化编程模型，因为用 OpenCL 开发的应用，可以在所有支持 OpenCL 语言扩展与 API 的处理器上不经修改地正确运行。然而，若要针对新的处理器获得高性能，人们往往仍需对应用进行修改。

那些同时熟悉 OpenCL 与 CUDA 的人都知道，OpenCL 的关键概念与特性同 CUDA 之间有着惊人的相似之处。也就是说，一名 CUDA 程序员可以用极少的精力学会 OpenCL 编程。更重要的是，在使用 CUDA 过程中学到的几乎所有技术，都可以轻松地应用于 OpenCL 编程。

1.6 总体目标

我们的首要目标，是教会作为读者的你如何为大规模并行处理器编程，以取得高性能。因此本书的大部分内容都致力于开发高性能并行代码的技术。我们的方法不需要太多硬件方面的专门知识。不过，你仍需要对并行硬件体系结构有良好的概念性理解，方能对你的代码性能表现做出合理的推断。因此，我们将用一些篇幅来直观地理解关键的硬件体系结构特性，并用大量篇幅来介绍开发高性能并行程序的技术。具体而言，我们将聚焦于计算思维（Wing, 2006）技术，它能使你以适合在大规模并行处理器上高性能执行的方式来思考问题。

在大多数处理器上进行高性能并行编程，都需要一些关于硬件如何运作的知识。要构建出能让程序员在没有这些知识的情况下也能开发出高性能代码的工具与机器，恐怕还需要很多年。即便有了这样的工具，我们猜想，了解硬件的程序员会比不了解的程序员更有效地运用这些工具。出于这个原因，我们专门用第 4 章“计算体系结构与调度”来介绍 GPU 体系结构的基础知识。在讨论高性能并行编程技术的过程中，我们也会探讨一些更专门的体系结构概念。

我们的第二个目标，是讲授为了正确的功能与可靠性而进行的并行编程，这在并行计算中是一个微妙问题。曾在并行系统上工作过的程序员都知道，仅仅达到初期的性能是不够的。挑战在于：要达到这样的性能，同时还能够调试代码并支持用户。CUDA 编程模型鼓励使用简单形式的屏障同步、内存一致性以及原子性来管理并行性。此外，它还提供了一系列强大的工具，使人们不仅能调试功能方面的问题，也能调试性能瓶颈。我们将说明，通过聚焦于数据并行，人们可以在自己的应用中同时实现高性能与高可靠性。

我们的第三个目标，是通过探索并行编程的方法，实现跨未来硬件代际的可扩展性，使得未来那些并行程度越来越高的机器，能够比今天的机器更快地运行你的代码。我们希望帮助你掌握并行编程，使你的程序能够扩展到新一代机器的性能水平。这种可扩展性的关键在于：对内存数据访问进行规整化与局部化，以尽量减少关键资源的消耗以及对数据结构进行更新时的冲突。因此，开发高性能并行代码的技术，对于确保应用未来的可扩展性同样十分重要。

要实现这些目标，需要大量的技术知识，因此本书将涵盖相当多的并行编程原理与模式（Mattson et al., 2004）。我们不会孤立地讲授这些原理与模式，而是把它们放在并行化实用应用的背景中来讲解。不过，我们不可能涵盖全部，因此精选了最有价值、也最经过验证的技术来详细展开。事实上，本版大幅扩充了关于并行模式的章节数量。现在，我们准备为你快速概览本书的其余部分。

1.7 本书结构

本书分为四个部分。第一部分涵盖并行编程、数据并行、GPU 以及性能优化的基础概念。这些基础性章节为读者提供了成为 GPU 程序员所必需的基本知识与技能。第二部分涵盖基础的并行模式，第三部分涵盖更高级的并行模式与应用。这两部分应用了在第一部分中学到的知识与技能，并在需要之时引入其他的 GPU 体系结构特性与优化技术。最后一部分，即第四部分，介绍高级实践，以补全那些希望成为专家级 GPU 程序员的读者的知识体系。

关于基础概念的第一部分，由第 2 章–6 章组成。第 2 章“异构数据并行计算”介绍数据并行与 CUDA C 编程。该章基于读者已有 C 语言编程经验这一前提。它首先将 CUDA C 介绍为 C 语言的一个简单、小巧的扩展，该扩展支持异构的 CPU/GPU 计算以及广泛使用的单程序多数据（SPMD）并行编程模型。接着，它涵盖了在以下过程中所涉及的思路：（1）辨识应用中需要被并行化的部分，（2）隔离出并行化代码所要使用的数据，借助 API 函数在并行计算设备上分配内存，（3）使用 API 函数把数据传送到并行计算设备，（4）把并行部分发展成为将由并行线程执行的核函数，（5）启动核函数交由并行线程执行，以及（6）最终通过一次 API 函数调用把数据传回主机处理器。我们用一个贯穿始终的向量加法示例来阐释这些概念。虽然该章的目标是讲授足够的 CUDA C 编程模型概念，使读者能够编写简单的并行 CUDA C 程序，但它也涵盖了基于任何并行编程接口来开发并行应用所需的若干基本技能。

第 3 章“多维网格与数据”更详尽地阐述了 CUDA 的并行执行模型，尤其是它与使用线程的多维组织来处理多维数据相关的部分。它使读者深入领会线程的创建、组织、资源绑定与数据绑定，从而能够用 CUDA C 实现复杂的计算。

第 4 章“计算体系结构与调度”介绍 GPU 体系结构，重点在于计算核心是如何组织的，以及线程是如何被调度到这些核心上执行的。书中讨论了各种体系结构方面的考量，以及它们对运行于 GPU 体系结构上的代码性能的影响。这些概念包括透明可扩展性、SIMD 执行与控制发散、多线程与延迟容忍，以及占用率——所有这些概念都在该章中加以定义和讨论。

第 5 章“内存体系结构与数据局部性”通过讨论 GPU 的内存体系结构，对第 4 章“计算体系结构与调度”做了延伸。它还讨论了可用于保存 CUDA 变量、以管理数据交付并提升程序执行速度的特殊内存。我们介绍分配与使用这些内存的 CUDA 语言特性。恰当地使用这些内存，能够大幅改善数据访问的吞吐量，并有助于缓解内存系统中的流量拥塞。

第 6 章“性能考量”介绍了当前 CUDA 硬件中若干重要的性能考量。具体而言，它更详细地说明了线程执行与内存访问的理想模式。这些细节构成了程序员推理其计算与数据组织决策所带来后果的概念基础。该章以一个清单作结，列出 GPU 程序员常用来优化各类计算模式的通用优化策略。这份清单将在本书接下来的两部分中，被用来优化各种并行模式与应用。

关于基础并行模式的第二部分，由第 7 章–12 章组成。第 7 章“卷积”介绍卷积——这是一种频繁使用的并行计算模式，根植于数字信号处理与计算机视觉，并且需要谨慎管理数据访问的局部性。我们也借助这一模式来引入现代 GPU 中的常量内存与缓存。第 8 章“模板”介绍模板——这是一种类似于卷积的模式，但根植于微分方程的求解，并具有一些独特特征，为进一步优化数据访问局部性提供了机会。我们也借助这一模式来引入线程与数据的三维组织，并展示第 6 章“性能考量”中引入的一种针对线程粒度的优化。

第 9 章“并行直方图”介绍直方图——这是一种在统计数据分析和大规模数据集的模式识别中广泛使用的模式。我们也借助这一模式来引入原子操作，作为协调对共享数据的并发更新的手段，以及私有化这一优化——它能降低这些操作的开销。第 10 章“归约与最小化发散”介绍归约树模式，该模式用于对一组输入数据进行汇总。我们也借助这一模式来展示控制发散对性能的影响，并演示缓解这种影响的技术。第 11 章“前缀和（扫描）”介绍前缀和（亦即扫描）——这是一种重要的并行计算模式，把本质上顺序的计算转化为并行计算。我们也借助这一模式来引入并行算法中工作效率的概念。最后，第 12 章“归并”介绍并行归并——这是一种在分而治之的工作划分策略中广泛使用的模式。我们也借助这一章来引入动态输入数据的识别与组织。

关于高级并行模式与应用的第三部分，在精神上与第二部分相似，但所涵盖的模式更为精细，且常常包含更多的应用背景。因此，这些章节较少聚焦于引入新技术或新特性，而更多聚焦于特定应用的考量。对于每一个应用，我们都从辨识构建并行执行基本结构的不同方式入手，进而推理每种方案的优劣。然后，我们走完为取得高性能所需的代码变换的各个步骤。这些章节帮助读者把前面各章的材料融会贯通，并在他们着手自己的应用开发项目时提供支持。

第三部分由第 13 章–19 章组成。第 13 章“排序”介绍两种形式的并行排序：基数排序与归并排序。这一高级模式利用了前面章节中涵盖的更基础的几种模式，尤其是前缀和（扫描）与并行归并。第 14 章“稀疏矩阵计算”介绍稀疏矩阵计算，它在处理超大规模数据集时被广泛使用。该章向读者引入为了更高效的并行访问而对数据进行重排的概念：数据压缩、填充、排序、转置与规整化。第 15 章“图遍历”介绍图算法，以及图搜索如何能在 GPU 编程中高效地实现。书中给出了许多用于并行化图算法的不同策略，并讨论了图的结构对最优算法选择的影响。这些策略建立在直方图与归并等更基础的几种模式之上。

第 16 章“深度学习”涵盖深度学习——它正成为 GPU 计算中极为重要的一个领域。我们介绍卷积神经网络的高效实现，并把更深入的讨论留给其他资料。卷积神经网络的高效实现，借助了诸如分块之类的技术以及诸如卷积之类的模式。第 17 章“迭代式磁共振成像重建”涵盖非笛卡尔 MRI 重建，以及如何借助循环融合与分散—汇聚变换等技术来提升并行性、降低同步开销。第 18 章“静电势图”涵盖分子可视化与分析——它们得益于从稀疏矩阵计算中学到的经验、用以处理不规则数据的技术。

第 19 章“并行编程与计算思维”介绍计算思维——即以更契合 HPC 的方式来表述并求解计算问题的艺术。它通过涵盖这样一种概念来做到这一点：把程序的计算任务组织起来，使它们能够并行完成。我们首先讨论把抽象的科学性的、针对具体问题的概念，组织转化为计算任务的翻译过程——这是产出高质量应用软件（无论串行还是并行）的重要第一步。该章接着讨论并行算法的结构及其对应用性能的影响，这建立在 CUDA 的性能调优经验之上。尽管我们不去深入这些不同并行编程风格的实现细节，但我们期望读者凭借在本书中所打下的基础，能够学会用其中任何一种风格来编程。我们还给出一个高层次的案例研究，以展示通过富有创造性的计算思维所能看到的机遇。

关于高级实践的第四部分，由第 20 章–22 章组成。第 20 章“异构计算集群编程”涵盖异构集群上的 CUDA 编程，其中每个计算节点都同时包含 CPU 与 GPU。我们讨论如何将 MPI 与 CUDA 结合使用，以整合节点间计算与节点内计算，以及由此产生的通信问题与实践。第 21 章“CUDA 动态并行”涵盖动态并行——即 GPU 能够基于数据或程序结构为自己动态地创建工作，而不必总是等待 CPU 来这样做。第 22 章“高级实践与未来演进”梳理了一系列杂项的、但对 CUDA 程序员而言很重要的高级特性与实践。这些主题包括零拷贝内存、统一虚拟内存、多个核函数的同时执行、函数调用、异常处理、调试、性能剖析、双精度支持、可配置的缓存/便笺存储器大小，等等。例如，早期版本的 CUDA 在 CPU 与 GPU 之间只提供有限的共享内存能力。程序员需要显式地管理 CPU 与 GPU 之间的数据传输。然而，当前版本的 CUDA 支持诸如统一虚拟内存与零拷贝内存等特性，使 CPU 与 GPU 之间能够无缝地共享数据。借助这样的支持，CUDA 程序员可以把变量与数据结构声明为在 CPU 与 GPU 之间共享。运行时硬件与软件维护一致性，并代表程序员按需自动执行经过优化的数据传输操作。这种支持显著降低了把数据传输与计算及 I/O 活动重叠在一起时所涉及的编程复杂度。在教材的入门部分，我们使用用于显式数据传输的 API，以便读者更好地理解底层实际发生的情况。随后，我们在第 22 章“高级实践与未来演进”中引入统一虚拟内存与零拷贝内存。

尽管本书各章都以 CUDA 为基础，但它们帮助读者打下并行编程的总体基础。我们相信，人最好的理解来自于具体的例子。也就是说，我们必须首先在某个特定编程模型的背景中学习这些概念，这为我们把知识推广到其他编程模型时提供了坚实的立足点。在此过程中，我们可以借鉴从 CUDA 实例中得来的具体经验。对 CUDA 的深入经验，也能使我们获得成熟度，从而有助于我们学习那些甚至可能并不属于 CUDA 模型的概念。

第 23 章“结论与展望”给出总结性评述，并对大规模并行编程的未来做出展望。我们首先重述我们的目标，并总结各章如何彼此配合以帮助实现这些目标。最后，我们以这样一个预测作结：大规模并行计算中的这些快速进展，将使之成为未来十年中最令人兴奋的领域之一。
